## 3. Traps and what the spec gets wrong versus the code

- **T1 `src/page/features/pageRuntime.ts` is 798 of 800 lines.** Adding any member to the `PageRuntime` interface (a `rawCopy` field, a `receiveSourceText` method) fails `just check-limits`. Do not touch it: install `rawCopy` in `runtime.ts` and register its host handler in its own installer. `hostHandlers.ts` (118) is not the place unless the handler needs `rt`. Also near the limit: `blockSelectionView.ts` 699 (do not add to it); `test/visual/scenarioDefinitions2.ts` is **1500 of 1500** (never add there); `scenarioDefinitions1.ts` 1471 of 1500 (only the import and the spread, 2 lines, then 1473: OK).
- **T2 Spec 2.1 bound**: use the existing exported `MAX_PAGE_TEXT_LENGTH` (hostToPage.ts:415), not `MAX_COPY_TEXT_TRANSPORT_LENGTH`.
- **T3 `mapRenderedCaret` cannot be reused as is.** It is a click caret: it needs a unique match and falls back to a 12-character tail/head match (`bTail`, `aHead`), which would silently place a copy edge at a wrong character; it skips backticks, `*_~[]` everywhere (code content such as `a*b` would be wrong, the spec rightly splits code blocks out), it does not know table pipes and delimiter rows, escapes `\*`, entities, directive opening/closing lines, option lines (`:class:`), HTML comments; it splits on `\n` only (lone CR); and it returns "the offset after the character before the click" for both sides, which is wrong for a start edge at the beginning of a text run (`Hello **world**`, start at "w": it gives the offset before `**`, the exact cut would be `world**`; and the end edge wants the opposite rule). Recommended design: a deterministic projection of the frame's source lines into (rendered char, source offset) pairs, **all whitespace dropped on both sides**, and a **whole-text equality** test against the page's rendered text (chrome removed); equal means the offset is read straight from the index map, different means `unplaced`. No search, no tail fallback. Start edge = source offset of the first selected character; end edge = source offset just after the last selected character. The BLOCK-026 projection stays as it is for clicks (a delegating wrapper), the new projection is a sibling that shares the marker-skipping.
- **T3b Rendered text vs source text separators**: `textContent` of a table or a list has no space between cells or items while the source has pipes/newlines; the whitespace-free comparison above removes the problem. Tables (the owner's example): the table is the innermost mapped frame (`tr`/`td` carry only marker lines), so the projection needs table-row rules (leading/trailing pipes, `\|` escapes, the `| --- |` delimiter row skipped).
- **T4 Chrome lists are parse5-typed.** `isChrome(element: HtmlElement)` uses `hasClass`, `attr`, `element.attrs`. The page has DOM `Element`s. The shared module must expose the data (tags, classes, attribute names and the comment-attribute rule) plus a small predicate over an accessor (`tag`, `hasClass(name)`, `attributeNames()`), with two thin adapters. Also: the export's chrome is not enough for the page. The page chrome also needs `[data-okf-comment-popover]`, the find bar, the selection status, the toolbar, `[data-okf-sbs-side="base"]` and `[data-okf-sbs-replaced]` (see T9), line numbers (`data-line-number`), KaTeX duplicate text (`.katex-mathml`), the code Copy button (a `button`, already in `REMOVED_TAGS`). And `REMOVED_TAGS` has `button`: tab labels (`button.myst-tab`) are real content, the export rebuilds tabs before that rule (radio inputs); for the clipboard HTML a tab set cut by a range would lose its labels. Decide: keep tab buttons in the HTML copy, or accept the loss (not claimed by the spec).
- **T5 Text-run edges that are not text positions**: a triple click or a Shift+Down ends at `(nextBlock, 0)` or `(parent, childIndex)`. Taken literally, "the character under the end" is the first character of the next block, so a triple-click copy of one paragraph would also copy the blank line and, for a next heading or list item, its marker (`## `, `- `). Not balancing, it is the resolution of the edge. The page handler must normalise a Range: end edge at offset 0 moves back to the end of the previous non-empty text node in the content, start edge at the end of a text node moves forward to the next one, element-level boundaries are turned into text positions before frames are collected. The spec does not say it. Needs a decision (see section 5, Q1), and E3 must include a triple-click case.
- **T6 Tab items**: spec 3.2 and E2 say "its frame is the tab set". In the code the tab **panel** is mapped (`mystGridToctree.ts:535`), so the innermost frame of a block under a tab item is the panel, whose lines include the opening `:::{tab-item} Title` line, option lines and the closing fence. The projection must therefore know container frames (admonition, tab item, card, grid): skip the opening line, leading `:option:` lines and the closing fence. Without it, every edge inside a tab item is `unplaced` and falls back to native, which breaks the E2/E3 tab case. The tab label (a `button`, only the tab set is the mapped ancestor) is the second tab case: edge in a label has the tab set as innermost frame, no rule in the spec; make it "atomic: whole tab set" or unplaced and say so.
- **T7 Frontmatter frame**: the `data-sphinx-source-end-line` of `section[data-okf-properties]` is 1; the real end is `data-okf-frontmatter-end-line` (what `lineMarker.ts:98` already does). The page handler must read it (else atomic frontmatter copies only `---`). Also the generated `--- ... ---` lines sit in the source, the "included" end line of lists may cover the blank lines after them (`mappedBlocks.ts:150` comment: the item range runs to the line before the next item): the end-edge-of-atomic rule `end of last line` is exact for fences and directives but a list in the middle of a copy keeps its trailing blank lines in the source slice anyway (verbatim, fine).
- **T8 Unmapped gaps**: spec 3.5 clamps an edge only when there is **no mapped element before/after it**. An edge inside an unmapped element that has mapped elements on one side (footnotes section, the heading anchor icons, an `hr`-like unmapped decoration, a hidden panel, the gap between blocks) matches neither "frames" nor "clamp"; the handler needs a rule: start moves to the start of the next mapped block, end to the end of the previous one (or `unplaced`). Say which.
- **T9 Side by side**: the hidden original block stays in the DOM next to its card (`data-okf-sbs-replaced`), so `range.cloneContents()` of a range spanning a card yields the current copy (card) **and** the hidden original: the text/html would duplicate the block. Remove `[data-okf-sbs-replaced]` as well as `[data-okf-sbs-side="base"]` and `[data-okf-sbs-card="removed"]` content from the HTML clone. text/plain is cut from the source, so it is right. Edge in the current side: the original is the card's next element sibling (`insertBefore(element, block)`), use it for frames; a `removed` card has no current side (edge there: native, as Q15).
- **T10 Block selection guard**: BLOCK-166's handler works only when `state.editMode && range`; spec 3.1 says "a block selection is active: the raw copy does nothing". In reading mode a leftover block selection exists (BLOCK-166 row) and the block handler ignores the key: the raw copy must then **run** (the F4 rewording promises it). Guard with the same condition as the keydown handler (`state.editMode && blockSelection.isActive()`), not `isActive()` alone. Also the guard must not apply when the copy is a context-menu copy with a block selection and edit mode on (the keydown handler is not involved): then both paths could fire; unclaimed (F6), but do not crash.
- **T11 `endLine` in `RawCopyFrame`**: always present after the sanitizer, so "else line" is a defensive default only. Frames with the same lines can nest (included blocks, a one-line container); sort outermost first by DOM order, not by line.
- **T12 Markers (constitution 1, project guidelines)**: 7 SwRS with `@implements_req` at the code point and `@tests_req` at **each** test, at most 3 IDs per marker block (`just check-markers`); the SwRS-3 marker goes on `balanceRawCut` and the resolution functions, the moved projection keeps `BLOCK-026` (3 files carry it: textEditing, textControls, editMode). `rawCopy.ts` (page) must carry the SwRS-2 and SwRS-6/7 markers on separate functions (split the handler into `shouldTake`, `edgeOf`, `clipboardHtml`) so no block exceeds 3. Do not hand-edit `index.md`, `status`, the Links block; run `just requirements-update` and commit the generated files; add the dated log entry (`## 2026-11-24`, `### Raw copy of a selection`).
- **T13 Changed approved requirements**: spec says none; BLOCK-166 and StRS-016 are `proposed` in the files I read (`req_lifecycle: proposed` in SwRS-166). Check StRS-016's `req_lifecycle` before editing (I did not read its front matter header); if `approved`, the project rule requires the owner's recorded agreement, so stop and ask.
- **T14 Performance and size**: the host posts the whole text on every ready (up to 20 MiB); the page keeps one string. Fine for documents of normal size; mention in the PR. The core function runs `sourceRangeForLines` (builds a line table each call): call it once per copy for both edges or build the table once, not per frame.
- **T15 CRLF/CR**: `lineBreak` in `RawCut` is "first line break found"; a document mixing breaks keeps its own breaks in the slice (slice is verbatim); the projection splits on `/\r\n|\n|\r/`, unlike `mapRenderedCaret`.
- **T16 Rendering the E2 helper**: `renderMyst(source, context)` does not write `data-sphinx-source-*`; the sanitizer `rewriteSphinxHtml(html, context)` does (`HtmlRewriteContext` needs `outputRoot`, `policy`, `nonce`, `sourceMapping`, `resolveResource`, `resolveNavigation`), see `test/core/render/mystFeatures.test.ts` for how existing tests build that context. The properties table (frontmatter) is rendered by `propertiesTable.ts`, **not** by `renderMyst` (which strips the frontmatter), so the frontmatter and whole-document E2 cases need that renderer too; and the "unmapped panel text, Mermaid SVG drawn by the page" cases cannot come from core HTML (Mermaid diagram text exists only after the page draws it): use the fence element as is.
- **T17 Tests that may need updating**: none of the BLOCK-166 or export tests should change; `test/core/protocol/hostToPage.test.ts` (224) and `test/page/hostMessages.test.ts` list the message types (check for an exhaustive list when adding the type).
