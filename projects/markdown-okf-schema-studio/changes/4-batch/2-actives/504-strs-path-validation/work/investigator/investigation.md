## 2. Tooling (what works here, Windows)

- The worktree has **no `.venv` and no `node_modules`**: run `just dev` first (AGENTS.md). The main checkout's `.venv` holds okf-schema 0.17.0 (stale, do not use).
- Scratch okfreq 0.18.1 without touching the lock: `uvx --python 3.12 --from "okf-schema==0.18.1" okfreq <cmd>` works. **Without `--python 3.12` it fails** (pyjson5 has no wheel on the newest Python and needs MSVC). `uv sync --group requirements` uses `.python-version` (3.12), so the project path is fine. `uv lock --dry-run --upgrade-package okf-schema` shows `okf-schema v0.17.0 -> v0.18.1` (the existing `>=0.17.0` already admits it; the pin is still needed).
- `okfreq --version` does not exist; `okfreq init <dir>` writes the bundle below `<dir>/.agents/requirements/` (config, guideline, 3 schemas) with **CRLF** line endings on Windows; the repo is LF (`.gitattributes eol=lf`): normalise when copying.
- The Studio schemas are hand-formatted (indented lists, folded descriptions) and differ from the `init` files in every line (diff after CR strip: base 289 lines, swrs 134, strs 70+). It is a merge of the 0.18 declarations, not a copy. Needed pieces seen in the init output: base `scenarios` (array, minItems 1, items `{id ^S[1-9][0-9]*$, title}`, additionalProperties false) and the `approved` lifecycle description text; strs `tested_in_files`, `accepted_in_files`, `acceptance_exemption`, `acceptance_exemption_reason` plus the `if/then` requiring the reason; swrs `accepted_in_files: {type: array, maxItems: 0, description: ...}`. The Studio `strs.schema.yaml` has `unevaluatedProperties: false`, so `scenarios:` fails validation until the base schema declares it (commit 1 must come first).
- `okfreq install-skills <dir>` installs `okfreq`, `okfreq-gardening`, `okfreq-setup`; both vendored skills differ from 0.18.1 (SKILL.md and `okfreq/references/operations.md`). `requirements.guidelines.md` differs from the init copy by 51 diff lines; `okfreq-baseline.guidelines.md` has its own header (compare with the init guideline, keep if not matching).

## 4. Risks

1. **File-size ratchet (hard blocker without a plan).** `scripts/file-size-baseline.json` has `files: {}`: a test file may not exceed 1500 lines and no exemption exists. Nine files with SwRS markers are at or near the limit and each marker line becomes N lines: `test/visual/scenarioDefinitions2.ts` 1500 (59 markers), `test/integration/previewEditing.test.ts` 1500 (25), `test/visual/capture_comment_checks.py` 1500 (2), `test/visual/capture_edit_checks.py` 1499 (7), `test/page/runtimeTableCellEditor.test.ts` 1499 (34), `test/page/modules/editActions.test.ts` 1498 (52), `test/core/preview/previewStyles.test.ts` 1479 (67), `test/visual/scenarioDefinitions1.ts` 1473 (48), `test/core/render/mystFeatures.test.ts` 1463 (43); 10 files exceed 1500 if every marker gains 2 lines. Those files must be split (a refactor, markers move with the code) before their sweep; a companion `*.markers.ts` file is the other existing mechanism (named lines `— scenario`, host in the same folder), but is meant for code that cannot carry markers. Decide in round 1 by listing the exact line budget per file after a dry-run count (the sweep script can compute the final line count).
2. **The sweep is semantic, not scriptable.** 3962 marker lines, 2611 scenarios; "read from the test, not guessed from the name". Only the mechanical parts can be scripted (the list of (marker, SwRS, declared scenario ids, test body), single-scenario SwRS: 3 SwRS; unmarked tests). Budget accordingly; this is the round that may need to be split.
3. **Per-commit invariants vs the spec's round layout.** Check-markers' new rule (fragment required on a declaring target) and the new-mode scratch validation both fail the moment a requirement gets `scenarios:` while its markers are fragmentless. So the migration script may not be committed for all groups in round 1; `scenarios:` + headings + sweep + StRS sort of one group must be one commit. In round 1 the script is written and proved on a scratch copy only.
4. W003 can only be 0 once all 95 StRS (including the three D6 ones) declare paths, so the "no W003" check is a head check; at intermediate commits only "0 errors" can hold.
5. Retired SwRS exemption (D5) changes the StRS `covered` status (old mode) of 46 live StRS; record before/after counts (23 covered now) in the log entry and evidence. Never touch the 97 files other than those two fields.
6. Text-level editing only: the frontmatter is folded/wrapped YAML; a dump/reload (yaml.dump) would reflow all 552 files. Insert/replace lines with exact text, keep LF, and verify with a post-check that parses each file and compares everything except the intended diff (scenarios block, renamed heading lines, `approved_at`, exemption fields). Quote titles via a YAML emitter for the 36 titles that need it.
7. Approved StRS: `approved_at` change also regenerates `verified.at` (generated field) on `just requirements-update`; do not hand-edit it; one timestamp for the 15, with the +01:00 offset form the repo uses. `approved_by` stays.
8. The spec's `okfreq` plain-output diagnostic gap (section 2) can hide the real error in CI-style runs; use `--json` in the scratch check.
9. check-markers ID extraction: `parseMarker` returns the id without `#S`, rule 2 stays distinct-ID based (fragments of one ID count once), the companion regex (`(\S+)(.*)$`) and the `requirementIds.has(marker[2])` check need the fragment stripped, and the baseline's `blocks` numbers will shrink when StRS markers are removed from the `test/integration` blocks (each shrink must be lowered with `--update` in the same commit or the check fails on a stale entry).
