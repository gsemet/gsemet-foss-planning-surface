## Open points

1. Spec gap, fixed here. Each part job begins its own campaign, so the report job holds one part's
   `campaign-visual.json`, while `review:finish` requires the run manifest's `campaignStartedAt` to
   equal its `startedAt`. The spec only looked at `e2e-campaign.mjs`. `_align_campaign` in
   `merge_parts.py` sets the file's `startedAt` to the merged (earliest) start, only when the file's
   (runId, startedAt) is one of the parts' own. Unit-tested (4 cases) and seen on the real run above.
2. Not listed in the spec: `requirements/config.yml` gets `test/visual` in the `source_dirs` of
   rendering-core. Without it the generated `implemented_in_files` cannot list the `test/visual`
   files the spec asks for.
3. Checklist item 2 names a purge in `scripts/run-e2e.mjs`; that file has none. The purge of
   `SCREENSHOT_DIR/*.json` is in `capture.py`, so `*.part-*.md` was added there.
4. The worktree had no `.venv` and no `node_modules` at the start, so I ran `just dev` (exit 0, log
   `work/scratch/just-dev.log`).
5. Local edge, not covered by the spec: `begin visual` does not remove part manifests, so rerunning
   one part alone could merge it with an older other part of the same revision and run id.

## Judgements inside the spec

- `parts_problem` is checked on every `capture.py` run, not only with `--part`.
- Part manifests have `partial: true`. A part run first removes its own three report files, so an
  interrupted part leaves nothing for the merge. A part index links its own machine report.
- Merged `workerCount` is the maximum. "Different results" compares status, failures and capture
  file names, not measured values.
- Only a failed part and identical PNGs across parts write the merged files; other refusals write
  nothing. If some part files exist and one is missing, the merge refuses even when a full manifest
  is there.
- `test_visual_parts.py` adds cases beyond the spec's list (campaign file, parts check, `--part`
  usage, and `capture.main` for both parts with the browser replaced).
