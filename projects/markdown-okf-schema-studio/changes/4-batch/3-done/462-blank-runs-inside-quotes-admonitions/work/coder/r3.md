## Observations for the Inspector (no code change made)

- Spec row `>\t- x` says `>   More`; the real columns give `>` plus five spaces (the tab goes to column 4, the item content starts at column 6). The test asserts the five spaces (already noted in r2).
- Spec: a tab before a footnote label "is kept as is". The code (and the spec's own rule, "after at most three spaces") refuses a tab before `[^label]:`, since that line is a code block in Markdown. The tests assert the refusal and the three-space case.
- `    [^c]: f3` written inside footnote a (the spec's "[^c]: f3 between two paragraphs of one footnote" row): the written text matches the spec, but Markdown then reads it as a definition of its own: footnote a vanishes from the rendered footnotes, c holds f3 and "more" falls out as a top-level paragraph. The test asserts the written text and that actual render, as the spec's rendered-result rule has no better outcome for it. This is the spec's rule, not a defect of the code.
- The frontmatter reader knows LF and CR LF only: in a lone-CR text no frontmatter block exists, so the frontmatter exclusion checks run in LF and CR LF only.
- A GitHub alert in a lone-CR text renders as a plain `blockquote` (existing renderer limit): the alert row's render checks are skipped in lone CR; its written text is still asserted.
- `[^c]` must be referenced in the text to render as a footnote (the fixture strings reference it).
