## 2. Findings that shape the design

1. The "first render before the index is ready" concern is already solved structurally: the first paint uses `inspectLinks:false` (links `pending`, no "missing" state), and link resolution is a separate debounced enrichment that re-patches the table (`scheduleLinkEnrichment` -> `setState(...,true)` -> `patchPropertiesTable`) after revision/generation guards. Making the enrichment async only widens an already-asynchronous step. No wrong "missing" state can appear, and the re-render once ready already exists.
2. `analyzeFrontmatter` stays sync for `inspectLinks:false` (used in render, refresh, save validation, which must stay sync: `handleSave` returns a decision inside the message handler; the rendering call is inside a sync assembly). Only the `inspectLinks:true` variant must become async.
3. Symlink semantics: the old walk used `Dirent.isDirectory()` (a symlink to a directory is NOT descended) and accepted symlink entries named `*.md` as candidates (a dangling one then yields W15 "unavailable"). The port's `readDirectory` reports the target kind (a symlink to a directory = "directory", broken = "other"). A naive port would descend symlinked directories (cycles, escaping the root, different results). Preserve behaviour: call `isSymbolicLink` for directory entries before descending (skip), and treat a `.md`-named "other"/file entry as a candidate. Cost: one lstat per directory (not per file).
4. Windows vs the memory FS: the core still uses `node:path` (kept by the request). `path.resolve("/ws")` on Windows returns `C:\ws`, which `MemoryFileSystem` (POSIX normalise) cannot serve. The unit tests on `MemoryFileSystem` would fail on the Windows leg of `ci-static` unless handled (see risks).

## 3. Smallest change (proposed design)

Choice for the stem index: **async build on demand, cached, invalidated by the existing watcher events; no eager prebuild**. Reasons: the render path never waits (first paint has no link inspection), the cache + watcher machinery already exists, and the walk now yields the event loop (readDirectory awaits) so even a cold build no longer blocks the extension host. An optional cheap warm-up (fire-and-forget `getStemIndex` from `watchStemRoot`) can be added but is not needed and would walk workspaces that never use stem links; recommend not doing it (stated in the PR as the choice the request asks to say).

Concrete steps:
1. `stemIndex.ts`
   - Core-local narrow port interface (stat/readFile/readDirectory/isSymbolicLink/realpath), exported from a pure core types file (e.g. `fileLinkTypes.ts` or new `linkFiles.ts`).
   - `MarkdownStemIndex`: private constructor + `static async build(files, roots)`; `canonicalRoot` async (realpath, fallback to `path.resolve`); `visit` async over `readDirectory` with the symlink handling of finding 3 and the same exclusion rules; `lookup(files, stem)` async (realpath + stat, same `escaped`/`unavailable` flags). `stems()`, `nearestStems()`, `get`/`pathsForStem` sync or async accordingly (`get` calls lookup, so async). `nearestStems` uses `canonicalRoot(directory)`: needs the canonical directory passed in or an async variant.

Share the in-flight promise between concurrent callers (several previews). `invalidateStemIndex` bumps a generation so a build started before an invalidation is not stored as fresh; also drop on rejection. Keep the signature of `invalidateStemIndex` (sync, used by `hostEvents`).

3. `okfFrontmatter.ts` (558 lines, close to the ratchet: check `scripts/file-size-baseline.json`, which has no entry for these files per grep, so the default cap applies; verify with `just check`)

This keeps all 40+ sync `inspectLinks:false` call sites and tests untouched.

Add a rejection guard (catch, log, leave table pending) so an unhandled rejection cannot leave the timer chain broken.

## 4. Risks
- Timing: link enrichment now yields between steps; a document edit during the build is covered by the existing revision guards, but the stale-write case "invalidate during in-flight build" needs the generation counter (race: an old walk finishing after a create event would cache a stale index; test it).
- Concurrency: many previews call `getCachedMarkdownStemIndex` concurrently on open; they must share one in-flight build (otherwise N walks in parallel).
- Perf: async walk = one `readDirectory` await per directory plus `isSymbolicLink` per directory (extra lstat); per-candidate `realpath`/`stat` in lookup stays per-lookup as today. Compare cold-build time on the repo itself before/after.
- Behaviour drift: symlink handling (finding 3); `.git` as a file in worktrees; case of paths on Windows (`realpath` JS impl, as used today); `unavailable` -> single rebuild retry; `escaped` detection; `isExcludedDirectory` rules unchanged.
- Windows test portability (finding 4): the memory FS is POSIX, core paths are platform paths. Proposed handling: a small test adapter that maps `C:\x\y` <-> `/x/y` around `MemoryFileSystem`, or build roots through `path.resolve("/ws")` and an adapter that normalises. Without it the Windows `ci-static` leg fails.
- Every sync test of `inspectFrontmatterLinks`, `resolveFrontmatterLinkRoots`, `MarkdownStemIndex`, `getCachedMarkdownStemIndex` must be rewritten async (about 10 files); `eventFanOut.test.ts` asserts cache identity (`assert.equal(getCachedMarkdownStemIndex(...), before)`): becomes awaiting a promise; identity of the index object must still be preserved when no invalidation happened.
- Value-derived search: no size/constant measured by other code changes (debounce 150 ms/300 ms untouched).
- File-size ratchet: `fileLinks.ts` 400 and `okfFrontmatter.ts` 558 lines; async plumbing adds lines; the split (prepare/finish) may push `okfFrontmatter.ts` over its limit: check `scripts/check-file-sizes.mjs` caps before and extract `linkRoots` (the root resolution functions) into a new file if needed (move the markers with the code).
