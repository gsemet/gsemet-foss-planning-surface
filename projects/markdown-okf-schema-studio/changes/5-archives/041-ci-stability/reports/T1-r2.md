## Root cause per flake

### 1. scenarioFlushFrontmatterKeptAsTyped case 2: PROVED (code + logs), mechanism in VS Code

What the logs prove: the editor was open (`waitForEditor` passed), then gone right after
Control+A, with no page load, no content patch, edit mode still on, no editor at all. In the page
only these paths remove the frontmatter editor (all `closeFrontmatterEditor` callers, traced):
content patch (0), page load (0), edit mode off (still on), Escape (not pressed), properties table
(deferred while editing, never removes it), and **blur of the control with an unchanged value**
(`saveValue` -> `unchanged` -> close). Nothing was typed yet, so the value was unchanged. Only the
blur path fits.

Why Control+A blurs it (read in VS Code 1.143 `out/vs/workbench/contrib/webview/browser/pre/index.html`
and `workbench.desktop.main.js`):

- The webview forwards every keydown to the workbench (`handleInnerKeydown` -> `did-keydown`;
  Ctrl+A is not prevented).
- `editor.action.selectAll` is a MultiCommand: `code-editor` (needs text focus), `generic-dom-input-textarea`
  (workbench active element must be an input; it is the webview iframe), `webview` (priority 100:
  `activeWebview?.isFocused`), and the default `generic-dom` (priority 0):
  `getActiveCodeEditor().focus()` then select all.
- The webview's `isFocused` comes only from `did-focus`/`did-blur` messages, and the page reports
  them from a **250 ms `setInterval` poll** (`trackFocus`, `interval = 250`).
- So Ctrl+A within 250 ms of focusing the webview after the focus was elsewhere runs the fallback:
  the source text editor takes the focus, the textarea blurs, the unchanged editor closes.

Why case 2 and never case 1 (inferred, consistent with the code): case 1 runs after the preview was
just opened and its webview was last reported focused (stale `isFocused = true`), and it also clicks
the edit toggle first. Case 2 runs after a tab switch away and back (the poll has reported
`did-blur`), skips the edit toggle (edit mode already on), and presses Control+A a few ms after the
click. The same mechanism explains CI run 39831790532 (case 3, number input, after Ctrl+A; the old
comment blamed the number input) and the 300 ms "wait for the selectAll echo" sleeps of RI-T06 and
RI-T07. The r1 theory (deferred host work) is refuted by `content patches 0`.

This is a **product bug**: a user who clicks a preview text box and presses Ctrl/Cmd+A at once
gets the source document selected and loses the frontmatter editor.

## Fixes

- **Product: Cmd/Ctrl+A stays in the text control** (`src/webview/selectAllKey.ts`, injected in
  `scrollSync.ts`). A document-level keydown listener stops the propagation of the platform
  select-all when the target is a textarea, a text-like input or an editable element, so VS Code's
  window listener never forwards it; the default action (the browser's own select-all) is not
  prevented. Outside text controls, and for every other key (undo, copy, paste), nothing changes.
  No dependency on the workbench's 250 ms focus poll remains for this key.
- **Test waits on reported state** (`test/integration/realInput.test.ts`):
  - `waitForPageSettled(page, label, document)` replaces r1's `waitForPageReady`: host phase ready
    AND render version = buffer version AND `webviewReady` (page echoed this render's request id)
    AND no deferred timer armed AND the page shows the host's last properties table (new
    `propertiesTableAwaited` seq on the host, echoed by the page on `<html data-okf-properties-seq>`).
  - `waitForTextInput(page, selector)`: the control is the page's `activeElement` and the page has
    focus, before any key press.
  - `selectAllInControl(page, selector)`: waits for the caret, presses Mod+A, waits until the whole
    value is selected, fails at once with diagnostics if the control is gone. Replaces three 300 ms
    sleeps (RI-T06, RI-T07, case 1/2).
  - StRS-A: one `boundingBox()` read after `waitForPageSettled`; r1's box poll removed.
  - Table Tab: `waitForPageSettled` + `waitForTextInput` on the new row's cell; r1's extra editor
    poll removed.
  - Flush cell/frontmatter: `waitForPageSettled` + `waitForTextInput` for both editors.
- **Host** (`src/extension.ts`): `propertiesTableSeq` / `propertiesTableAwaited` (set on a
  properties post, cleared by a page load or a content patch, which carry the latest table), and
  `propertiesTableAwaited`, `panelActive` in the test snapshot. r1's `deferredWorkPending` kept.

### Why each wait is deterministic

Every condition is a state the host or the page reports for the current render: request-id echo,
buffer version, armed timers, the seq of the last applied table, the focused element. No delay, no
retry around an action, no raised timeout (the default 10 s `waitFor` bound is unchanged). Once all
hold, no host code path can replace the page content without a new trigger (a new buffer version,
which the test does not cause before typing).
