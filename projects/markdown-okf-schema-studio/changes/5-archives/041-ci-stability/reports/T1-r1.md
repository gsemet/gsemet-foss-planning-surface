## Files changed

- `.github/workflows/ci.yml`: `timeout-minutes` on every job (integration 30, report 10, static/visual/gallery/checks/tag-release 15). `release` and `pages` are reusable-workflow calls (`uses:`), where job-level `timeout-minutes` is not allowed; their workflows are untouched.
- `.agents/guidelines/ci.guidelines.md`: rule 11 (every job has a timeout; never raise one to pass).
- `justfile` (`dev-ci`): apt gets `Acquire::Retries=5`, HTTP(S) timeout 30 s, IPv4 only, so a stalled mirror connection fails and retries instead of waiting.
- `src/extension.ts`: test snapshot gets `deferredWorkPending` (true while a link-enrichment, frontmatter-refresh, content-patch-ack or pending-overlay timer is armed).
- `src/webview/firstClearance.ts`: after any change, the layout is re-measured on every animation frame until 60 frames in a row are unchanged (max 300), so a late toolbar layout always gets a final measurement.
- `test/integration/realInput.test.ts`: new `waitForPageReady` (page ready AND no deferred host work) used in `scenarioFlushCellAndFrontmatter` (both editors), `scenarioFlushFrontmatterKeptAsTyped` (replaces the inline wait), `scenarioListEditorClickAndKeys` (plus a poll until the link has a visible box), `scenarioTableTab` (before typing in the new row). Failure messages now also print content patches since the editor opened.
- `test/webview/firstClearance.test.ts`: one new test.

## Why the waits are deterministic

`webviewReady` is true only when the page echoed the request id of the staged render. `deferredWorkPending` is read from the same host object, so "ready and no timer armed" means nothing is left that could patch or reload this render; any later update has a new trigger. The link box is polled until it is non-null with a size, and read only from the ready page.
