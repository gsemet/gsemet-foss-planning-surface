# T1 round 3: no job depends on a live Ubuntu mirror download

## Evidence (run 39937862256, head 36bdf5f, image ubuntu-26.04 20261012.163.1)

- All jobs ran `apt-get install plantuml graphviz`, which needs 89.7 MB (openjdk-25-jre-headless
  59.2 MB, batik, bcprov, fop, plantuml 1:1.2020.2). Then `playwright install --with-deps chromium`
  ran a second apt install of 24.9 MB: fonts (ipafont-gothic, freefont, unifont, wqy-zenhei,
  tlwg) and upgrades of libnss3, libnss3-tools, xserver-common and xvfb. Both installs use
  `azure.archive.ubuntu.com`, so the Playwright install has the same risk.
- Fast runners: 89.7 MB in 1-6 s (8 logs), 24.9 MB in 1-2 s (8 logs). Slow runners: attempt 1
  static, visual and integration, and attempt 2 visual. The openjdk download alone took 10 min
  (static: 10:16:17 to 10:26:35). The Playwright step never ran on a slow runner, but nothing
  protects it.
- r1's `Acquire::Retries=5` with a 30 s timeout made this worse. In attempt 2, the visual job
  started `Get:4 openjdk-25-jre-headless [59.2 MB]` three times (10:47:52, 10:51:23, 10:58:30).
  The connection is slow, not stalled, and each retry fetched again.
- `apt-get update` (3 MB of indexes) was fast on every runner.

## Options and decision

- (a) Install the packages only in jobs that use them: yes. Static, integration, stress, report and
  gallery now run `just dev-ci` (npm ci and uv sync only) and touch neither apt nor the Playwright
  CDN. No test changes, so coverage stays the same.
- (a) alone does not fix visual, which is the job that failed in attempt 2.
- (b) Cache the .deb archives: chosen for the visual job. It is the only option that also covers
  the Playwright apt install. That install runs plain `sudo apt-get install` with the default
  archive folder, so `dev-ci visual` pre-seeds `/var/cache/apt/archives` from
  `.cache/apt-archives`. A cached package is never downloaded again.
- (c) PlantUML jar plus `setup-java`: rejected. The fonts would still come from apt, so we would
  need two mechanisms instead of one.
- Cache keys use `actions/cache/restore` and `actions/cache/save`. The restore key is the prefix
  `apt-archives-visual-<os>-<arch>-` (newest wins). The save key adds the `hashFiles` of the
  archives, so a save happens only when the package set changes. The save step is skipped when it
  would write the key it restored.
- `apt-get autoclean` drops outdated versions before the copy-back, so the cache does not grow.
- On a cache hit, only `apt-get update` (fast) reaches the mirror. When a package version changes,
  only that package is fetched.
- Dropped `Acquire::Retries` (rule 9, and the evidence above shows the harm). Kept the 30 s
  `Timeout` and `ForceIPv4` from r1: a stalled connection fails fast and names the package.

## Open points

- First run: the PR has no cache yet, so the visual job's first run still downloads about 115 MB
  from the mirror, once. Main's first run after the merge also downloads once, because PR caches
  are scoped to the PR. A slow runner at that moment can still time out. After that, every run
  restores the cache. Check the "restored/saved" lines in the next visual log.
- Not verifiable offline: whether the runner image keeps downloaded .debs in
  `/var/cache/apt/archives`. apt-get keeps them by default. If the next log says "0 package
  archive(s) saved", add `-o APT::Keep-Downloaded-Packages=true` to an apt.conf.d file in
  `dev-ci visual`.
- If the cache key already exists from a parallel run, `actions/cache/save` logs a warning; it
  does not fail the job.
- Non-visual jobs no longer get upgraded libnss3 and xvfb or the extra fonts. VS Code uses the
  image's versions, which are present. The integration fixtures have no CJK text.
