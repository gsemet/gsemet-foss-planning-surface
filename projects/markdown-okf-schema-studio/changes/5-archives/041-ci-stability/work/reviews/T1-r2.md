## Root cause of case 2 (verified against VS Code 1.143 shipped source)

- `pre/index.html` adds `handleInnerKeydown` with `contentWindow.addEventListener('keydown', ...)`
  in the window **bubble** phase. It does not prevent Ctrl+A and forwards it as `did-keydown`.
  Calling `stopPropagation()` on a document bubble listener in the page therefore does stop the
  forwarding.
- `trackFocus` polls `document.hasFocus()` every 250 ms (`interval = 250`), as the report says.
- The `editor.action.selectAll` implementations in `workbench.desktop.main.js` are `code-editor`
  (1e4, needs text focus), `generic-dom-input-textarea` (1e3) and `generic-dom` (0). The last one
  runs `getActiveCodeEditor()`, then `i.focus()`, then select-all. That fallback moves the focus to
  the source editor.
- One more point supports the theory. The fallback can steal the focus only when a code editor is
  the active editor. That is the case right after `showTextDocument(first, ViewColumn.One)` (the
  tab switch of case 2), until the poll reports the webview focused and its group becomes active.
  Case 1 runs while the preview is already active. The theory also explains `page loads 0,
  content patches 0`, edit mode still on, and an unchanged value closed on blur. It is plausible
  and is the only close path left over.
- The fix is a product fix and has no harmful side effects. The listener is installed first and
  calls `stopPropagation` (not `stopImmediatePropagation`), so other document listeners still run.
  No page code listens to keydown on the window. The default action is kept, so the browser selects
  the text, which is what the old `webview` implementation's echo did too. The page skips the
  shortcut when Shift or Alt is held, or when Ctrl and Meta are both held. macOS uses Cmd only and
  Linux/Windows use Ctrl only, through `isApplePlatform()`. Checkbox and other non-text inputs and
  the page body still forward the key. The find widget lives in the workbench and is not affected.
  Keyup is still forwarded, which does no harm.
- Tests that fail on the old code: in `scrollSync.test.ts`, "Cmd/Ctrl+A ... stops at the document"
  (`stopped` would be 0 and `__studioDiagnostics` would be missing) and the trace and seq tests.
  The `selectAllKey.test.ts` unit tests cover the predicate.

   `document.hasFocus()` in the webview frame. Nothing has checked this under Xvfb with
   `connectOverCDP`: Playwright enables focus emulation on the main frame only, and the webview
   may be an out-of-process frame. If it is false there, every run fails the same way (it would
   not flake), and the message shows `pageFocus=false`. If the first CI run shows that, drop the
   `hasFocus()` term and keep `activeElement === control`.

   call it before they open an editor. A comment on that precondition would help.
