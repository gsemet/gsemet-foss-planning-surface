# T1 round 6 - CR 123 (tall block rework)

## Reproduction (real VS Code window, macOS, cream preview)

The new e2e `test/integration/tallBlockScroll.test.ts` ran on three trees: main (4ee26ba), the unchanged branch (469f9af), and the fixed branch.

**Bug 1, toolbar too low.** I reproduced it on the branch and on main.

- The tall code block was opened while its top was 150 px above the pane.
- The window width was 2320 px, chosen so that the preview controls overlap only the empty right end of the two-row bar, as in the user's image.
- The bar stuck at 126 px, under the preview controls (`--sphinx-preview-toolbar-bottom`), over the middle of the block.
- The top of the pane is at 34.6 px (sticky band bottom + 4).
- Cause, on main too: the sticky line in `src/core/preview/styles/editPaletteStyles.ts`. It is `max(reading-offset, toolbar-bottom) + 4` (`.sphinx-preview-block-editor-host > .sphinx-preview-edit-palette`). It uses the controls' full box even when none of the bar's buttons is under them.
- The branch made it worse: `tallBlockClearance` (editorChrome.ts:182, 197-212 at 469f9af) scrolled the page up on opening, by the sticky line minus the band bottom + 6 px plus the bar height. Lines 01-04 came into view above the stuck bar, and the bar sat over lines 05-07, as in the user's image.

**Bug 2, scroll jumps to the top.** It is a branch regression and does not happen on main.

| Tree | Scroll after a 90-paragraph paste in the Start writing editor of an empty document |
| --- | --- |
| main | `scrollY` 4305: the page follows the caret to the end of the paste |
| unchanged branch | `scrollY` 0-53: the page stays at the top, with the caret about 4,900 px below the viewport |

- Mechanism: `reservePaletteClearance` (editorChrome.ts:224-247 at 469f9af, plus the `margin-top: var(--sphinx-preview-palette-reserve)` rule in contentLayoutStyles.ts:338-342) adds a 4 px reserve. It pushes the frame top (263) below the bar bottom (260).
- `caretRevealDelta` (src/page/modules/caretRect.ts) returns 0 whenever `bar.bottom <= frame.top`, including for a caret below the viewport. So `revealCaretBelowPalette` never scrolls after the paste. Main worked only because the bar overlapped the frame by 1 px.
- Then the host re-renders the pasted text. The content patch closes the editor, and `restoreState` scrolls back to where the page was. That is `scrollTo(0)` on the branch (traced: restoreState ← applyContentPatch) and `scrollTo(4252)` on main.
- So a user who scrolls down after the paste is thrown back to the top when the re-render arrives.
- Wheel scrolling alone never moved the page up in any run, on any tree.

## Fix

- `src/page/features/editorChrome.ts`
  - Removed `tallBlockClearance`.
  - A frame taller than the viewport (`isTallFrame`) whose host is above the usable top keeps the clicked text in place on opening (shift = bar height). The bar sticks over the first lines.
  - Tall frames get no reserve.
  - New `syncTallPaletteTop`: for a tall frame whose bar buttons do not share columns with the preview controls, the host gets `data-sphinx-palette-top` and `--sphinx-preview-palette-top` set to the visible band bottom. It is cached by pane, bar, band and tall state. Scroll padding follows that line.
  - `toolbarUsableTop`'s reading top is split out as `readingAreaTop`.
- `src/core/preview/styles/editPaletteStyles.ts`: a rule (min-height 521 px, not static) sticks that bar at `var(--sphinx-preview-palette-top) + 4px`.
- `src/page/features/scrollCore.ts`: `postScroll` calls `syncPaletteSticky` again after the sticky band updates, so the line follows the band.
- `src/page/features/pageRuntime.ts`: `paletteTopKey` field.
- `src/page/modules/caretRect.ts`: a caret below the viewport is revealed whether the bar is stuck or not. The "caret under the bar" branch still requires a stuck bar.
- Blocks that fit the viewport are unchanged: reserve, keep-text-in-place, the line under the controls. The `editToolbarCover` measurements are identical.
