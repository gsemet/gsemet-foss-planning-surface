# T1, round 1: table toolbar vs five-row floating toolbar

Worktree: markdown-okf-schema-studio-wt-167 (uncommitted).

## Root cause

Order of two clearance mechanisms in `renderTableCellEditor` (src/page/features/tableCellEditor.ts):

1. `rt.scroll.applyAnchor()` -> `revealTableToolbar` scrolled the page up by the distance that brings
   the first bar item sharing columns with the floating controls below them (min(wanted, scrollY)).
2. Only afterwards `clearPreviewControls(menu)` ran, deciding whether the bar wraps left of the
   controls (inset) when the page "cannot scroll the bar below them".

Geometry from the log: before the reveal scrollY 137 and bar top 37; controls bottom 178 + 4 = 182, so
missing (box) = 145 > 137: the inset applies (SwRS TABLE-064: page scrolled less than the missing
distance). But the reveal had already scrolled 105 px (137 -> 32, menuTop 142). With the inset the
buttons wrap left of the controls, so that scroll was useless: the cell moved 105 px, and the test's
"revealed" acceptance could not match either (no item overlaps the controls any more, firstTop
undefined; not pageTooShort; menuTop 142 is not the reading line 81.8). The five-row toolbar (bottom
178) made the window where both fire large enough to show.

Decision: product fix, not a test change. The requirement promises the inset for this situation and
that the page is revealed only when needed; the selected cell must move only by a reveal that clears
the controls. The assertion is unchanged.

## Fix

`clearPreviewControls(menu)` now runs before `rt.scroll.applyAnchor()` (and no longer after the field
is filled), so the inset is decided from the page as it is when the bar appears; the reveal then sees
a bar already clear of the controls and only brings it below the reading line (accepted by the
existing belowBand case).
