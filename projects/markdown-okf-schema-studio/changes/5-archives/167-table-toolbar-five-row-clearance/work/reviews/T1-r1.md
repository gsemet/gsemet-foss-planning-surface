## 1. Root cause and geometry

- Root cause confirmed. In `renderTableCellEditor` (src/page/features/tableCellEditor.ts:425-426, was
  :426 + :431 before), `rt.scroll.applyAnchor()` -> `revealTableToolbar` (src/page/features/editorChrome.ts:74)
  measured the bar without the inset. Its status/buttons shared columns with the controls, so
  `toolbarUsableTop` asked for `controlsBottom + 4 - offset` and the page scrolled by
  min(wanted, scrollY) = 105 px. The inset was only set after that, which made the scroll pointless:
  in the final state no item overlaps the controls (`firstTop` absent from the log JSON), so neither
  `revealed` nor `pageTooShort` (scrollY 32 != maxScroll 360) nor `belowBand` (menuTop 142 vs reading
  line 81.8) could match.
- Log numbers check out: bar top before the reveal = 142 - 105 = 37, scrollY = 32 + 105 = 137. The bar's
  page top is 37 + 137 = 174 < controlsBottom + 4 = 182, so the page can never clear the bar: the
  inset case of TABLE-064 applies.
- The reorder is safe for the inset decision. `clearPreviewControls`
  (src/page/features/tableCellEditor.ts:163) tests `missing > scrollY`, i.e. bar page top <
  controlsBottom + 4, which does not depend on the scroll. So measuring before the anchor restore (on
  the first render the anchor scroll that compensates the filled menu has not run yet) gives the same
  answer. The only check that depends on the scroll is `bar.top >= controls.bottom`. Before the anchor
  restore the bar sits lower on screen, so the inset could be skipped only when the pre-anchor scrollY
  is under 4 px. That cannot happen on a first render: the empty-menu anchor at :259 already scrolled
  by the menu's chrome. In the real scenario bar.top_pre <= 174 < 178, so the inset is set.
- Expected real-window result. With the inset, `max-width: calc(100% - inset)`
  (src/core/preview/styles/editModeStyles.ts:361) ends the bar box 4 px left of the controls.
  `toolbarUsableTop` is then the reading-area top (81.8), and the reveal scrolls 81.8 - 37 = 44.8 px.
  So the cell moves about 45 px (not 0), menuTop lands at the reading line, and moved (45) <=
  menuHeight + 1 (119). That matches the existing `belowBand` acceptance
  (test/integration/realInput/editorWidgets.ts:758-760) without changing it.
  Residual risk (non-blocking, heavy CI decides): if the sticky heading band shows at scrollY ~92 with
  a bottom more than 2 px past the reading offset, the test's readingLine and the product's
  `readingAreaTop` could disagree. Both take the band bottom when it is visible, so they should agree.
