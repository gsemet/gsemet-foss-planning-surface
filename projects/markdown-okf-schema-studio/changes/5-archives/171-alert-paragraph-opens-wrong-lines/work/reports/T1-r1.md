# T1, round 1: alert paragraph opens the editor on the wrong lines

Worktree: `/Users/az02065/Projects/DevTools/markdown-okf-schema-studio-wt-171`, branch
`change-requests/171-alert-paragraph-opens-wrong-lines`. Nothing was committed, pushed or stashed.

## Cause

It is lead 2, the alert line mapping. Lead 1 (a stale map after an outside edit) is not the cause:
the README snapshot alone, rendered fresh, gives the paragraph of the second alert lines 42-43.

`expandGithubAlerts` rewrites an alert into `:::{note}` + `:class: simple` + body + `:::`. That is
one line more than the source when a blank line follows the alert (the closing fence takes the
blank line's place), and three lines more when an unquoted line follows it. Nothing mapped the
lines back, so:

- each block inside an alert came out 1 line late;
- each block after an alert came out 1 line later per alert above it (3 when no blank line
  followed the alert);
- each alert's `data-end-line` overshot its last line.

**Data loss: yes.** The host trusts the page's line numbers:

- Clicking the paragraph of the second alert opened lines 42-43 (the blank line and
  `### Edit MyST visually`). Done would have overwritten those lines.
- Cut, copy and move of a block after an alert would act on the wrong lines with no editor shown
  first, so the user gets no visual warning.

This supports escalating to 1.0.0.

## Fix

The fix uses a line map and does not change the rewrite itself, so the HTML stays the same.

- `src/core/render/mystGithubAlerts.ts`:
  - `expandGithubAlertsWithLines(text)` returns the rewritten text and `sourceLines`, the input line
    each output line comes from (`undefined` when no alert was rewritten).
  - The opening line and `:class:` map to the marker line. The closing fence (and the blank line
    added before an unquoted line) map to the alert's last quoted line, so an admonition ends on
    its own last line.
  - `alertLineMapper(expanded, firstLine)` gives the line function. `mapAlertSourceLines(root,
    expanded, firstLine)` remaps every node's start and end lines, plus the
    `data-line` / `data-end-line` hProperties the grid pass has already written.
  - `expandGithubAlerts(text)` stays as a wrapper.
- `src/core/render/mystRenderer.ts`:
  - New tree pass "alert source lines" right after "context tags".
  - The passes before it (shift, unclosed fences, grids, context tags) read `parsedText` line for
    line and stay in parsed numbering.
  - Every pass after it works in document lines: the MyST extension check, includes, directive
    errors (`state.source` lines), comment markers and the HTML writer.
  - `RenderState.alerts` holds the map.
- `src/core/render/mystUnclosedFences.ts`: an optional `sourceLine` mapper. The unclosed-fence
  warning line and the raw opening line shown as code now use the document's line. Before, after an
  alert, they showed the wrong line's text.
- `src/core/render/mystContextTags.ts`: the slice re-parse uses the mapped variant before
  `offsetNodeLines`, so a raw alert in a grouped context-tag HTML block maps correctly.
- Other paths, unchanged:
  - Checkbox markers are counted on the text before the alert rewrite, so their lines were already
    correct.
  - The includes call (`expandGithubAlerts` on the included source) needs nothing, because
    `setIncludedSourceLine` overwrites every included position with the `{include}` lines.
  - Tab ids (`myst-tab-<line>-<n>`) are still built from the parsed line during the grid pass, so
    the HTML ids do not change.

## Defense in depth (assessment only, not implemented)

The question: can the host refuse an edit, cut or move when the block at those lines is not the
block the page rendered?

- **A source hash or first-line text computed at render does not help.** The renderer would hash
  the same wrong lines the host later reads, so the check would pass. It only catches staleness,
  which the revision and requestId checks already refuse.
- **Option A, text-sample guard (independent of the line map).**
  - The page sends a short sample of the rendered block's text with the line range. The host
    strips Markdown from its source lines and refuses when the sample's first and last words are
    missing.
  - Files:
    - `src/core/protocol/pageToHostMessages.ts` and `pageToHost.ts`: optional `blockText` on
      `previewEditOpen`, `previewBlockMove` (both ranges), `previewBlocksCopy` and
      `previewBlocksCut`.
    - `src/page/features/blockEditor.ts`, plus the move and selection senders in `src/page/`.
    - `src/session/features/blockEdits.ts` (`handleEditOpen`) and
      `src/session/features/sourceEdits.ts` (`handleBlockMove`, `handleBlocksCopyCut`).
    - A pure matcher in `src/core/edits/`.
  - Size: about 200-300 lines with tests, plus BLOCK SwRS updates for the message fields (the
    BLOCK-240/241/242 validators).
  - Risks: false refusals that would make blocks uneditable. Rendered text often differs from the
    source: KaTeX math, roles and substitutions, default admonition titles ("Note"), images,
    diagrams, tables, smart quotes, footnote numbers, included blocks. It needs a skip list (no
    sample means no check), so its coverage is partial, and it adds a field and a check to every
    block message.
- **Option B, render-side sanity check (cheap).**
  - At the end of the tree passes, drop `data-line` / `data-end-line` from a block whose start line
    is blank in `state.source`, or whose range is past the end of the file. The block then just
    cannot be edited, which fails safe.
  - Size: about 20-30 lines in `mystRenderer.ts` and `mystNode.ts`, plus tests.
  - It would have stopped this exact click (line 42 is blank) and the past-EOF list item (228), but
    not a shifted block that lands on a text line (the h3 at 45).
  - Risk: it can hide a real mapping bug instead of surfacing it, so it should log a diagnostic.
- Recommendation: B is cheap enough to add as a fail-safe in a follow-up. A only if data-loss
  reports recur.

## Open points

1. **An alert inside a 3-colon container is broken (pre-existing render bug, not fixed here).** The
   alert's closing `:::` closes a surrounding `:::{card}`, `:::{grid-item-card}` or
   `:::{tab-item}`, and a stray `:::` shows as code. The README had such a `::: {card}` wrapper
   before the user's edit. The tests use 4/5-colon containers. Worth a backlog item; one fix is to
   emit a longer fence (`::::`) for alerts.
2. Alerts inside a backtick-fenced directive (```` ```{note} ````) are not rewritten, because
   `advanceFence` treats them as code. Pre-existing.
3. Nested alerts (`> > [!TIP]` inside an alert) are not supported: the inner one stays a quote. The
   test pins its lines only.
4. The Sphinx build path (`src/node-services/build/sourceTransforms.ts`, its own
   `expandGithubAlerts`, no `:class:` line) keeps lines only when a blank line follows the alert:
   +1 per alert followed directly by text. Untouched; out of this CR unless that build feeds block
   lines to the editor.
5. A list item ending with an alert ends on the alert's last quoted line. markdown-it would also
   count the trailing blank line, so the range is one line shorter, which is harmless.
6. BLOCK-014 says a body click on an admonition opens the whole directive. For a GitHub alert the
   page opened the paragraph only (user screenshot, and this test). Worth checking that this is
   intended for `simple` alerts.
7. Lead 1 (outside edit changing the line count) was not reproduced as a cause, so I added no test
   for it.
