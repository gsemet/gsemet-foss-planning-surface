## Defense in depth: option B in this PR? No

- **The cause is already fixed and pinned.** The README test checks every heading and paragraph
  of a whole document against its source line, so option B would add no protection against this
  regression.
- **It is not a complete guard.** The coder notes it would not catch a shifted block that lands on
  a text line (the h3 at 45), so it cannot replace the line map.
- **It is not as local as it looks.**
  - `data-line` also drives scroll sync and comment anchors, not only editing. Dropping it in the
    renderer changes the output for every document.
  - Synthetic or wrapper nodes (grids, context tag groups, toc markers, comment markers) could
    start on a blank line. Each such case would quietly become uneditable and unsynced.
  - Proving that safe needs the full unit and visual suites, plus a new SwRS behaviour. That
    delays a P1 hotfix for a fail-safe that does not cover the bug class.
- **A better follow-up (backlog, P2) is a host-side check.**
  - In `handleEditOpen`, `handleBlockMove` and `handleBlocksCopyCut`, refuse a range that is past
    the end of the document or whose first line is blank, with a diagnostic.
  - It is about the same size, does not affect scroll sync or the HTML, and protects every caller
    of the line map, including future ones.
  - File it as its own CR with its own SwRS.
