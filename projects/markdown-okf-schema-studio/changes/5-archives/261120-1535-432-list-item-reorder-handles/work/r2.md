# CR-432 round 2: the held drag in the v40/v41 PNGs

## Cause

The `drag` check did hold the drag, and its marks were there (the check passed in CI), but it took
the held state only as a step PNG (`-drag.png`), then released the button. The release posts the
save; the visual page gets no render back, so the list on the page did not change. The scenario's
own PNG, taken at the end of the run, was then the page of v36/v37 with the button up: byte-identical.
The table scenarios (`table-editing/v09..` row-dragging) avoid this with a `pageActions` drag with
`hold: true`, never released, so the scenario PNG is the held drag; `check_table_move` releases and
sends the host's render back (`previewContentPatch`).

## Change (test/visual only, not committed)

- `capture_list_item_handles.py`: `drag` mode now (1) drags the first bullet over the third and
  checks the marks, (2) releases: one save, order second/third/first, no editor, (3) sends the
  host's render of that order (`PATCH`, like `capture_table_move.py`; the page refuses a drag until
  a render arrives, `settleTimer` in `listItemMove.ts`), checks the rendered order, (4) drags the new
  first item over the third and keeps the button down for the capture. New
  `check_list_item_drag_held`: at capture, item 0 has `data-okf-list-item-dragging="true"` and item 2
  `data-okf-list-item-drop="after"`. The `drag` step PNG is gone (it was what the final PNG now is).
- `capture.py`: runs `check_list_item_drag_held` right after `check_final_frame`, before the screenshot.
- `capture_final_checks.py`: `check_tooltip_contrast` skips `drag` scenarios (its hover would move the
  held pointer), as it does for held `pageActions`.
- `capture_support.py`: `drag` removed from `STEP_NAMES`; `scenarioIds.ts`: the two `STEPS_BY_ID`
  entries removed, the v40/v41 locks reworded; `listItemHandleScenarios.ts`: descriptions reworded.
