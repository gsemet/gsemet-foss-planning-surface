## What

The stylesheet does all the motion, through attributes. Nothing sets an inline `style=`.

1. **Editors, bars and menus appear softly.** This uses CSS `transition` plus `@starting-style`, opacity only. Menus also move with the `translate` property by 3 px. The rule covers:
   - the block editor frame, the table-cell editor and the frontmatter editor: 160 ms, from opacity 0.35;
   - the edition palette, the table bar and the frontmatter menu: 120 ms;
   - the palette popovers, the `/` menu and the frontmatter picker: 120 ms.

   Every enter rule is gated by `html[data-sphinx-preview-motion="on"]`. The first `pointerdown` or `keydown` sets it, and a content patch takes it back. So a page that loads, a restored editor and a page that follows scroll sync never animate. Because these are transitions, removing the gate cannot restart them later.

   Closing an editor makes the block it gives back fade in (`data-sphinx-preview-edit-closed`, keyframes, 160 ms). This happens only after a user action.
2. **Theme switch.** The toolbar theme button sets `data-sphinx-preview-theme-switching`. While it is set, background, colour, border, outline, fill and stroke transition over 200 ms. The attribute is removed on the body's `background-color` `transitionend`, with a 400 ms fallback in the runtime.
3. **Update glow.** A brief wash of the focus colour, 24 % `color-mix`, as background plus box-shadow, using a single `from` keyframe. The block's own background comes back as the glow fades.
   - **Host** (`src/extension.ts`):
     - The 7 preview-originated `workspace.applyEdit` and 5 `TextEditor.edit` calls now go through `applyPreviewEdit` / `editInPreview`. Both track the edits in flight for each document.
     - `onDidChangeTextDocument` records `outsideChangeVersion` when a change is outside the preview (`isOutsideChange`). That is an Undo or Redo reason, or no preview edit in flight.
     - `postContentPatch` adds `updatedRanges` when the patch moves across that version. The ranges are `changedLineRanges(previous, next)`; there are none above 50 ranges.
   - **Page** (`src/webview/motion.ts`): marks the innermost `[data-line]` blocks that meet a range with `data-sphinx-preview-updated`.
     - A code block is marked on its `<pre>`.
     - Included blocks and open editors are skipped.
     - Nothing is marked above 40 blocks, or with reduced motion.
     - The mark is removed on `animationend` / `animationcancel`.
4. **`prefers-reduced-motion: reduce`.** A block at the end of the Motion section sets `animation: none !important; transition: none !important` for every motion selector. The runtime also marks nothing in that mode.

   I also changed the existing page-wide rule from `transition-duration: 0.01ms` to `0s`. With the default `transition-property: all`, the tiny duration still started a transition on every style change, so a theme switch was read mid-transition. Nothing in `src` depended on `transitionend`.
5. **Docs.**

## Autonomous decisions

- **Glow duration is 600 ms.** The other effects are 120–200 ms; a 200 ms glow cannot be seen as "this changed".
- **Own edits versus outside changes are told apart on the host.** Edits are tracked while in flight, because VS Code reports the change event before the edit promise settles. Undo and Redo always glow. A patch of more than 50 ranges, or a page change of more than 40 blocks, never glows (a checkout, a reload).
- **Soft appearance waits for a user action and is held after a content patch.** This makes "no animation on initial render or patch-restored editors" structural rather than timing-based.
- **No exit animation for removed editors or menus.** Keeping a removed element alive for an exit animation would delay synchronous closes that the tests and runtime rely on. Instead, the block an editor gives back fades in.
- **The page-wide reduced-motion rule uses `0s` instead of `0.01ms`.** The reason is in point 4 of "What".

## Open points

- **The own-edit classification is not tested in a real window.** It relies on VS Code ordering: the document-change event comes before `applyEdit` or `TextEditor.edit` resolves. If that ever failed, the result would only be cosmetic: an own edit would glow. An integration test could cover it with two more lines in the `getActivePreviewForTests` snapshot: an outside `WorkspaceEdit` and an `undo` should carry `updatedRanges`, and a preview save should not. I did not run the real-window suite because it would hold the shared lock for a long run.
- **The theme transition applies to `body *`** (about 485 transitions on the test page) for 200 ms. That is fine for normal documents; very large documents were not profiled.
- **Soft appearance has no visual scenario.** I verified it manually in Chromium with a scratch Playwright probe:
