## What

1. **Typing in the active text editor no longer glows.** I used the driver's rule. I found no cleaner signal: VS Code does not say where a change comes from, and `TextDocumentChangeReason` only marks Undo and Redo.
   - `isOutsideChange(reason, previewEditing, inActiveEditor)` in `src/preview/updatedRanges.ts` returns true for Undo or Redo. Otherwise it returns `!previewEditing && !inActiveEditor`.
   - `noteOutsideChange` (`src/extension.ts`) sets `inActiveEditor` when the changed document is the document of `vscode.window.activeTextEditor`.
   - The Studio custom editor or the preview panel being focused leaves no active text editor, so changes from agents, tools and the disk still glow in that case.
2. **Real-window assertion.**
   - New test hook: `updateGlowPatches` holds the last 10 content patches as `{fromVersion, toVersion, ranges}`. It is kept on `ActivePreview`, set in `postContentPatch` and exposed by `getActivePreviewForTests`.
   - New `test/integration/updateGlow.test.ts`, wired into `trusted-suite.ts` after `runIncomingChanges` and registered in `test/shared/e2eGroups.ts` (group lifecycle-sync). It opens a fixture and its preview, then makes an untitled plaintext document the active editor, so the preview keeps the Markdown document. It then checks four steps:
     - (1) A preview checkbox toggle, sent as `previewCheckboxToggle` through `sendPreviewMessageForTests`: the patch has no ranges. The Markdown document is not in the active editor here, so only the in-flight tracking keeps it from glowing.
     - (2) A `WorkspaceEdit` from outside: the ranges cover the edited line.
     - (3) The Markdown editor is shown again and the `type` command types into it: no ranges.
     - (4) `undo`: the ranges cover the typed line.
   - Every step waits for the patch whose `toVersion` is the document version. There are no fixed sleeps, except the existing 250 ms retry of a stale preview message, copied from blockClipboard.
3. **README.** It now says "about 120 to 200 ms; the update glow fades over about half a second".
   - README, CHANGELOG and the glossary also follow item 1. Examples of outside changes are now another tool or an agent, or a file changed on disk. Typing in the active text editor is listed as not glowing. Before, the docs gave typing as an example of an outside change.
   - The glow stays at 600 ms.
4. **`test/visual/capture.py`.** After its checks, `check_update_glow` now:
   - saves a step PNG `glow` (new name in `STEP_NAMES`) that shows the paused glow;
   - restores `reduced_motion="reduce"`;
   - waits (`wait_for_function`, not a sleep) until the glow animation and its mark are gone.

   The rest of the scenario, and the final frame, now run on a settled page like the other scenarios. Restoring reduced motion cancels the glow, so the final PNG no longer shows it. The glow evidence moved to the `--glow` step PNG, and the scenario descriptions say so.
5. **Editor-close fade cut short by the next patch.** Not fixed; see open points.

## Autonomous decisions

- **"In the active text editor" means "typing".** A tool or agent that edits the document the user has open in the active text editor does not glow either. The API gives no way to tell the two apart. Undo and Redo always glow.
- **The glow evidence is a step PNG (`--glow`), not the final frame.** Restoring reduced motion, which the review asked for, cancels the glow animation.
- **The integration test runs under `--trusted-only`,** the suite it is wired into, so the shared window stays free sooner.

## Open points

- **Editor-close fade cut short by the next patch (item 5): not fixed.** A safe fix would have to move the running fade onto the element the patch puts in its place, at the same time offset (Web Animations `currentTime`). Simply moving the attribute would restart the fade from 0.35 and flash. That is more than a simple change. The effect is a jump of at most about 0.65 opacity to 1 within 160 ms, and it is cosmetic.
- **Agent edits of the document in the active text editor do not glow.** If that matters, a follow-up could add a short "recent keystroke" window, for example from `onDidChangeTextEditorSelection` with `kind === Keyboard`.
- **The visual captures show a "Zoom out (90 %)" tooltip next to the toolbar.** It is also in the round-1 captures, so it is not caused by this round.
- **Only the trusted real-window suite was run.** The other suites (scroll-sync, untrusted, standalone, reload) were not run.
- **Not rebased on origin/main.** That needs the network.
