## What I checked and found sound

- **Own edits versus outside edits and undo.** All 12 edit calls that come from the preview
  (`workspace.applyEdit` and `TextEditor.edit`) go through `applyPreviewEdit` / `editInPreview`. No
  other write path to the previewed document is left: the sidecar `fs.writeFile` calls write other
  files. Undo and Redo always count as outside changes.
  - The in-flight counter relies on VS Code sending the model-change event to the extension host
    before the edit's reply. MainThreadDocuments forwards `onDidChangeContent` synchronously and the
    RPC keeps messages in order, so this holds.
  - The version window (`previous < outsideChangeVersion <= next`) stops a stale mark from
    re-glowing after a full render.
- **No glow on initial render or scroll sync.** Only `postContentPatch` carries `updatedRanges`. An
  initial or full render never does, and scroll sync posts no patch. A patch caused by settings or
  the theme, at the same version, falls outside the window.
- **Soft appearance gate.** `hold()` runs before the patch closes or restores editors, so restored
  editors and patch-closed editors never fade. `@starting-style` only applies at first style, so a
  later keypress cannot replay it.
- **Spec compliance.**
  - Nothing sets an inline style.
  - Only opacity, `translate` and colours move. No existing rule uses the `translate` property, so
    nothing conflicts with it.
  - The table bar's transform is not transitioned.
  - The glow is background plus box-shadow, which causes no layout shift. The visual check measures
    0 moved elements.
  - The reduced-motion block covers every motion selector, and the runtime marks nothing under
    reduce.
  - Contrast stays at least 4.5:1, asserted on light, dark and cream. Current-theme is the default
    mode of the light and dark runs.
- **Changing the page-wide rule from `0.01ms` to `0s` is safe.** No source file, unit test, visual
  test or integration test listens for `transitionend` or `animationend`, except the new
  `motion.ts`, which does nothing under reduce. No existing test asserted `0.01ms`.
- **Running the whole visual campaign with `reduced_motion="reduce"` matches decision 3** ("visual
  tests disable animations"). It hides no runtime branch.
  - The only JS consumer of the media query is `applyTheme`, which mirrors it into
    `data-sphinx-preview-reduced-motion`, and no CSS or visual check reads that attribute.
  - Before this change, the existing 100 ms tooltip transitions ran during captures. They now settle
    at once, which makes captures more deterministic, not less.
- **Determinism.** No sleeps are used.

  - The glow is paused at `currentTime = 0` for the screenshot.

## Findings (none blocking)

- **Low: the README says something that is not true.** `README.md:164` says the animations last
  "about 120 to 200 ms", but the update glow lasts 600 ms (`src/preview/previewStyles.ts:4162`).
  Fix: say the glow fades over about half a second, for example "...short (about 120 to 200 ms;
  the update glow fades over about half a second)...".
- **Low (judgement): the 600 ms glow is outside "about 100–200 ms".** I accept it and do not
  require a change. The glow is a fade-out of a background tint, not a movement, and a 200 ms wash
  is hard to notice as "this changed". The decision is a token (`--sphinx-preview-motion-glow`)
  and the reason is written down. Fix required only in the PR: list it under "Autonomous
  decisions" with the reason, so the user can ask for a shorter value; 300–400 ms would be the
  compromise. If you shorten it, keep the visual bound `300 <= duration` in `check_update_glow` in
  line, or lower it.
- **Medium (recommended before ready): own-edit classification is not tested in a real window.**
  `src/extension.ts:571` (`noteOutsideChange`) and the wrappers are only covered through the pure
  `isOutsideChange` / `updatedRangesForPatch`.
  - I believe the VS Code ordering holds (see above), but if it broke, every preview edit would
    glow. That would go against decision 1.
  - Fix: add the integration assertion the coder proposes. Expose `updatedRanges` of the last patch
    in the `getActivePreviewForTests` snapshot, then assert:
    - a preview checkbox toggle or block save gives no ranges;
    - an outside `WorkspaceEdit` gives ranges;
    - `undo` gives ranges.
  - Run it once under the window lock. This is not blocking for this round because decision 3 asks
    for a unit test of the trigger, which exists.
- **Low (design note for the PR): side-by-side typing will glow on every patch.**
  - Typing in the text editor counts as an outside change. With the preview open beside it, the
    paragraph being typed glows on every debounced patch, because the patch replaces the elements
    and the animation restarts.
  - This follows the user's decision as written ("external change"). Mention it in the PR so the
    user can choose a follow-up, such as not glowing when the change comes from the focused text
    editor.
- **Low: `test/visual/capture.py:2813` leaves the page at `reduced_motion="no-preference"`** for
  the rest of the glow scenario's checks. It does no harm today, because the glow is paused and
  those scenarios have no other motion-sensitive checks. Fix (optional): call
  `page.emulate_media(reduced_motion="reduce")` again after the `state` evaluation, once the glow is
  paused.
- **Info: one new test passes on HEAD.** `test/webview/scrollSync.test.ts:6742` ("own edit ... glows
  nowhere") passes on HEAD by design, as a negative guard that pairs with the positive test above
  it. This is acceptable; say so in the PR's test notes.
- **Info: two effects have no motion-on visual coverage.** The soft appearance and the theme-switch
  transition are covered only by unit tests (attributes and the CSS rule shape) and by the coder's
  manual probe. Decision 3 does not require more. A follow-up visual scenario could assert that
  each enter transition ends at opacity 1 through `getAnimations()` + `finish()`.
- **Info: a fade can be cut short by the next patch.** A block that fades back in after its editor
  closes (`src/webview/scrollSync.ts:1149`) is replaced by the content patch of the save. If the
  patch arrives within 160 ms, the fade ends early, with a small jump to full opacity. This is
  cosmetic and needs no change.
