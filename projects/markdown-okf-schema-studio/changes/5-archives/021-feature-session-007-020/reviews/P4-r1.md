## Findings
1. MEDIUM - the caret can sit under the stuck palette while typing/arrowing in a tall box. There is no `scroll-padding`/caret
   reveal anywhere (grep src), so when the caret moves above the viewport top (Up, PageUp, Home, Ctrl+Z restoring a position) the
   browser scrolls only to the viewport edge and the caret line ends under the sticky band + palette (about 190 px on desktop with
   the two-row MyST palette), invisible while editing; the box has no inner scroll (it auto-grows), so this is the only scroller.
   P4 enlarges the obscured strip by the palette height. Fix: in the block editor, after a caret move in the textarea
   (`keyup`, `input`, `selectionchange` filtered to the textarea), when `edit.host` exists and the palette is stuck, compute the
   caret rect with the existing `caretRectOf` and, if `rect.top < palette.bottom + 8` (viewport coordinates, palette rect from
   `edit.palette.element.getBoundingClientRect()`), `window.scrollBy(0, rect.top - (palette.bottom + 8))` (do not touch the page when
   the palette is not stuck, i.e. its top equals the box top). Also set `scroll-padding-top` on `html` while a host exists (value =
   the same sticky offset + palette height) as a cheap first line of defence. Add a visual/scroll scenario in the tall fixture:
   caret on line 2, press ArrowUp x3 from a scrolled position, assert the caret rect top >= palette bottom.
2. MEDIUM/LOW - the sticky palette is unbounded in height. At 360 px width it is five rows (about 330 px, see narrow-360

   (or set `position: static` from the runtime when the palette's height exceeds ~40 % of `window.innerHeight`), so small
   panes keep the old non-sticky behaviour. Add a unit style test for the rule and extend the 360 px scenario with a tall box if cheap.
