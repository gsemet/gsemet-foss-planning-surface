## Required fixes

1. (Medium) Selection that starts inside a generated span and ends outside it (or vice versa) writes
   markup with wrong extent. editActions.ts applyColour, "no target" branch wraps the raw slice, so
   the slice contains an unbalanced tag. Probe:
   - `ab<span style="color:#c00">cd</span>ef`, select `b<span...>c` ->
     `a<span style="color:#00f">b<span style="color:#c00">c</span>d</span>ef` (blue now also colours `d`).
   - select `d</span>e` -> `ab<span style="color:#c00">c<span style="color:#00f">d</span>e</span>f`
     (the red span now also colours `e`: existing content silently recoloured).
   The markup is balanced only by luck; the meaning changes. Fix: in the wrap branch, compute the
   tag balance of `value.slice(start, end)` (reuse the `<span...>` / `</span>` tokenizer of
   colourSpans, any span tag, not only colour ones); if the slice has an unmatched open or close
   tag, either return `undefined` (refuse) or extend/shrink the range to whole spans. Add a test
   for both directions asserting no change (or the chosen behaviour) and that the output re-parses
   with equal tag counts.

2. (Low) A selection or caret inside a tag's own text (e.g. inside `onclick="x"` of a span, or
   inside the `style="..."` of a generated span: colourTarget only matches content/whole-span, so a
   selection of attribute text) wraps there and corrupts the tag
   (`<span style="color:#c00" onc<span ...>l</span>ick="x">`). Fix in the same place: refuse when
   the range starts or ends inside a `<...>` tag (find the last `<` before each boundary with no
   `>` after it). Test with one case.
