## Findings

1. MEDIUM - quote fallback can silently place a thread on an unrelated block. src/webview/commentThreads.ts:316-334.
   When no block covers the line, `attach` searches every eligible `[data-line]` block and takes the FIRST occurrence
   of the quote in document order, with no uniqueness check and no minimum length. A thread quoting "the", "data", or
   any phrase repeated in the document is highlighted at the first occurrence, far from where it was written, which is
   exactly the "surprising misplacement" D25 wants to avoid (it should be listed as orphaned instead). Fix: in the
   fallback branch (`!block` only), count matches over all candidate nodes (use the same variants); place the mark only
   when exactly one match exists AND the quote length is >= ~12 characters (or when prefix/suffix of the anchor, which
   the page already receives, disambiguate); otherwise return false so the thread goes to the Orphaned box. Add tests:
   quote present twice -> orphaned, not marked; short quote -> orphaned; unique long quote -> placed (existing test).

2. LOW - fallback is quadratic. commentThreads.ts:332 `nodes.includes(node)` inside the loop over all text nodes of
   all blocks, executed for each unplaced thread (up to 1000 threads, thousands of nodes) can freeze the page during
   `apply()`. Fix: use a `Set<Text>` for dedupe (or iterate `document.querySelector("#sphinx-myst-preview-content")`
   text nodes once per apply and reuse the list for all orphan candidates).

3. LOW - a reply pending while the same thread is deleted can lose the typed text. commentThreads.ts:173-190
   (`paintActions`) and :597: Resolve/Delete are disabled only for a pending `act`, not for a pending reply (`sent`).
   Sequence: Send reply, then Delete -> Yes before the ack; if the delete is processed first (or the thread is deleted
   externally), the reply is refused ("no longer exists"), but the thread vanished, `apply()` closed the popover and the
   refusal and the text are invisible. Same for a draft typed in the reply box when Delete/Yes is clicked (explicit
   intent, acceptable). Fix: treat `sent?.waiting && sent.threadId === openId` as busy in `paintActions` and the click
   handler (disable Resolve/Delete/Yes while a reply is in flight). Optional extra: when `result()` gets a failed reply
   for a thread no longer in `threads`, show it through the existing toast/`showWarningMessage` (host already shows one,
   so this is covered for the user; hence LOW).

4. LOW - no real-browser scenario for the orphan box. The scroll review focus is guarded only by a CSS-string test
   (previewStyles.test.ts T44) that checks the margin text equals the padding text. My probe above confirms the intent,
   but nothing would catch a future change to the content's padding mode or the box's `width`/`padding`. Suggested
   follow-up (not blocking): one visual/scroll scenario with a document that has an orphan, asserting
   `documentElement.scrollHeight` equals the same page without the box when the box is shorter than the padding.

5. INFO - when a request carries a threadId over the validator limit or empty, the message is dropped by the registry
   with no `previewCommentResult`; the page times out after 15 s and keeps its state. Page-generated ids never hit this.
   No action.
