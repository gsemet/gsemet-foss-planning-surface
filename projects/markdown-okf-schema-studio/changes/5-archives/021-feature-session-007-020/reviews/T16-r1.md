# T16 r1 review - incoming-change marks

## Findings

1. MEDIUM - included blocks are marked from the parent file's diff.
   `src/webview/incomingChanges.ts` (apply, the `querySelectorAll("[data-line]")` loop).
   Blocks that come from `{include}` carry the directive's own `data-line`/`data-end-line` and
   `data-sphinx-preview-included="true"` (`src/render/mystRenderer.ts:491`, `:654-662`). The loop
   does not skip them. So when the directive line is new or edited, every included block (innermost
   ones) gets the green bar, although the included file's content did not change. Content of an
   included file is never diffed. The brief says included blocks must not be marked from the
   parent's diff, and no test covers it (no "include" in `test/webview/incomingChanges.test.ts`).
   Fix: in `apply`, skip elements that have `data-sphinx-preview-included` or sit inside one
   (`element.closest("[data-sphinx-preview-included]")`). Add a webview test with an included
   block whose mapped lines meet a range (expect no mark) and one with the directive's own
   non-included wrapper, if any.

2. LOW - trust change at runtime is not re-posted until the next render (implementer already
   noted it). `postIncomingChanges` checks `vscode.workspace.isTrusted`, but nothing listens to
   `onDidGrantWorkspaceTrust`. Acceptable (trust only goes false -> true, marks appear on the next
   render). Optional fix: call `scheduleIncomingChanges(preview, 0)` for each preview on grant.

3. LOW - `repositoryOf` in `src/git/headBaseline.ts` runs `getAPI(1)` on every call (cheap, wrapped
   in try/catch). No action needed. Noted: `watch` is only started once a baseline was read, so a
   repository whose first HEAD appears later (first commit in a new repo) is picked up on the
   next render/keystroke, not by the watch. Acceptable.

## Verified (no issue)

- Activation and failure safety: the extension is looked up with `vscode.extensions.getExtension`
  (undefined when missing or disabled); `activate()`, `getAPI`, `getRepository` and `show` are all
  inside try/catch and return undefined. `package.json` gains no `extensionDependencies`
  (grep: none). No git spawn. The unit test file `headBaseline.test.ts` (5) passes.
- Edge cases: non-`file:` scheme, > 1 MB (current length and blob), no HEAD commit (new repo),
  untracked (show throws -> undefined) all give "nothing". Detached HEAD has `HEAD.commit`, so it
  works. Untracked posts nothing unless marks or `enabled` must be taken back.
- lineDiff: prefix/suffix strip, Myers with cap fallbacks (20 000 lines, 2000 edits), EOL
  insensitive split, 1-based inclusive ranges. I ran 3000 random pairs: the unmarked lines are
  always a common subsequence of the base (0 failures). Ranges are in the whole current text, so the
  frontmatter offset is correct provided `data-line` is absolute (it is, shared with scroll sync).
  Deleted-only changes give no mark (D19).
- Performance: 300 ms debounce re-armed on each render/patch; 0 ms only for ready, setting and
  preference changes; the watch ignores `state.onDidChange` unless the HEAD commit id changed;
  cache keyed by commit+path, max 64 entries, each <= 1 MB; stale stage results dropped.
- Messages: page uses `sameContext` (documentId, version, requestId); ranges validated with
  `Number.isSafeInteger`, start >= 1, end >= start; only attributes are set, nothing as HTML.
  Existing scrollSync test covers a stale requestId.
- Marks and layout: innermost marking, skipped in/under open editors, cleared and re-applied in
  `initializeContent` after patches; inset 3px box-shadow, no layout shift; shell key untouched.
- Setting/preference: `showIncomingChanges` false -> `enabled:false`, empty ranges, marks taken
  back; combined with `sessionViewPreferences.incomingChanges` and trust. The config-change handler
  covers the new key (whole section) and posts at once. `data-okf-incoming-changes` is only set on
  message (absent = enabled), so there is no startup effect (the startup-effects snapshot was
  respected by removing init-time querySelectorAll/attribute set - correct fix in the product), and
  T17 can hide its toggle with `html[data-okf-incoming-changes="false"]`.
- Repo files: package.json description is in T02 style (markdownDescription with On/Off), README,
  CHANGELOG and glossary entry match the behavior.
- Gate log green per the orchestrator. The positive git path is only covered with a fake API
  (known limitation, accepted for this round).
