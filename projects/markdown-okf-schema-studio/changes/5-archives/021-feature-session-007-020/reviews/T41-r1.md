## Required fixes

1. [medium] `pendingMoveSelection` can outlive its move and restore a stale selection later.
   scrollSync.ts `resumeMoveSelection` (~l.3993) and `startBlockMoveFlight`.
   The only clearing paths are: applied, refused, the 5 s timer of the live flight, or a different
   document/count at apply time. If the page reloads while the flight is open (the timer dies with
   the page) and the reloaded page still has the move's version (the move was refused or never
   landed), `resumeMoveSelection` returns early and leaves the value in the saved state with no
   timer. It survives (also across a VS Code restart with a serialized webview). At the next full
   reload with a different version (any later edit, an external edit) and an equal block count, it
   selects blocks by ordinal that the user never selected. An external edit that reloads the page
   during the 5 s window can also restore by ordinal onto changed content.
   Fix: store `at: Date.now()` in the pending value; in `resumeMoveSelection` (and
   `applyMoveSelection`) drop it (`setPendingMoveSelection(undefined)`) when older than ~5 s
   (>= 5000 ms), and when the version equals `pending.version` after a reload, arm a 5 s timer that
   clears it (or clear it at once, since a lost flight cannot be completed). Add a webview test: a
   saved pending with same version -> nothing selected and the saved state no longer contains
   `pendingMoveSelection`; and one with an old `at` and a different version -> nothing selected.
