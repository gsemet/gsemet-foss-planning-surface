## 1. Blocker fix
- Select blur: relatedTarget inside the frame keeps the editor open; otherwise `onLeave` runs
  `saveBlockEdit` guarded by `activeBlockEdit === edit && !edit.finishing` (same shape as the link
  panel). One save; textarea blur and select blur cannot both save because the first sets finishing.
  The stuck-editor case (focus left on the select, then click outside/another block) now saves.
- Dismiss without change: the click-toggle heuristic (`listOpen`) is imperfect with a native popup
  (on macOS an outside-click dismissal sends no click to the select, so `listOpen` stays true and the
  next click on the select hands focus back to the text box while the list is opening, so the user
  may need a second click). Harmless: focus never stays stranded because blur-save covers it. [Low]
  Optional: reset `listOpen` on `mousedown` outside, or ignore.
- Escape on the select returns focus to the text box, a second Escape cancels: acceptable (the first
  Escape also closes a native list, so a single Escape cancelling the whole edit would surprise).
  Enter returns focus; Cmd/Ctrl+Enter runs `onDone` (final save), same as the text box. Fine.

## 2. New tests (reasoning against r1)
They drive `blur`, `click`, `keydown` on the select and `onLeave`/`onDone`; r1 had only a `change`
listener, so "dismiss hands focus back", "one final save on leave, none when moving inside",
"Escape/Enter/Ctrl+Enter" and "Ctrl+Shift+M" all fail on r1 (no handlers, no `focusModeSelect`).
The implementer did not run them on r1; reasoning confirms they are real. They set edited text so
an unchanged block's no-op save cannot hide a missing save. The "click another block afterwards"
path is covered only by the blur save (harness has one block): acceptable.

## 3. Read-only refusal (untrusted suite)
Sends `previewPaletteModeChanged strict` to the read-only preview and asserts the next preview's
runtime context still has `"initialPaletteMode":"myst"`. With the `!preview.readOnly` check removed
the stored value would be strict, so the test is real. Weakness: it passes too if the message is
dropped earlier (bad id), but the ids come from the live preview, so that is unlikely. OK.

## 4. Ctrl/Cmd+Shift+M
- Conflict: Cmd+Shift+M (macOS) / Ctrl+Shift+M (Windows, Linux) is the default workbench
  "Toggle Problems" binding. VS Code forwards webview keydowns to the host from a window-level
  listener; `preventDefault` alone does not stop that, `stopPropagation` on the textarea (done here)
  normally keeps the event from reaching it, so it should stay inside the webview, but this is
  behaviour of VS Code internals I could not verify offline, same class of risk as T22's Cmd+K.
- Scope is small: only while a block editor text box has focus, never in the plain preview.
  Recommendation: KEEP, conditional on the manual check you already list for T22: with a text box
  focused, press the shortcut and confirm the Problems panel does not open and the select takes
  focus (macOS and one of Windows/Linux if available). If the panel opens, switch to a binding with no
  workbench default (for example Alt+Shift+M, matching on `event.code === "KeyM"` so macOS Option
  characters do not matter). Not blocking; the select is also reachable with the mouse.
- Document the shortcut in the README shortcuts section once one exists (none today).
