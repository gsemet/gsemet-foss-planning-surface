## Checks that pass

1. No inline `style=` in markup. Width is applied only through `style.setProperty` in
   `src/webview/figureSizes.ts`. The function is self-contained (own regex, no outer references) and
   is injected with `.toString()` in scrollSync.ts. `data-okf-width` is validated three times with the
   same pattern: the renderer (`FIGURE_WIDTH`), the sanitizer (`SAFE_OKF_WIDTH`, attribute removed with
   a diagnostic) and the runtime. The html-policy test covers `60%;position:fixed`, `url(x)` and the
   empty value. The align class is built only from the `left|center|right` whitelist.
2. Label ids: `ANCHOR_LABEL = /^[A-Za-z0-9_.:-]+$/u` gates everything, so a hostile label (quote, `<`,
   space, unicode) gets no anchor and cannot reach the `id="..."` replacement. The span id is omitted
   when a heading or figure already carries it, and a test asserts exactly one `id="intro"`.
3. `{ref}` to a plain label links to `#name`. The heading `{ref}` text is taken from the heading text,
   without the icon. The anchor has no text node (the glyph is CSS `::before`), so
   `tocColumn.headingText` (`textContent`) and heading copies are unchanged. Screenshots show the
   heading ids, anchors and `{ref}` links correct in all three themes.
4. widthMode.ts: the change is minimal. A figure sized in %/em/rem does not break out in Auto, and a px
   `data-okf-width` replaces the intrinsic width. This is consistent with U22 (figures take the space
   they need, up to the max). previewNavigation.ts: the `#label` match is minimal, skips fences, is
   covered by a unit test, and uses the same character set as the renderer.
5. Tests: 7 of 8 new unit tests failed before the change. The amsmath test is a guard and passed
   before, which is stated honestly. The CHANGELOG, README and glossary diffs contain only the task's
   own lines. The user's heading-level change, the `<!-- TODO ... -->` lines and the commented
   CHANGELOG bullet are untouched.

## Required fixes

1. MEDIUM, src/render/mystRenderer.ts `anchorProperties` (and the anchor-row span): the span carries
   `data-line`. In html-sanitizer.ts `injectSourceMappings` (line ~339) every element with `data-line`
   becomes a mapped source block. It gets `data-sphinx-source-*`, a `data-sphinx-preview-block` id and
   `tabindex="0"`, because a span is not naturally focusable. Every anchor icon therefore becomes a Tab
   stop and a separate one-line mapped block nested inside its paragraph or heading. A click or
   double-click on the icon can target the one-line `(label)=` range instead of the paragraph. This
   also adds mapping noise for incomingChanges, scrollSync and source mapping, and risks the
   edited-text-stays-in-place and one-undo-per-action behaviour. The brief asked for `data-line` on the
   span, but the regression risk outweighs it. Fix: do not emit `data-line` on the inline span or the
   row span, and update the test that asserts `data-line="1"`. If `data-line` is kept, then at least
   (a) the sanitizer must not add `tabindex` to `.okf-anchor`, and (b) a test must show that clicking
   or editing from the icon opens the editor on the labelled block and not on the label line.
   Scrolling to a label already works through `markdownFragmentRange`, which does not need `data-line`.
