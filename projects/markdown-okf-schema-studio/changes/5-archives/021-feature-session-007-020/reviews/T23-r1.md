## Findings

### 1. [High] Dismissing the select without a change leaves the editor stuck open
`src/webview/editPalette.ts` (modeSelect, ~l.90-118) and `src/webview/scrollSync.ts` (textarea blur ~l.3005).
Clicking the select moves focus from the text box into the select (relatedTarget inside the frame,
so the textarea blur correctly does not save). Focus only goes back to the text box in the
`change` handler. If the user opens the list and dismisses it (Escape, click on the same option,
click elsewhere), nothing changes and focus stays on the select. Consequences:
- the textarea has no blur any more, and nothing listens to the select's blur/focusout, so clicking
  outside the frame never saves/closes the editor. `openBlockEditor` returns early while
  `activeBlockEdit` is set, so clicking another block does nothing: the editor is stuck;
- Escape is only handled in the textarea keydown (and the document Escape handler returns for
  a target inside the frame), so Escape does not cancel; Cmd/Ctrl+Enter is also dead.
This violates the "palette UI keeps the editor open / T22 blur relaxation" rule in the reverse
direction (it must also save when focus really leaves). The unit and reload tests only cover a real
change, so this is untested.
Fix (pick one, test it):
  a. Add `onLeave` to `EditPaletteDeps` and wire the select's `focusout`: if `event.relatedTarget`
     is not inside `edit.element`, call `saveBlockEdit()` (same shape as the link panel's `onLeave`
     with `isInsideFrame`); and add a select `keydown` that, for Escape, returns focus to the
     textarea (and lets a second Escape cancel) or calls `cancelBlockEdit()`; or
  b. Return focus to the text box whenever the select loses its popup: listen to the select's
     `blur`/`click`-after-close and call `getControl().focus({preventScroll:true})`.
Add unit tests: select focused, blur with relatedTarget null -> `previewEditSave` posted (or editor
closed); select Escape -> editor cancelled/focus back. Keep the same-value and unknown-value paths.

## Accessibility (recommendation, not blocking)
The select is unreachable by keyboard: Tab is trapped in the text box and the palette buttons are
`tabindex=-1`. The brief only requires mousedown/keyboard "changing", so this is not a blocker, but
a mouse-only control is a real gap. Recommend (follow-up task, small):
- a shortcut in the text box (e.g. Cmd/Ctrl+Alt+M, or Alt+ArrowUp/Down) that focuses the select, with
  Escape/Enter returning focus to the text box (this also solves finding 1 for keyboard users);
- or Shift+Tab from the first character/at caret 0 moving to the palette (roving tabindex).
If a shortcut is added it must follow Cmd on macOS / Ctrl elsewhere and be listed in the tooltips/README.
