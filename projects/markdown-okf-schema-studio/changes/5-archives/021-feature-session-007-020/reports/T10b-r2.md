# T10b r2 - tables take their full max-content width

## Cause
The table was already measured uncapped (r1), but `scrollWidth` is an integer: the table's max-content
width was 1038.2 px, it got 1038 px, so auto table layout squeezed the cells by 0.2 px and wrapped
them ("Latency p95", "OPS-1063", ...). Not a wrapping-dependent measurement (checked in a browser:
max-content with wrapping and with nowrap are both 1038.2).

## Changes
- `src/webview/widthMode.ts`: the natural width is `ceil(max(scrollWidth, declared width, naturalWidth,
  fractional getBoundingClientRect().width))`, read in the same single batched read pass (all
  `data-sphinx-preview-measuring` writes first, then all reads, then writes). Breakout is
  `ceil(natural - column)` when natural <= available, else `floor(available - column)` (never wider
  than the pane area, cells may wrap/scroll then). Centring shift unchanged.
- `test/webview/scrollSync.test.ts`: new "T10b: a wide table gets its fractional max-content width
  rounded up, so no cell wraps" (scrollWidth 900, box 900.4 -> breakout 201px; gives 200px before).
  Harness `getBoundingClientRect` already existed; existing T10 assertions unchanged and green.
- `test/visual/capture.py` `apply_width_shot` (scenario `readme-margin-break-cream`): fails when any
  table cell's text is taller than 1.4 line heights while the table fits the pane. The r1 screenshot
  state (wrapped cells) is what it detects; I did not re-run the suite against the old code
  (about 10 min), the unit test was reasoned to fail before (900 -> 200).
- `images/readme/margin-break-cream.png` regenerated (1200x900, 183180 bytes): every cell on one
  line, table about 1040 px wide centred, figure centred.
