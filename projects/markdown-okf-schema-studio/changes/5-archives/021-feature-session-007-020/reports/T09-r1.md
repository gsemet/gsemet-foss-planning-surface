## What was done
- CSS: `#sphinx-myst-preview-content > :first-child { margin-top: 40px }` (beats the h1/h2/properties
  margins by specificity). The column gets `display: flow-root` so the margin stays inside it and the column's
  own top never moves. NO padding on the column. The properties table margin 32px -> 0.
- The fixed `--first` offsets (56/96 px editor, 24 px insert point) are gone. The first-block editor
  (also in the paragraph case, where an existing `p[editing] + .editor` rule had overridden it, so the paragraph
  editor sat at 0 px before) and the Start writing button use
  `calc(40px + var(--sphinx-preview-first-clearance, 0px))`. The clearance applies to edit-mode
  elements only; the preview itself is always 40 px.
- `installFirstClearance(document, window)`: clearance = `max(0, toolbarBottom + 8 - contentTop - 40)`, only
  when the toolbar rect and the column content box overlap horizontally, else 0. Published as
  `--sphinx-preview-first-clearance` on the root, only when changed. Recomputed on window resize,
  ResizeObserver (column, toolbar), MutationObserver (toolbar rows/attributes; root style/class/edit-mode/zoom),
  and in `initializeContent` (every render/patch). Properties table first: works too (no `--first` class there,
  the table sits at 40 px).

## Scroll sensitivity (root cause, as requested)
Not an anchoring bug. RI-T31 case A clicked at 30 % of the height of `.monaco-editor .view-lines`, an element as
tall as the whole document (2952 px) that moves with the editor scroll. The preview sync scrolls the editor
to the preview's line: line 54 before my change, line 52 with the extra 40 px (any content offset shifts the
mapped line). That moved the click point by ~36 px: before, it landed on the title bar drag region (nothing
focused, the typed "x" was lost, ver stayed 1), after, on the `smoke.md` tab label (focuses the editor with the
cursor still on line 1). "x" then went in at line 1, VS Code revealed the cursor (editor jumped to lines
1-43), the host posted `sourceScroll line=1` and the webview ("the editor leads") scrolled the preview to
`yAtLine(1)=0`. That is the correct product reaction; the test only passed because its keystroke never
reached the document. Diagnosed with temporary instrumentation (removed). Fix: the test clicks inside the
visible `.monaco-editor:visible` box (one-line change plus comment) so it really clicks a text line;
RI-T31 case A/B/b then pass with padding-free 40 px margin. A margin on the first child (not padding on the column)
was kept as asked; `display: flow-root` was verified not to be the cause (same failure without it).

## Deviations
- Clearance is applied to the open first-block editor and the Start writing button only (item 2 of the brief),
  not to the first element in plain edit mode; in preview mode it is always exactly 40 px even where the toolbar
  covers it (required by the test statement "40 +-2 for narrow panes in preview").
- Changed the RI-T31 case A test click target (see above) and the final-frame toolbar rule.

## Open points
- Properties table at 40 px: on a narrow pane (460) the toolbar (bottom 82 px) covers the right part of the
  table header row, where the T08 32 px margin had been chosen to keep the Description toggle below row 2. The spec
  says 40 px for the properties table, so I followed it; if the Description toggle must stay reachable on narrow
  panes, the table needs the clearance in preview mode too. Screenshot:
  `out/reports/e2e/screenshots/first-element-gap-properties-460.png`.
- Entering edit mode never moves the first element (checked), but opening the first block's editor on a pane
  where the toolbar overlaps moves that block by the clearance (50 px) by design.
