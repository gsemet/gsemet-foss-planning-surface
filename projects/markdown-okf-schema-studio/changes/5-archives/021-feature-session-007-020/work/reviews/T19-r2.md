## 1. Refresh targeting (src/extension.ts `onConfFileEvent`, ~3050)

Correct. `before` is computed from the shared locator cache before `invalidateConfCache()`, `after`
from a fresh walk. Cases:
- change of the governing conf.py: before == after == file, refresh.
- deletion of it: the cached `before` is the deleted file, refresh (after finds the next one).
- creation of a closer ancestor conf.py or a D29 fallback appearing: `after` == new file, refresh.
- a D29 fallback disappearing: `before` == file, refresh.
- unrelated conf.py (not an ancestor, not the fallback): no refresh.
A stale cache can only make `before` name the previously governing file, which is exactly what is
needed. `sameFile` uses `canonicalPath`; ignored segments are skipped first. The forced refresh
(`isDependencyChange = true`) goes through `deferWhileEditing`, so an open block edit queues it
and `EditLock.release()` flushes it when the editor closes.

Low finding (no fix needed): the deferral key "render" is shared with `refreshReferencedPath`
(extension.ts:2894, non-forced), and a later `defer` with the same key replaces the earlier work.
A conf.py change queued during a block edit could be replaced by a non-forced refresh. In
practice that path returns early for an unchanged save, and any real edit bumps the document
version so the refresh renders against the already invalidated cache. Optional: use a distinct key
such as "render-conf".
