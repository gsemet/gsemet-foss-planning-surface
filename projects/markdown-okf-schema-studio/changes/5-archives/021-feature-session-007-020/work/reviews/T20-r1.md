### F1 (medium) Platform-specific modifier for B and I, and key-first matching
`src/webview/editActions.ts` `shortcutFor` (end of file) and `src/webview/scrollSync.ts`
`paletteShortcut` (~1518).
- Deviation 1: reject as implemented. The brief says "Cmd (mac) or Ctrl", which means Cmd on
  macOS and Ctrl elsewhere. Today Ctrl+B on macOS is swallowed (preventDefault) and replaced by
  bold, so the emacs "back one character" key stops working in every block text box. Ctrl+I is not
  a standard macOS text key but is still hijacked for nothing. On Windows/Linux, `metaKey` is the
  Windows key: accept it never.
  Fix: `shortcutFor(event, platform)` (or a `primaryModifier` option of `createEditActions`) with
  `mac = /mac|iphone|ipad/iu.test(String((navigator.userAgentData && navigator.userAgentData.platform) || navigator.platform || ""))`.

  that must stay. Add editActions unit tests for both platforms (Ctrl+B ignored on mac, Cmd+B
  ignored on Windows/Linux). The realInput scenario already uses `MOD` and keeps working.
- Related (same function): matching on `event.code === "KeyB"/"KeyI"` is layout independent in
  the wrong way. On Dvorak the physical B key types "x", so Cmd+X (cut) becomes bold; on Colemak

  already has the key fallback; for B/I use `keys: ["b","B"]`/`["i","I"]` as primary and keep the
  codes only for the non-Latin fallback. Add a test: `{key:"x", code:"KeyB", metaKey:true}` must
  not match, `{key:"b", code:"KeyX"}` must.

## Verified OK

  restored via the returned edit. `scenarioShortcuts` asserts one Cmd/Ctrl+Z restores each time.
  The scenario is real: the unchanged code would not edit the value (Cmd+B toggles the VS Code
  side bar / nothing, Ctrl+/ does nothing in the textarea), so `expectValue` times out. It
  asserts on the focused textarea value, not a mock. Note it always presses `Control+/`, so Cmd+/
  is covered by unit test only.
- Event handling: preventDefault + stopPropagation always, even for a no-op edit (so Cmd+B never
  toggles the sidebar). Composition (`isComposing`) and any `altKey`/AltGraph ignored (stricter
  than the brief's `ctrl && alt`; fine, keeps Cmd+Alt combos for other tasks). Shift ignored
  except for `/` (`anyShift`, needed for AZERTY).

  `wrapSelectionInControl` (which already returns on `metaKey`/ctrl non-AltGr), so `*`/`_` typing
  wrap is unaffected; navigation, Enter, Tab, Escape and Cmd+Enter keys do not match any
  shortcut. Only the block/insertion textarea registers it; frontmatter editor and cell input do
  not.
- Registry design: `{actions, byId, shortcutFor}`, `EditAction` fields as specified (modes,
  scopes, popover, apply). Shortcut matching is data-driven, so T21+ only append entries.

## Optional, low severity (no fix required for approval)

- L1 Partial selections inside markers produce garbled markup: `**f[oo]**`-like cases, e.g.
  `**foo**` with selection `fo` -> `****fo**o**`, and `foo **bar**` with `o **ba` ->
  `fo**o **ba**r**`; selection spanning two bold runs (`**a** and **b**` select all but the outer
  asterisks) -> `a** and **b`. Suggested rule: when the content has an asterisk run on only one
  side, treat as not wrapped and refuse (return undefined) rather than emit broken markup, or
  extend the selection to the whole word first.
- L2 Underscore emphasis is not toggled: `_foo_` + italic -> `_*foo*_`, `__foo__` + bold ->
  `__**foo**__`. Brief only specifies `*`; consider detecting `_`/`__` runs the same way, or at
  least document it.
- L3 Empty selection inside a word (`fo|o`) inserts an empty pair (`f****oo`) instead of wrapping
  the word; that matches the brief ("inserts the pair with the caret inside") and is acceptable.
