## Findings

### F1 (medium) Hidden comment body and chip label leak into heading text consumers
- `src/render/commentMarkers.ts:118-135` (`commentNode`), consumers `src/webview/tocColumn.ts:66`
  (`headingText`) and `src/webview/scrollSync.ts:699,705` (sticky headings).
- `## Plan <!-- TODO fix later -->` renders `<h2>Plan <span class="okf-comment"><span chip>TODO</span>
  <span class="okf-comment-body" hidden>TODO fix later</span></span></h2>`. Both consumers read
  `heading.textContent`, which includes hidden nodes. The TOC entry and sticky header then read
  `Plan TODOTODO fix later`; a gray comment gives `Plan <!--note`. Before T14 the comment was
  dropped, so this is a regression in the just-landed TOC feature. Book-style headings with a
  trailing TODO comment are plausible. A plain `# Title TODO` is fine (the chip text is "TODO").
- Fix: make the heading label ignore chips and hidden bodies. In `headingText` and the two
  scrollSync sites, clone the heading, remove `.okf-comment, .okf-comment-body` (keep the
  word-TODO chip, whose text is part of the sentence), then read `textContent`. Alternatively do
  not turn inline comments inside `heading` into chips (leave `PHRASING_PARENTS` without `heading`
  for comments only). Add a unit test on `headingText` (tocColumn tests exist) with a commented
  heading.

### F2 (low) Context-tag regression test is loose
- `test/rendering/commentMarkers.test.ts` "context tags still render as before": the regex
  `/&lt;context>|&#x3C;context>|<context/u` and "one chip" do not prove the admonition
  (`aside.myst-context-admonition`) is still produced. Behaviour is in fact intact (probe:
  `<context>\n<!-- c -->\n</context>` gives the aside with the comment div inside), but assert
  `findElement(doc, hasClass 'myst-context-admonition')` and add a comment-inside-context case.

### F3 (low, info) Two comments in one html block are dropped
- `<!-- a -->` immediately followed by another comment on the next line: probe showed two separate
  `div.okf-comment` (good, markdown splits them). Only `<!-- a --> trailing text` and
  `<div>\n<!-- c -->\n</div>` are dropped, exactly as before. Not a regression.

## Points the orchestrator asked about

- Comment followed by `<script>`: safe. `COMMENT` is anchored (`^<!--...-->$`) and any inner `-->`
  rejects the match (`commentText`, line 58). `<!-- x --><script>..</script>` and the nasty
  `<!-- x --> <script>..</script> -->` are not converted and stay dropped as before; nothing
  reaches the DOM. Stricter than the brief's "stays text" and acceptable; the test asserts no
  `<script` at all.
- Unit-test placement: acceptable. `rewriteSphinxHtml` is the production sanitizer
  (`src/preview/webview.ts:249`), the sanitizer is a deny-list (strips `on*`, `style`, `srcdoc`;
  `html-sanitizer.ts:233`), and role/tabindex/title/hidden/aria-expanded pass untouched, so no
  allowlist change was needed or made. Test checks 3 chips survive, no `on*` attributes, and
  `role` kept. It would be tidier in `test/security/html-policy.test.ts` as the brief said, but it
  runs the real path.
- 4 tests that pass before the change: meaningful guards (TODO in code/link/math, tool comments,
  script, raw table). The 9 others fail without the call (per the report; logic confirmed).
- `scenarioCommentBlockEdit`: real. It asserts one block chip, one TODO chip, chip click opens no
  editor, a click at x=300 on the block opens the editor with exactly `<!--\nkeep this\n-->`.
  The gate log shows it passing. It cannot pass on old code (no element), so "not run before" is
  immaterial.
