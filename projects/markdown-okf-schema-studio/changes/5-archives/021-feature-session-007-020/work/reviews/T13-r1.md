## Findings

### F1 (medium) src/webview/tocColumn.ts, `track()`: `entries[index].top <= line`
A TOC click scrolls via `revealElement` -> `scrollTopForY(y, offset)` = `y - offset`, so the
clicked heading lands exactly on the reading line. `y` (rect.top + scrollY) and
`readingOffsetValue` are fractional, and `window.scrollTo` snaps to device pixels. When the
scroll position snaps down, `top` ends up a fraction of a pixel below the line, the comparison
fails, and the previous section is highlighted right after clicking an entry. The unit tests use
integer tops and the visual check only asserts "exactly one current entry", so neither catches it.
Fix: compare with a tolerance, `entries[index].top <= line + 1`, in `track()`. Add a unit test with
fractional values (heading top 740.4, line 740, expect that heading current). Optionally have the
visual check assert that the clicked (9th) entry is the current one when it can reach the reading
line (a heading near the document end cannot, by design).

### F2 (low, no action required) cream theme not covered by the visual contrast check
`toc-column-*` scenarios run light and dark. The highlight is a 14 % tint of `currentColor` over
an opaque nav background (`--vscode-editor-background`), so contrast with the text is a theme-
independent ratio (about 7+:1 for any text/background pair that passes AA). Acceptable.

### F3 (low) `keepVisible` reads layout inside the scroll frame
`track()` calls `getBoundingClientRect` on the nav and the item only when the current entry
changes (early return otherwise). That is bounded (a few reads per section crossing, no heading
reads), and the heading-top cache requirement holds. Mentioned for completeness only.
