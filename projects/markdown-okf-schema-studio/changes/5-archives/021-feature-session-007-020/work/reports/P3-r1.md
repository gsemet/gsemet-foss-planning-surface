# P3 r1: one uniform 40 px gap above the first element

## Cause of the "huge" gap
The T09 clearance (toolbar bottom + 8 - 40 = 50 px) was added to the first interactive element
whenever the toolbar shared horizontal space with the COLUMN, not with the element. So at 900 px:
Start writing (a 105 px button on the left) sat at 90 px, a leading properties table at 90 px even in
read mode, and the first block editor at 90 px, while the toolbar is on the right. The palette
(P4) also sat 46 px below its frame top at every width, on top of the first text line (sticky top
below the reading offset), which the old check missed because it measured the host only.

## Decision (T09 exception revisited)
The toolbar still has to stay off interactive things, but the gap must not grow:
1. Plain content (read mode, title, text, picture, table, admonition): exactly 40, as before.
2. The clearance is now decided per element from the element's OWN rectangle, not the column:
   - Start writing: pushed only if the button itself is under the toolbar (never at 900/1600).
   - Properties table: only its clickable controls count (Description toggle, badge, links); the
     header cells no longer do. A plain table stays at 40 in all panes.
3. A full-width interactive block cannot dodge a corner toolbar by moving, so it narrows instead:
   `--sphinx-preview-first-inset` (inline-end margin) removes the width the toolbar covers from the
   open first-block editor (frame + palette) and from a properties table whose right-aligned
   Description toggle would be under the toolbar. Gap stays 40. It is decided before the editor
   exists (no jump) and the first-block palette uses `--sphinx-preview-first-bar-bottom` (0 when
   narrowed), without the reading offset.
4. Exception, only when less than 320 px would remain (panes of about 480 px or less, toolbar covers
   most of the width): the element is pushed just below the toolbar as in T09 (editor/Start 90,
   properties with a toggle 52). The visual check allows a gap above 40 only for panes <= 480 and
   fails any push at 900/1600, any overlap, and any palette displaced from its frame.
Trade-off: at 900 the first editor and a docs-style properties table are narrower by about 290 px
(the toolbar width) while open; the user asked for a uniform gap over a uniform width.

## Tests and pre-change failures
- Unit (firstClearance, 11 tests, 7 new/rewritten): beside column, narrowed editor (inset 292),
  narrow-pane push (52), Start button own rectangle, hidden Start button, properties no
  control/toggle/badge, no clearance when toolbar ends above 40, scrolled content top; plus CSS test for
  the inset rule. Pre-change (HEAD source with the new tests): type errors (no `inset`) and 7 failures
  (6 firstClearance, 1 previewStyles).
- Visual: 54 `first-element-gap-*` scenarios (was 22). Pre-change failures on HEAD, e.g.
  `[edit:Start writing] the gap is 90.0px, expected 40px +-4` (empty 900, dark 900),
  `[read:properties] the gap is 90.0px` (properties 900, read and edit), `[editor:element] the gap is 90.0px`
  (paragraph 900/full 900), paragraph-460 failed too. 1600 passed except for the new palette check
  (palette 85.8 px). Existing assertion changed: the old T09 `check_first_element_gap` ("gap = 40 +
  measured clearance") is replaced by the uniform rule above; the old rule encoded the behaviour
  being replaced. Tolerance is 40 +-4 (brief), previously +-2.
- Defects found by the gates and fixed: a hidden Start button counted as first element (editor
  overlapped the toolbar in `edit-empty-document-enter-opens-editor`); an oscillation in the
  properties measurement hung the trusted integration run (renderer OOM in the boolean scenario,
  killed by me, no process left): positions are now taken relative to the table and updates are
  rate-limited (200 per second); first-block palette `inset-block-start` overrode the small-pane rule
  (displaced 94 px) so overrides were added.
