## 2. The product fix

- **Where `focusAtOpen` is set.** `state.activeBlockEdit` is assigned in one place only
  (`blockEditor.ts:289`), so every editor records `focusAtOpen`.
- **Where the change applies.** Only the focus call of the raw textarea changes. These paths are untouched:
  - the error and refused-open path;
  - `tableRowMove.receiveSource`, which returns before the check;
  - the table-cell input.
- **A second source cannot reach the check.** It returns early on `edit.textarea`.
- **The normal path is unchanged.** When the focus is on the body, on the clicked block, or on the element
  that held it at the open, the textarea is focused as before. A unit test covers this.
- **Keyboard and navigation flows.** These were checked by reading the code.
  - Arrow navigation between editors: the old textarea is either still the focused `focusAtOpen`, so it is
    equal and the new textarea takes the focus. Or it has been removed, so the focus is on the body and
    the new textarea takes it too.
  - A click while the find field has the focus: either the browser blurs the field to the body, or the
    field is still `focusAtOpen`. In both cases the textarea takes the focus, as before.
- **The three edge cases:**
  - **Stale element:** only an identity compare is made, so a stale element has no effect.
  - **Detached node:** a detached node cannot be `activeElement`, so it has no effect.
  - **The editor's own textarea:** `edit.element.contains` covers it, because the textarea is appended to
    `edit.element`.
- **Nit, not blocking.** `focusMovedToAnotherField` uses `edit.element.contains` and not
  `editorChrome.frameContains(edit, …)`. The palette host sits outside `edit.element`. It cannot hold the
  focus at that moment, because it is built in the same call, so this changes nothing today. It would only
  make the helper consistent with the blur handler.
