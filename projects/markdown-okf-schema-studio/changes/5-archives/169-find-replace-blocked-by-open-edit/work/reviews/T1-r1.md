# T1 review, round 1 (inspector)

Verdict: **CHANGES REQUESTED**. The diagnosis is right, and the test change is clean and deterministic.
But it hides a race in the product: a user can hit the same race and get it written into their document.
Rule 12 says to fix that kind of race in the product. Doing so also gives the headless check that fails on
main, which task.md asks for. The driver or the user may decide to scope the product fix out. In that case,
file it in the backlog and treat items 2–4 below as the only ones left.

## 1. Diagnosis (code reading)

The coder's diagnosis is confirmed, and the evidence is stronger than the stated 75%.

- The suite runs the test in edit mode.
  - `blockActionsFollowSelection.test.ts:97-102` turns edit mode on.
  - `pinStoredWorkspaceChoices` does not reset it.
  - Each new preview starts in the stored mode (`rendering.ts:162`, `initialEditMode: choices.editMode === true`).
- In edit mode, a click on `h1` opens the editor right away:
  - `pageInput.ts:208` → `openMappedEditor` → `openBlockEditor`.
  - `state.activeBlockEdit` and `data-sphinx-preview-block-editing` are set at once, then `previewEditOpen` is posted.
  - From that moment, `replaceBlockedReason` (`runtime.ts:310`) refuses replace.
- The textarea arrives with `previewEditSource` and calls `focusTextControlAtLastContent` without any
  condition (`blockSourceEditor.ts:396`). It takes the focus from whatever holds it, including the find field.
- The two outcomes:
  - **Cmd/Ctrl+F after the source arrived:** the textarea keeps the key (`findBar.ts:560`, `if (editing) return`).
    The find bar then opens through the host command. The textarea blur saves the unchanged text and closes
    the editor, so replace is allowed. This is the green path.
  - **Cmd/Ctrl+F before the source arrived:** the page opens the find bar with no textarea in place. The source
    then arrives and takes the focus.
    - If "studio" was still being typed, it goes into the source. This is run 1, "match count".
    - If the source came after the count, the editor stays open. This is run 2, "aria-disabled ... Save or cancel the open edit".
- Why it showed in the dark step only:
  - The old dark step pressed the shortcut right after the click, with no wait at all.
  - The cream step waited once for `document.hasFocus()` first. That extra CDP round trip usually gave the
    source time to arrive.
  - Compiled lines 227/228 are both in the dark step, so both runs match this.
- **#181 is correctly ruled out.**
  - The only product change in b71fac7c..eca17c42 is CSS on `.sphinx-preview-table-menu` (`editModeStyles.ts`).
  - That menu is created only inside a table-cell editor (`tableCellEditor.ts:234`), and the find test never
    opens one. Its table is never clicked.
  - A CSS-only change cannot alter this sequence. The race was already there, and the timing simply varied.
- Other paths I checked and ruled out:
  - **An earlier test leaving an editor open:** not possible. The find test opens a new document in a new
    preview, and `closePreview()` disposes it before the dark step.
  - **Panel reuse:** no effect, since `openPreview` waits for a new render of `notes`.
  - **A late navigation (`pendingBlockNavigation`):** only applies to the same document.

## 2. The fix

- The readiness signals are deterministic:
  - the textarea inside `[data-sphinx-preview-block-editor]` holds the focus;
  - then Escape;
  - then no `data-sphinx-preview-block-editing`, no editor, and the frame keeps the focus.
- No assertion was removed or weakened. `waitFor` becomes `settle` with the same predicates and timeouts.
- The new checks:
  - an assertion that the find field has the focus in the dark step;
  - `assertReplaceAllowed`, which fails fast with diagnostics instead of a 30 s Playwright click timeout.
- None of the forbidden fixes: no sleep, no retry loop, no `force`, no raised timeout, no skip. The `before`
  phase keeps its old screenshot-only sleeps, which are unchanged.
- **Escape on an unchanged editor does not save.** The path is `blockSourceEditor.ts:388` →
  `finishEditorWithSelection("cancel")` → `cancelBlockEdit` → `closeBlockEdit(hasAutosavedChange === true)`.
  It is `false` here, so neither a save nor a cancel is posted, and the editor is removed in the same call.
  - The host keeps `pageEditorId` until it needs to wait for the editor. It then sends `previewEditorWatch`,
    and the page answers `previewEditClosed` (`hostHandlers.ts:13-17`). This is the normal user path.
  - The h1 block is left selected (`selectBlocksNow`). This does not affect Cmd+F, the fold toggle or replace.
- **The toggle click when edit mode is off is not a hidden retry.** It is one conditional click followed by a
  wait on the state. It is the same pattern as `checkboxToggle.test.ts:191`, and the other tests even wrap it
  in a retry loop.
  - It does store edit mode on. In the full trusted suite edit mode is already on at this point, so nothing
    changes.
  - Run alone (`STUDIO_REAL_INPUT_SCENARIO=find-in-preview`), the run ends right after the test, so no later
    test sees the stored mode.
  - It does make the precondition explicit: the test now always runs in edit mode, where before it depended on
    the order of the suite. Acceptable.

## Requested changes

1. **(Main) Fix the product race, or have it scoped out explicitly.**
   - Today, a user who clicks a block in edit mode and quickly presses Cmd/Ctrl+F gets their search text typed
     into the Markdown source. That text is autosaved, so the document changes. Run 1 is exactly this case.
   - Rule 12 says "when the product itself misbehaves ... fix the product".
   - Two possible fixes:
     - (a) `receiveBlockEditSource` does not take the focus when it has moved since the open to a control
       outside the editor, such as the find field; or
     - (b) `find.open()` cancels a block editor that is still loading (no textarea, nothing changed).
   - Add a page unit test in `test/page/`. The `runtime*.test.ts` files already send `previewEditSource`. The
     test does: open editor → open find → deliver source → the find field keeps the focus or the editor is
     gone. It fails on main, which meets the DoD line "a unit/headless check that fails on main".
   - Keep `focusPageWithoutEdit` as the test's explicit precondition.
   - If the driver or the user scopes this out, file a backlog item and record it in the report.
2. **(Minor) `pageEditorOpen` in `pageState` stays `true` after an unchanged Escape**, until the host sends a
   watch. Say so in the comment, so the next reader of a failure does not take it for an open editor.
3. **(Minor) Two waits still use plain `waitFor` without page state:**
   - "the host's final replace answer" (line 262), which has its own `.catch` with less detail;
   - "the rendered preview" in `openPreview`.
   Moving the first one to `settle` costs nothing.
4. **(Open point, not blocking) Rule 12 also asks for the stress list.**
   - `test/shared/stressPlan.ts` and `realInput/run.ts` only cover real-input scenarios, and this test is in
     the trusted suite.
   - The request says the stress verdict is "reported, not fixed here". The driver's report should say that
     find-in-preview is not under stress, with a backlog item if wanted.
