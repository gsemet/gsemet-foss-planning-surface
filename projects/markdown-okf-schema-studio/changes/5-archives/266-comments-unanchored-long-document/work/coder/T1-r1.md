# T1 round 1 report (CR 266)

## Root cause (evidence, not length)
- Host side is fine on the real README: I rendered README.md (267 lines, raw HTML div/picture, images, tables) with the real
  pipeline, took every block and every single text node as a quote, and ran `reanchor`: 0 orphans for commentable text
  (only code blocks, which comments never target). MAX_CANDIDATES / MAX_FUZZY_TEXT (2 000 000) are not reached: README plain
  text is 10 009 characters. `commentMarkers.ts` only handles inline HTML comment chips, not sidecar threads. No deferred or
  chunked rendering exists on the comment path (`contentPatch` re-runs `commentThreads.apply()` after each patch).
- Page side is the cause: the compose box stores the selected text with whitespace collapsed (`collapse(selection.toString())`),
  but a source paragraph, list item or cell wrapped over several lines keeps the line break inside its rendered text node
  ("alpha beta\ngamma delta"). `attach()` in `src/page/modules/commentThreads.ts` used `value.indexOf(quote)` (and the
  collapsed quote), so a quote holding a space where the node holds "\n" was found in no text node: no highlight, only a badge on
  the block. Experiment: 35 of 170 single-node quotes of README.md failed; all 35 (and none of the other 135) came from text nodes
  containing a "\n". The README wraps every paragraph at about 80 columns, a short test document does not; that is why it looked
  like a length problem.
- Fix: `locate()` in commentThreads.ts matches a whitespace run of the quote with any whitespace run of the node (regex, words
  escaped), used for the single-occurrence count of moved threads, for the mark position and for the mark length.
  Unplaceable threads keep the existing badge / Orphaned box behaviour; the host and anchoring.ts are unchanged.
