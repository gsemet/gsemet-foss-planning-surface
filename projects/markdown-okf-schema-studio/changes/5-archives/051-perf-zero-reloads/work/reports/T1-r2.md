## Fix per finding

### 1. MAJOR: preview stuck on the old document after a switch with an unchanged editor open

- **Fix:**
  - `switchPreviewDocument` (same-root branch) now calls `editLock.forgetPage()` and clears
    `watchedPageEditorId` before it renders the new document.
  - `forgetPage` forgets the page editor and discards all queued work. A deferred `render-result`
    frees its stage. It keeps the host lock if a final save is still being applied.
  - The old document's work is dropped, not run. The queued `theme-render` closure captures the old
    document, and the new document renders with the current theme anyway.
  - The page answers `previewEditorWatch` by editor id, whatever the document id.
  - The host accepts `previewEditClosed` by editor id only. `closePageEditor` ignores an unknown
    id, so this is safe.
- **When the switch does not happen** (the reader switches A→B→A quickly, so the target is the
  current document): after the flush, the host re-posts the watch for the open page editor. The
  page answers at once if the editor is closed. If it is still open (for example after a refused
  save), it answers when the editor closes.
- **Not in the `previewEditFlushed` handler:** this replaces the reviewer's "close in the
  `previewEditFlushed` handler". A blind close there would run the old document's deferred render
  just before the switch. It would also let renders destroy an editor that stays open to show a
  save error.
- **Finding:** in a real window the reported freeze does **not** happen on a256ef9.
  `switchPreviewDocument` always calls `showPending(preview, true)`, which assigns a pending status
  document. `assignWebviewHtml` then calls `closePageEditor` (`extension.ts:899-903`), so the
  result was not deferred.
  - I wrote a real-window scenario (open an editor, type nothing, switch tab, expect "Second body."
    in the page). It **passed on a256ef9**. Markers showed 4 page loads during the switch.
  - Per rules.md (new tests must fail on the unchanged code), I removed it.
  - What the fix does change in practice: that assignment used to **run** the old document's
    deferred work (its result and its theme render) right after the switch. Now that work is
    dropped. Future changes that stop assigning a status page on a switch are covered by the unit
    tests below.

### 2. MINOR: real-window typing redrew 8 Mermaid diagrams once

There were two causes.

1. **Probe bug.** In the real-window probe, the first typed key landed at offset 0, not at the
   end. The selection set through the API had not reached the editor yet. The `a` broke the
   frontmatter (`a---`), so every block number shifted (`source-block-1` became
   `source-block-8`). All 504 blocks were rebuilt and the 8 diagrams redrawn, which was correct
   for that edit. The probe now moves the caret with the keyboard, repeating until the extension
   host sees it at the end, and asserts that the typed text is at the end of the chapter.
2. **Real key mismatch, found while checking.** When VS Code's webview loader shows a page, it
   gives every link without a title its `href` as title (`toContentHtml` in
   `/Applications/Visual Studio Code.app/.../webview/browser/pre/index.html:862-869`). Content
   patches do not go through the loader. So on the first patch, every block of the first page
   that holds a link missed its key and was rebuilt. A Mermaid figure with a link in its caption
   was redrawn too.
   - Fix: `morphKey` removes an `<a>` `title` that equals its `href` from both keys. A title the
     host wrote itself that differs from the link target stays in the key.
   - The probe chapter now has a link per section, and the windowless probe loads the first page as
     the VS Code loader would.

### 3. NIT: an older-theme Mermaid render overwriting a newer one

- **Fix:** `showImage` and `showMermaidError` run only when `drawnKeys.get(diagram) === key`. The
  drawing is still stored in the cache.
- **No test:** passes are already serialised through `renderQueue` (each pass waits for the
  previous one), so no test can fail on a256ef9. The guard is defensive.

## Autonomous decisions

- **The old document's queued work is dropped on a switch, not run.** Running it would refresh the
  old document (the `theme-render` closure) or apply its result after the host had moved on.
- **No blind close in the `previewEditFlushed` handler.** The host re-posts the watch when the
  switch does not happen. This is exact (the page answers by editor id) and keeps an editor that
  shows a refused-save error.
- **`previewEditClosed` is matched by editor id only**, like `previewEditFlushed`. An unknown id
  changes nothing.
- **I removed the round-1 assertion "a watch for another document is ignored"**, because it is the
  behaviour the finding removes.
- **I dropped the real-window switch scenario**, because it passes on a256ef9 (rules.md).
- **`morphKey` normalises only `<a title>` equal to `href`**, which is exactly what VS Code's
  loader adds. Both keys go through it, and the page's DOM is not changed. Patched links still get
  no loader title, as before.
- **The probe fixture gained 80 external links** (`https://example.com/...`, never fetched), so the
  probes see VS Code's link titles. The fixture grew from 93 KB to 99 KB, and the a256ef9 numbers
  were re-measured on it.
- **Real-window probe caret:** the probe presses the key again until the extension host reports the
  caret at the end. This is a state check, not a fixed sleep.
