## 1. Root cause: plausible and traced

- **VS Code loader timing, verified in the installed product.**
  `.../webview/browser/pre/index.html:1172-1179`: `hookupOnLoadHandlers` arms a 200 ms
  `setTimeout` that calls `onLoad`, which flushes `pendingMessages` (lines 1162-1165). After that,
  messages go straight to the active frame (lines 1264-1273). Nothing waits for the document's
  scripts. A runtime loaded via `<script src>` (`src/preview/webview.ts:80`, `:260-264`) can
  therefore miss messages that an inline script would not.
- **The listener is installed before ready.** `window.addEventListener("message", …)` is at
  `src/webview/scrollSync.ts:5288`. `postPreviewReady()` is the last statement of the runtime
  (`:5653`). So a host answer to `previewReady` always finds a listener.
- **The failure matches.** The CI log shows the button `disabled` with "No text editor shows this
  file", which is `applyPairing(false)` (`scrollSync.ts:1221-1231`). That is the value baked from
  `context.pairedTextEditor` (`:5248`), never corrected afterwards.
- **The ids are correct.** The ready path reaches the handler only after
  `matchesCurrentPreview(preview, value)` (`src/extension.ts:4208`). So the ready identity equals
  the stage identity that `notifyPairing` (`:4669-4680`) and `notifyTheme` use, and it passes the
  page's `sameContext` (`scrollSync.ts:678-682`). The values are live:
  `visibleEditorFor(preview)` and `activeColorTheme.kind` at handling time (`extension.ts:4693-4696`).
- **No other pre-ready state is lost.** I checked the other messages a page can receive:
  - Content patches are gated on `readyRequestId === stage.requestId` (`pageHasStage`,
    `extension.ts:1085`), and so is the properties-table patch (`:1015`). They are never posted to
    a page that has not reported ready.
  - The pending overlay, history state, show-comments, incoming changes, comments and the
    selection marker are all re-sent from the ready handler (`extension.ts:4303-4327`).
  - Pairing and theme were the only gap.

## 2. Determinism

- **Deterministic.** The fix uses the page's own readiness signal (`previewReady`). It adds no
  sleep, no retry and no raised timeout.
- **Nothing else changed in the tests.** The integration suite is untouched, and no assertion was
  edited or removed.

## 3. Unit test (`test/webview/scrollSync.test.ts:5816-5832`)

- **Meaningful.** It runs the real runtime unpaired and never dispatches the "lost" messages. It
  builds the answer from the page's real `previewReady` through `pageLiveStateMessages`, and it
  asserts the enabled state, title, aria-label and theme attribute.
- **Would catch broken builder logic.** Wrong or missing ids would fail it, because `sameContext`
  drops the message. So would a wrong field name or a missing `themeChanged`. On unchanged code it
  fails only because the module is missing, but the body does exercise the behaviour.
- **Gap, nit.** The wiring at `extension.ts:4317` is not unit-tested. No `vscode` host harness
  exists for the unit layer. The real-window suite covers it, though not deterministically on a
  fast machine. Acceptable.

## 4. No re-render or loop

- **Host side.** `postPageLiveState` only posts (`extension.ts:4689-4699`). It does not call
  `refreshPreviewDocument` or defer `theme-render`, unlike `notifyTheme`.
- **Page side.** `applyPairing` → `applyAnchorMode` and `applyTheme` are attribute writes that
  post nothing (`scrollSync.ts:1172-1177`, `:1208-1231`). Neither triggers another `previewReady`.
- **Cost.** Two small idempotent messages per ready, including after each content patch.

## 5. Quality and consistency

- **Consistent.** The new module follows the existing pattern of `vscode`-free helpers in
  `src/preview/` (`contentPatch`, `flushWait`, `previewMessages`). The comments are accurate and
