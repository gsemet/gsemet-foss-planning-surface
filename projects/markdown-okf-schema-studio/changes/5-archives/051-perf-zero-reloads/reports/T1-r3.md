## Failure

The heavy CI `integration` job (run 40011969386, job 120614352515) failed in
`test/integration/scroll-sync-suite.ts`. The six `solo-*` scenarios passed. Then the suite opened
a fresh preview in group Two and the fixture as text in group One. The anchor button stayed
`disabled`, with the title "No text editor shows this file", and the first `paired-*` click timed
out after 30 s.

## Root cause

This is a regression of PERF-11 (the runtime loads as a file), not of the content patch path.

1. **The page reads the pairing from its render's context.** `updatePreview` writes
   `pairedTextEditor: visibleEditorFor(preview) !== undefined` into the context
   (`src/extension.ts` ~1203). The runtime applies it once at start
   (`src/webview/scrollSync.ts:5248`, `applyPairing(context.pairedTextEditor !== false)`).
2. **Later changes come only as messages.** A pairing change after that comes only from
   `onDidChangeVisibleTextEditors` → `notifyPairing` → `previewPairing`. A theme change works the
   same way, with `themeChanged`. Nothing sends the state again later.
3. **VS Code can deliver queued messages before the runtime listens.** Its webview loader
   (`/Applications/Visual Studio Code.app/Contents/Resources/app/out/vs/workbench/contrib/webview/browser/pre/index.html`)
   does this:
   - It writes the new document.
   - `hookupOnLoadHandlers` arms a **fixed 200 ms timer**.
   - `onLoad` then promotes the frame and posts the `pendingMessages` (lines ~1150-1166).
   - The timer does not wait for the document's scripts. A message that arrives later goes straight
     to the active frame (lines ~1264-1274).
4. **Before this CR**, the runtime was an inline `<script>`. It ran during `document.write`, so it
   always listened before the timer fired.
5. **With PERF-11**, the runtime is `<script src=".../out/bundle/preview.js">`
   (`src/preview/webview.ts`, `injectRuntimeFile`). On a slow runner, the fetch through the
   webview service worker takes longer than 200 ms. Every message posted between the html
   assignment and the runtime's listener is then delivered to a document with no listener, and is
   lost.
6. **How the suite hits it.** It waits only for the host's queue phase `ready`, not for the page.
   It then calls `showTextDocument` at once. So `previewPairing { pairedTextEditor: true }` falls
   in that window. The page keeps the `false` it read from its context, and no later message
   corrects it. A content patch does not carry pairing (`runtimeContextSettings` leaves it out),
   and before T34 a full reload re-baked it.
7. **Why it passes locally and on main.** Locally the bundle loads in well under 200 ms (the suite
   passes locally on HEAD too). On main the runtime is inline.

The same loss applies to `themeChanged`. The patched page keeps the theme kind of its first
context, because `themeKind` is not part of the patch either. I fixed both, since they share one
cause. Other pre-ready messages were already safe, because the host re-sends them on ready:
history, comments, pending overlay, incoming changes and the selection marker.

## Fix

The host answers every `previewReady` with the live state. The page posts `previewReady` only after
its `message` listener is registered, at the end of the runtime and after each content patch. So
the answer always arrives, and it reflects `visibleEditorFor` and the theme at the moment the host
handles it. Any change announced before the page listened is covered, by construction. There is no
timing, no retry, and no extra page load.

- `src/preview/pageLiveState.ts` (new, no `vscode` import): `pageLiveStateMessages(ready, live)`
  builds `previewPairing` and `themeChanged`, addressed to the identity the page reported in its
  ready message.
- `src/extension.ts`: the ready handler calls `postPageLiveState(preview, value)` next to
  `postHistoryState` (line 4317). `postPageLiveState` (line 4689) posts the messages with the
  current pairing and `activeColorTheme.kind`. It only posts state. It does not render.

`applyPairing` and `applyTheme` are idempotent attribute writes, so the extra messages after each
ready are harmless. They make two small messages per page ready.

## Autonomous decisions

- **The fix is "answer ready with live state", not "carry pairing in content patches".** The patch
  path was not the cause. A page loaded fresh can lose the message too.
- **`themeChanged` is in the same answer.** It is the same loss, and it is a state-only message.
  The answer does not trigger the theme re-render.
- **No change to the integration suite or the stress plan** (see Tests).
