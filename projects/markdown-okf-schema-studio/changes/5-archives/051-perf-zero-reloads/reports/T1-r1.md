### Host design (STAB-03)

- `EditLock` now knows the **page editor**. `previewEditOpen` marks it open; the host learns of an
  editor before its first autosave, which was the gap.
- While a page editor is open, these all wait:
  - a finished render (`render-result`; a newer outcome replaces the older one and frees its
    stage);
  - a failed render's status document;
  - the theme render (`theme-render`);
  - the save, dependency and PlantUML work (already deferred).
- When work waits for an editor, the host posts `previewEditorWatch {documentId, editId}` once per
  editor. The page answers `previewEditClosed` when that editor closes, or at once when it is
  already closed. A new registered message is validated on `editId` and gated on `documentId`
  only, like `previewEditFlushed`. Without a watch, a close stays silent, so the existing "closes
  without a message" tests are unchanged.
- An explicit Refresh (the command or the toolbar button) still replaces the page, as before
  (`forceNextResult`). The real-window lock scenario in `previewEditing.test.ts` relies on that.
- A deferred result older than the page's stage is dropped. Disposal and missing-source drop a
  deferred result, and a full assignment forgets the page editor.
- Host edit error paths (`releaseHostEdit`) keep page work waiting while the editor still shows
  the error.

## Open points

- **Behaviour change to review:** while an inline editor is open, typing in the text editor no
  longer updates the preview until the editor closes. This is what "no reload during edits" asks
  for. A real-window test that types in the text editor with a preview editor open would now wait;
  none of the trusted suite does.
- An editor that is opened but not yet saved has no host range. After an outside change, its first
  save gets the explicit error "The preview is stale. Reopen the block before saving." instead of
  being rebased. Only edits the host already holds are rebased.
- Real-window typing still draws 8 Mermaid diagrams once over the 10 patches; the windowless probe
  draws 0. Likely cause: one patch whose diagram host HTML differs from the first page's (for
  example a resource URI or a deferred enrichment pass), so those blocks do not match their keys
  once. Worth a look in round 2.
- The standalone suite and the reload campaign were not run in a real window.
- The `node_modules` and `.venv` entries in `git status` are symlinks to the main checkout that
  were already in the worktree. `.gitignore` ignores `node_modules/` (a directory pattern), not
  the link, so they must not be committed.

## Autonomous decisions

- **Watch protocol instead of always reporting closes.** The page always posting `previewEditClosed`
  broke 11 existing "closes without a message" tests. So the page reports a close only after the
  host sent `previewEditorWatch` for that editor.
- **Explicit Refresh bypasses the deferral.** The reader asked for it, and the existing lock
  scenario expects it.
- **Failed-render status documents also wait for an open editor.** Otherwise a failing render
  would destroy the editor just as a successful one used to.
- **Stale and error status documents outside editing are still assigned**, because of the RI-T34
  nonce test (PERF-05 step 1 is not extended to them).
- **The scroll budget criterion uses the 4x slow-CPU p95** (< 4 ms), as well as normal p95, in the
  windowless probe.
- **The probe's theme change sets new colour variables on the page body.** The page's forced theme
  modes set these variables on `html` and `body` themselves.
- **No lazy Mermaid rendering and no sequential rendering**, to keep screenshots unchanged.
- **The inline runtime path is kept when no `extensionUri` is given** (visual fixtures), so the
  visual baselines did not have to change.
- **The baseline scratch copy was made a throwaway git repo** (outside the project), because the
  integration runner needs `git rev-parse HEAD`.
