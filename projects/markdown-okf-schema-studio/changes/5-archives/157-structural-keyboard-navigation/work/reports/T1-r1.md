## Deviations from the design plan / decisions
1. Cell ring is NOT hidden by a pointer move (the block ring is, via `actions-owner=pointer`). The capture harness parks the mouse at the end, which hid the ring in the screenshot; a cell is not tied to the block actions anyway. docs line "moving the mouse hides the keyboard selection ring" still describes the block ring.
2. Selecting a cell or an inner block keeps the top-level block selection active on the ancestor (so Escape/clipboard/restore logic stays coherent) but moves the outline to the inner element/cell; any top-level re-render resets the structural cursor.
3. Up/Down on an inner block (not specified) move among siblings of the same parent and stop at the edges; at top level they stay the existing flat behaviour. Rows with fewer cells clamp the column on Up/Down.
4. Right with nothing selected (page focused) selects the first non-included block ("first child of the document"), not the top-visible one.
5. Announcement of a cell: "Table cell row R, column C selected"; inner blocks reuse "1 block selected".
6. Enter on a cell/inner block is taken by the structural listener (stopImmediatePropagation) because the page input would otherwise open the whole table; it calls `openMappedEditor(tableBlock, cell)`, the click path.
7. Real-window: no plain-key scenario existed in blockKeys.ts, so the step (ArrowDown to the table, Right, Right, Escape; asserts cell focus attribute and no editor) was appended to `scenarioBlockSelection`, with a table added to its document. No new capture/registry entry. Unverified by running.
8. No `depends_on` on BLOCK-253 (optional; BLOCK-004/140 are cited in the body).
