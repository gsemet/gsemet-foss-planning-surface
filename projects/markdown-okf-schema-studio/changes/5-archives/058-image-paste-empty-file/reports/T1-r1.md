## Root cause

All the paths that write the file before its bytes are complete:

1. Page (`src/page/modules/pasteImage.ts`): reads the clipboard file as base64 and posts
   `previewPasteImage`. It inserts `![image.png](image.png)` only on the host's `ok` answer.
   This path is correct.
2. Host (`src/session/features/hostRequests.ts` `handlePasteImage`): `readDirectory`, then
   `nextImageName`, then `host.files.writeFile(final path, bytes)`, then the `ok` answer. The
   answer comes after the write resolves, so this ordering is also correct.
3. Adapter (`src/host-vscode/vscodeHost.ts`): `vscode.workspace.fs.writeFile(uri, data)`. VS Code
   1.143's extension host serves `file:` locally and calls
   `provider.writeFile(uri, content, { create: true, overwrite: true })` with no `atomic` option.
   The bundled `DiskFileSystemProvider.doWriteFile` (read from
   `/Applications/Visual Studio Code.app/.../extensionHostProcess.js`, 1.143.0) does
   `s = await this.open(e, { create: true, ... }); await this.write(s, 0, n, 0, n.byteLength)`,
   and `open` does `ht.open(path, "w")`. The file therefore exists **empty** from `open` until
   `write` completes, which takes several awaits on the libuv thread pool. The atomic branch,
   `doWriteFileAtomic` (temp file plus rename), runs only when `opts.atomic.postfix` is passed,
   and the API never passes it.
4. Test (`test/integration/realWindowGaps.ts` `scenarioImagePaste`): it polled
   `fs.existsSync(image.png)` every 25 ms **in the same extension host event loop**, then read the
   file at once. When a poll fell between `open` and `write`, it saw the empty file. This is a
   1-in-N timing window, which matches 3 passes and then a failure on a loaded runner.

The product exposes the gap as well. While the write runs, any reader (a watcher, Git, an image
viewer, a preview reload) sees an empty `image.png`. A failed write (disk full, permissions) leaves
an empty or partial `image.png` behind. The name is chosen from a `readDirectory` snapshot, then
`writeFile` overwrites, so a file that another writer created in between was silently replaced.

## Fix

- `src/session/features/hostRequests.ts`: new `writeNewFileAtomically(files, folder, name, bytes)`.
  It writes to a hidden `.<name>.<random>.partial` file in the same folder, then
  `rename(partial, final, { overwrite: false })`. If anything fails, it deletes the hidden file in
  a `finally` and the page gets the reason. The final name only appears complete, so a reader never
  sees partial bytes. A name that another writer took in between is kept, and the paste is refused
  with the error. `handlePasteImage` uses it, and the `ok` answer (the page's readiness signal)
  still follows the completed rename.
- `FileSystem` port (`src/host-api/fileSystem.ts`): new `delete(path)`. It is implemented in the
  VS Code adapter (`workspace.fs.delete`, no trash, not recursive), the Node file system (`unlink`)
  and the memory file system (ENOENT when missing).
- `test/integration/realWindowGaps.ts`: the scenario no longer polls for the file to exist. It
  waits for the reference in the editor, which the page inserts only on the host's `ok`, sent after
  the rename. It then reads the file. The same assertions remain: exact bytes, then the commit and
  the buffer text. Failure messages now carry the expected and saved sizes (or "no file"), a
  listing of the folder with each entry's size, and the editor text. A timeout of the reference
  wait carries the same state. No sleep, retry or timeout change. The scenario stays in
  `test/shared/stressPlan.ts` (untouched).

`test/session/pasteImageWrite.test.ts` drives `HostRequestController` through its registered
`previewPasteImage` handler. It uses an in-memory folder whose `writeFile` writes the way VS Code
does: it creates the file empty, yields, records the visible images and their sizes, then writes
the bytes (or throws ENOSPC).
