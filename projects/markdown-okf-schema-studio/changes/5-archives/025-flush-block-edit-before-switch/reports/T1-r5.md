## Cause: product bug (race between the editor's blur save and the host flush)

`showTextDocument(second)` focuses the text editor, so the preview iframe loses focus and the open
frontmatter value editor gets a `blur` before the host's `previewFlushEdit` request reaches the page
(the request goes renderer -> extension host -> renderer, the blur is local). The blur handler calls
`saveValue()` as a **plain** save (no `flush` flag). For case 1 (`[unclosed`, invalid YAML) and case 2
(`just text`, valid YAML that does not fit the object schema) the host refuses that plain save
(`Invalid YAML value` / `stale or ... does not match the schema`). Meanwhile the page answered the
flush: `flushFrontmatterEditor()` returned early because `edit.saving` was true (the refused save was
still pending), so no flush save was posted, the host saw no pending save and switched document.
The typed text was dropped with the page and `waitFor(... meta value ...)` timed out.

Trace of the three cases:
- case 1 `[unclosed` (YAML textarea): blur plain save refused -> flush skipped -> lost. Failing case.
- case 2 `just text`: same path (schema refusal) -> would fail too.
- case 3 emptied number: the plain save stops page-side ("Enter a valid number.", `saving` stays false),
  so the flush then posts `fieldValue: ""` with `flush: true` -> written as `count: ""`. Works.
- Scenario d (title " more", valid) passed because the plain blur save is accepted.

The same race exists for a real pointer click on a link or on Back (the click blurs the editor first);
the integration tests use `clickWithoutBlur`, so they did not show it.

Test expectations are correct (checked with `createFrontmatterFieldPatch` on the fixture):
`meta: "[unclosed"`, `meta: just text`, `count: ""` all match the scenario regexes. No test changed.

## Fix (page side only)

- `src/webview/scrollSync.ts`: a plain frontmatter save (value and key editors) sets
  `edit.plainSavePending`; `receiveFrontmatterResult` clears it and runs `edit.afterResult`.
  New `flushOpenEditorsThen(navigate)`: flushes as before; if a plain frontmatter save is still
  pending, it waits for its result (bounded 1 s, below the host's 1.5 s `FLUSH_WAIT_MS`), then calls
  `flushFrontmatterEditor()` again (a refused save is re-posted with `flush: true`, an accepted one is
  not re-sent) and only then posts the navigation / `previewEditFlushed`. Nothing pending: unchanged,
  synchronous. The in-flight key-editor object also carries `save`/`cancel` so a refused key rename can
  be re-flushed.
- `src/webview/historyControls.ts`, `src/webview/linkNavigation.ts`: `beforeNavigate` now receives the
  navigation as a continuation (`beforeNavigate(navigate)`), so Back/Next and links wait too. Without a
  hook, or for same-page anchors, they post at once as before.
- Host code unchanged: it already waits for the answer (bounded) and then for tracked saves.

## Tests added (test/webview/scrollSync.test.ts), all 4 fail on HEAD and pass now
