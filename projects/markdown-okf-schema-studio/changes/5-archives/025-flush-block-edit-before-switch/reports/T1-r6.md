## Cause: test-input race (Cmd/Ctrl+A echo), not a product bug

The failing line is the `waitFor("the typed meta value ...")`. The stack has `realInput.test.js:3792`
called directly from the `withFlushDocuments` callback. A `waitForPreviewOf` failure would show that
function in the stack and say "the preview to show ...". It is case 1 or 2 (field `meta`). Case 3
says `count`.

This is the only place in the suite that types right after `${MOD}+a`, here at 5 ms per key.
RI-T06 and RI-T07 (realInput.test.ts:677-683, 743-745) already record the cause. VS Code forwards
Cmd/Ctrl+A to the workbench, and the workbench later echoes an asynchronous `selectAll` into the
webview. Keys typed before that echo get selected again, and the next keys replace them. RI-T06
saw `abstract` become `bstract`. Those scenarios wait 300 ms after the shortcut; this one did not.

So the textarea held only the tail of `[unclosed` (for example `losed`) when the tab switched. The
flush then wrote that tail as typed (`meta: losed`). `/\[unclosed/` can never match it, so the
wait timed out whatever the flush did. This also explains why the r5 page fix changed nothing. r5's
blur/refusal race is still a real path for a pointer click, and its unit tests hold, so I kept it.
It was not this failure.
