## Where it failed

Compiled `realInput.test.js:3818` is the r6 **select-all check** (`waitFor("... fully selected")`
-> `locator(item.selector).evaluate`), not the read-back after Backspace. Backspace was never
pressed. `waitForEditor` had seen exactly one visible `[data-okf-frontmatter-editor] input` (the
`count` number input). After `Mod+A` and 300 ms, the current frame had no such input, and
`locator.evaluate` waited 30 s. (The 30 s locator wait also outlasts the 10 s `waitFor`.)
Cases 1 and 2 passed, and so did screenshot 40 (`scenarioFlushBeforeTabSwitch`, a separate
earlier scenario) and `scenarioFlushCellAndFrontmatter`.

## Cause (from the code; CI cannot be run locally)

- Case 3 is the only `Mod+A` in a `type=number` input in the whole suite. Case 3 never ran in CI
  before r6, because the run stopped at case 1 or 2. RI-T06/T07 use `Mod+A` in a text input and a
  textarea only.
- The frame and the flow are the same as in case 2, which passed. Only the control differs. A
  re-render or a stale frame would hit case 2 as well.
- VS Code handles Cmd/Ctrl+A twice: natively in the webview, and then as an asynchronous
  `selectAll` echo from the workbench (`execCommand('selectAll')` on the frame document, RI-T06).
  A number input exposes no text selection (`selectionStart === null`). So the echoed select-all
  most likely does not stay inside the control: the page selection moves to the document and the
  input loses focus.
- The editor's `blur` handler then calls `saveValue()`. `Number("3")` equals the stored `3`, so
  `unchanged` -> `closeFrontmatterEditor()` removes the editor. This matches "the input is gone,
  the frame is alive".
- Product side: a blur on an unchanged field is meant to close the editor. The page
  (scrollSync.ts) has no Mod+A handler, and nothing in the frontmatter editor reacts to the key.
  This is a test-input artefact of the VS Code echo, not a CR 025 regression. A user who presses
  Ctrl+A in a number field may see the same close. That is an existing behaviour of the
  host/Chromium pair (see open points).

## Fix (test only, assertions unchanged)

test/integration/realInput.test.ts, `scenarioFlushFrontmatterKeptAsTyped`:
- Number case (`typed: undefined`): no `Mod+A`. The test reads the value length, presses `End`,
  then presses `Backspace` and `Delete` once per character. That empties the input wherever the
  caret is (macOS can ignore End in an input). The frontmatter control has no handler for these
  keys (only undo, Escape and Enter), and `homeEndInControl` is not attached to it.
- Text cases: unchanged `Mod+A` + 300 ms + select-all wait. The number-specific `null` escape is
  gone because only textareas reach it now.
- New helpers `flushEditorValue` / `flushEditorSelection` read the control through
  `frame.evaluate(querySelector)` instead of an auto-waiting locator. If the editor is gone, the
  test fails at once with the case, the step and `flushFrameState`, instead of a 30 s locator
  timeout.
- Unchanged: the read-back `assert.equal(held, typed ?? "")` (valid for a number input: `value`
  is `""` once emptied), the immediate `showTextDocument(second)`, and all three expected regexes,
  including `/^count:\s*(""|'')\s*$/m`. The host path for an empty number on flush is unchanged:
  `fieldValue = control.value` = `""` -> `count: ""`, as checked in r6.
