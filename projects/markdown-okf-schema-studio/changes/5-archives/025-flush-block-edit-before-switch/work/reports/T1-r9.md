## Failure

`case 2 (meta, typed "just text"): no [data-okf-frontmatter-editor] textarea after Control+A;
preview first.md (ready), frame {"editMode":"on","frontmatterEditors":0,"blockEditors":0}`.
`waitForEditor` had seen the textarea. 300 ms after Ctrl+A it was gone. The current frame was
alive, showed first.md with edit mode on, and had no editor open. Case 1 passed. The r8
previewHistory test also passed.

## Root cause: test sequencing (it clicked before the page reported ready). Not a flush bug.

- `waitForRender` checks the host side only: queue phase `ready` and the document version.
  `findCurrentFrame` matches the document id, version and request id written in the HTML. Neither
  of them waits for the page's own ready report (`readyRequestId` / `webviewReady`).
- After a document switch the host assigns the full HTML. About 150 ms later,
  `scheduleLinkEnrichment` (LINK_ENRICHMENT_DEBOUNCE_MS) runs `patchPropertiesTable`. If the
  page has not reported ready for the stage yet (`readyRequestId !== stage.requestId`), it calls
  `setPanelHtml` and reloads the whole page (extension.ts:888-901). The reloaded page keeps the
  same document id, version and request id, so it matches as the "current frame". It also gets
  edit mode back from the stored state, but no editor is open.
- Case 2 is the first case that runs right after a switch back (second -> first). Edit mode is
  already on, so the test clicks the cell at once. On slow CI the page had not reported ready
  when the enrichment fired, so the reload removed the editor that had just opened. Case 1 did
  not hit this: the preview was opened earlier, and `setEditMode` waits for a page round trip.
  The page was ready long before the click.
- This matches the observed state exactly (frame alive, `editMode: on`, 0 editors). The other
  explanation, a blur through the select-all echo closing an unchanged editor, does not fit. Case 1
  used the same textarea and the same Ctrl+A, and RI-T06/T07 pass with them.
- The flush path is not involved. No text had been typed yet, and case 1's flush and switch were
  correct: its text reached the document.

## Fix (test only, assertions unchanged)

test/integration/realInput.test.ts, `scenarioFlushFrontmatterKeptAsTyped`:
- After `waitForRender(first)` the test now also waits for `webviewReady === true`, which is when the
  page reports ready for the current render. It waits before it reads the edit mode and clicks the
  cell. After that report a deferred properties update is sent as a message, and the page holds it
  back while an editor is open (`deferredPropertiesMarkup`). So nothing can reload the page under
  the editor any more. The test waits for observable state, not for a timer.
- Diagnostics: `flushFrameState` now reports `page ready` and the number of full page loads
  since the editor opened (`htmlAssignments` minus a value taken right after `waitForEditor`). A
  reload under the editor now shows up directly in the message.
- Unchanged: the immediate switch after typing, the `assert.equal` on the held value, and all
  three expected regexes.
