## F1 detail: the refusals kept on a flush

- Stale field (`!field` / no document): the field no longer exists in the source, so no place to write. Real impossibility, but see R2-2 (the user is not told).
- Add with empty or padded name, rename to a duplicate key: writing would corrupt the YAML. Real impossibility; the least-loss is to keep the old key and tell the user (R2-2).
- Removal of a required field: a flush never sends a remove (only value and rename saves), so this refusal is unreachable from a flush. Not a loss.
- Rename with padded or empty key (`saveKey`, scrollSync.ts ~1823): the page refuses before posting and does not know about the flush. A key typed as `" foo"` is lost (R2-3).
- Frontmatter message dropped by `matchesCurrentPreview` when the stage moved (a render between typing and the flush): same pre-existing behaviour as blocks; rare.

`scenarioFlushFrontmatterKeptAsTyped` does go through the real path: `meta` is `object` with a schema, so `structuredValue` selects the YAML editor (`useYamlEditor`), and `count` is a number input. The only unproven parts are CI-only (selectors, written form `count: ""`). The reuse of the loop for three cases on the same doc is fine.

## New findings

### R2-1 MEDIUM (contradicts a binding decision): window close / Reload does not flush a frontmatter editor
00-request.md lists window close / Developer: Reload Window as a trigger ("all"). `pagehide` calls `flushPendingAutosave`, which only posts a pending block autosave. A frontmatter value editor has no autosave: its typed text exists only in the page and is lost on Reload Window or close (the test for pagehide covers blocks only). The report calls this a "documented limit", but the user decision does not allow that limit.
Fix: on `pagehide` (not on `visibilitychange`, which must not close the editor of a hidden-but-retained page) also call `activeFrontmatterEdit.save()` inside the `flushingEditors` guard (same code as `flushOpenEditors`), best-effort. Add a unit test: type in a frontmatter field, dispatch `pagehide`, expect one `previewFrontmatterSave` with `flush: true`. Also check that an open table cell with typed text but no pending autosave timer is covered by the same pagehide path (the timer check in `flushPendingAutosave` may skip it); if not, use `flushOpenEditors()` semantics for the cell too.

### R2-2 MEDIUM: a refused flush is silent
When the host refuses a flush save (stale field, duplicate key, `applyEdit` false), `postFrontmatterEditError` posts to a page that is about to be replaced. The user never learns the text was dropped, which is the data-loss the CR exists to remove.
Fix: when `message.flush === true` and the save is refused, also call `vscode.window.showWarningMessage` (or `setStatusBarMessage`) with the reason and the typed text if it is short. Cheap and keeps the "never block the navigation" rule.

### R2-3 LOW: key rename typed with leading or trailing spaces is lost on a flush
`saveKey` refuses `" foo"` before posting. During a flush, trim it (and keep the old key when the result is empty or unchanged); a duplicate key stays refused by the host (R2-2 reports it).

### R2-4 LOW: the link and Back scenarios do not reproduce a real pointer action
`clickWithoutBlur` is correct for what it claims: it asserts the caret is in a TEXTAREA/INPUT, `Locator.evaluate` + `dispatchEvent` does not move focus, and no document-level click handler commits the paragraph editor (the generic click handler at scrollSync.ts ~5128 returns early for links and only saves a table cell editor). The click is handled by the same `activate` (link: no modifier check in `linkNavigation`, so Meta/Ctrl is only needed for the edit-mode handlers at ~143-156, and the scenario passes it exactly as a real Ctrl-click does) and `go()` (Back). So the page flush ordering is truly the only save. But a real mouse click blurs the text box on mousedown and the blur commit saves first, so this exercises defence in depth, not a user path. Fine to keep; say so in the PR text and the scenario comment. The real race is covered by the tab-switch scenarios. Minor risk: a dispatched click on a disabled Back button is not delivered; `history` is enabled by then (typing takes longer than the state message).
