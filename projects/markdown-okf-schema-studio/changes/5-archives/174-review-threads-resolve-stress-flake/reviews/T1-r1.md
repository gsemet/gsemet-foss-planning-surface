## Coder's side finding: `CommentsController.post()` sets `state.textHash` too early

I read `src/session/features/comments.ts:132-209` and confirmed the finding. **It is a real latent
bug.**

- `state.textHash = hash` (line 145) runs before
  `await this.currentDocumentText(...)` (line 168) and its `sequence !== state.seq` check (line 169).
- Interleaving: post A reads the new sidecar and stores its hash, then awaits the document text.
  Post B enters, runs `++seq`, and reads the same sidecar. A resumes, sees that `seq` changed, and
  returns without posting. B computes the same hash: `hash === state.textHash` and
  `state.posted !== undefined` are both true, so B returns at line 144 as well. The page keeps the
  old threads until the sidecar text changes again.
- Two concurrent posts are the normal case after our own write. `update()` (line 435) awaits
  `this.post()`, and the sidecar watcher (line 381) fires another post for the same write.
- It cannot explain this flake:
  1. The scenario's document is open, so `currentDocumentText` returns `getText()` synchronously.
     The window is then a few microtasks. A watcher post enters by a macrotask and cannot land
     inside it.
  2. The symptom would be different. The popover would stay present and read "Resolve". The old
     test would then have failed by the 10 s `waitFor` deadline, not with a 30 s "no element"
     locator wait.
- It is reachable when the shown document is not open in an editor, because then
  `currentDocumentText` awaits `stat` and `readFile`.
- Fix: assign `state.textHash = hash` only after the last `seq`/`stage` check, just before
  `state.view` is set or the post is sent. Unit test: hold `readFile` of the document, start a
  second post, release the first, and assert that the second post reaches the page.
- Does it belong in this CR? **No.** It does not explain the flake. CR 174 is diagnostics-only and
  its traceability is scoped to the popover. The fix is a session behaviour change with its own
  SwRS-REVIEW-012 test. File it as its own backlog item (small, P3). Not blocking.
