## What the failing run proves (stress-b71fac7c.log)

- Round 9: `r05-thread-reply` was captured at 17:14:00.307. The failure was reported at
  17:14:31.694, which is 31.4 s later. Of that, 30 s is Playwright's own `locator.textContent`
  timeout. So the Resolve click, the "resolved thread in the sidecar" wait and the first (or an
  early) `textContent` call all finished within about 1.4 s of r05. In green rounds, r05 to r06
  takes about 220 ms.
- The call log says `waiting for locator(...)`, so for the whole 30 s **no element** matched
  `[data-okf-comment-popover] [data-okf-comment-resolve]`. If 2 had matched, Playwright would have
  raised a strict-mode error. If 1 had matched, it would have returned "Resolve" or "Reopen" at
  once. The sidecar held `resolved: true`, so the click did reach the page and the host.
- Conclusion: soon after the Resolve click, the popover element (or the page that held it) was
  gone and never came back.
- The log does not show whether the page was reloaded, which handler closed the popover, or what
  the host posted. No page or host state was printed.

## Every code path that removes the popover (src/page/modules/commentThreads.ts)

The popover is appended to `document.body`, outside `#sphinx-myst-preview-content`. A content
patch (`contentMorph.replace(main, ...)`) never touches it. No page module removes body children
or `[role=dialog]` generically (grep: nothing). The only removals are calls to `close()`:

| Caller | Can it explain this run? |
|---|---|
| `apply()` (`setThreads` on `previewComments`, and `initializeContent` after a content patch) | It reopens the popover whenever the thread is still in `threads`, because some holder always exists: the mark, else the badge, else the orphan entry. It loses the popover only when the posted list **lacks the thread** or is **empty**. The host posts `[]` only when the sidecar read gives `undefined` or no threads. Writes are atomic (tmp file and rename, `commentStore.ts` `writeAtomically`), so the reads in the run's states (1 or 2 comments, resolved) always find the thread. Not excluded, but no path found. |
| `pointerdown` outside the popover | The Resolve click lands inside the popover. Playwright's hit-target interceptor blocks a click whose target changed. Nothing else in the test presses after the click. Not excluded. |
| Escape keydown, toggle (click on the mark), `commentCompose` `beforeOpen` | None happen after the Resolve click in this scenario. |
| A page load (webview document replaced: `assignWebviewHtml`) | This loses all page state, the popover included. `withCurrentFrame` retries on the detached frame, then waits 30 s on the new frame, which matches the observed 30 s locator wait. Possible triggers: the patch-ack fallback (`armContentPatchFallback`, 2 s), `reportsReloadedDocument` (VS Code re-created the webview), or a status page. No trigger was found for this step: the sidecar write does not render (only `**/*.md` and `conf.py` are watched for renders), and the document is not edited. Not excluded. |

## Another race found while reading (not this failure, not fixed)

`CommentsController.post()` in `src/session/features/comments.ts` sets
`state.textHash = hash` **before** its later awaits and `seq` checks. A watcher post can be
overtaken by a newer post (`seq` changed) after it read the new sidecar. It then returns without
posting, but the hash is already stored. The newer post reads the same text,
`hash === state.textHash` holds, and it also returns. The page never gets the new threads.

This needs the older post to reach `currentDocumentText` with an awaited file read, which means
the document is closed. In this scenario the document is open (`getText()` is synchronous), so the
window is microtask-short. The symptom would also differ: the popover stays on "Resolve" and the
failure reads "Timed out waiting for the resolved state in the popover", not a 30 s locator
timeout. A unit test can reproduce it with `test/session/reviewReqComments.requirements.test.ts`:
hold `readFile` of the document, then post again. Fix: assign `textHash` only after the last `seq`
check. Proposed as a backlog item, not done here.

## Changes

1. `src/page/modules/commentThreads.ts`: new optional 4th argument `trace(event, detail)`, for
   diagnostics only; behaviour is unchanged. It records "comment popover closed" with the reason
   and the thread id when an open popover goes away: `pointerdown outside on <tag>`, `Escape`,
   `toggled`, `closed by the page` (compose), `re-apply without threads`, or
   `re-apply without the thread / a holder` (with the thread count). A re-apply that keeps the
   popover records nothing.
2. `src/page/runtime.ts`: passes the page editor trace (`pageDiagnostics.editorTrace.record` with
   `traceStack()`), so `window.__studioDiagnostics.trace()` lists these entries with their callers,
   next to the existing "page request" and "content patch" entries.
3. `test/integration/realWindowGaps.ts`: the last wait no longer uses `locator.textContent`, which
   blocked blindly for 30 s. It uses the existing `waitFor` with a non-blocking `frame.evaluate`.
   The condition is just as strict: exactly one `[data-okf-comment-popover]
   [data-okf-comment-resolve]` whose trimmed text is "Reopen"; the default timeout is unchanged.
   The wait is wrapped in `explained` (`previewDiagnostics`: host phase, request, page loads,
   content patches, page focus, page trace and its start time). A new helper `reviewThreadState`
   adds:
   - the sidecar threads (resolved, comment count);
   - the host counters before the click and now (`htmlAssignments`, `contentPatches`, comment
     posts);
   - the threads the host posted last, and its last `previewCommentResult`;
   - the page's request id, every popover (attributes, actions row `outerHTML`, text), the mark
     attributes, the compose box count, and `activeElement`.

   With this, the next failure tells the cases apart. A page load shows a higher page-load count
   and a new trace start time. An in-page close shows the trace entry and its caller stack. A
   missing post shows `posted` without the resolved flag.
4. `test/page/modules/commentThreads.test.ts`: new test "CR 174: the trace names what closed an
   open popover, and a re-apply that keeps it is silent" (`@tests_req SwRS-MDOKFSTUDIO-REVIEW-081`).

No SwRS change: no behaviour changed. No CHANGELOG entry: the change is diagnostics only and
invisible to users.
