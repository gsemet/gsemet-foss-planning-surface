## Findings (required)
1. The webview `localResourceRoots` narrowing (`src/session/features/rendering.ts`, `[]` for a
   read-only broad root) is the second half of the intent and has no test. The SwRS verification
   notes admit this. If `preview.readOnly` or the root check regressed, every test would stay green
   and the whole home folder would be readable again. Add a test that fails on the old code: a
   session-level unit test in the `test/session` style, or a case in `test/integration/untrusted-suite.ts`.
   The test should open a document in a temp HOME and assert that `localResourceRoots` has no
   home/document folder. I consider this required, not optional.
2. Home detection differs from the spec and from `os.homedir()`. The code prefers `HOME`, and
   `os.homedir()` on Windows prefers `USERPROFILE`. Under Git Bash/MSYS, `HOME` can be a different
   path from `USERPROFILE`, so the real home may be missed on Windows. Prefer `USERPROFILE` when
   `process.platform === "win32"`. Also fix the SwRS wording ("os.homedir() after realpath") to say
   what is really used. The report is right that `node:os` is forbidden in core, so alternatively
   inject the home folder from the session layer.
3. Case-insensitive file systems: `isWithin` is a case-sensitive string compare and `realpath` does
   not canonicalise case on macOS (APFS) or Windows. `/users/me/x` against `HOME=/Users/me` is not
   detected as being in the home folder. Compare with a lower-cased path when the platform is win32
   or darwin, or use `realpath.native`. Add a test for the Windows drive-root and trailing-slash
   cases if they are cheap (`path.parse(real).root === real` already covers `C:\`).
