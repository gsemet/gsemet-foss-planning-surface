## Findings

1. **Blocking: the hint-shown mark is erased at every page start, so the hint replays on refresh
   and reload of the same preview.** `src/page/modules/toolbarCollapse.ts:121` writes
   `viewToolbarHintDocument` into the webview state. Then `postPreviewReady`
   (`src/page/features/contentPatch.ts:148`) calls `rt.scroll.stateSnapshot`
   (`src/page/features/scrollCore.ts:43-68`). That call replaces the whole webview state with a
   fresh `PanelStateSnapshot` that has no `viewToolbarHintDocument` key. Refresh
   (`src/page/features/pageInput.ts:55`) and every scroll snapshot do the same.
   I reproduced it with the compiled runtime harness. After the first page load the state keys are
   `documentId, sourceFile, …, expandedChips` and `viewToolbarHintDocument` is undefined. A second
   page started from that saved state sets `data-sphinx-preview-toolbar-hint="true"` after
   `flushFrames()`. This breaks the user's decision 3 ("never on … a refresh, or a reload of the
   same preview"), SwRS-TOOLBAR-130 (row "a refresh, a reload … no hint"), the docs and the
   CHANGELOG. The unit test at `test/page/modules/toolbarCollapse.test.ts:120-126` passes only
   because it runs the module alone.
   Fix: carry the mark in `PanelStateSnapshot` (`src/page/features/pageRuntime.ts:410`) and write it
   in `stateSnapshot`, or keep it where the snapshot cannot overwrite it. Add a runtime-harness test
   (`test/page/runtime*.test.ts`) that starts a page, takes the ready snapshot, starts a second page
   from `getWebviewState()`, and asserts there is no hint. That test must fail on the current code.

2. **Medium (decision for the driver or user): the replay rule is keyed on the document, not on
   the preview opening.** `toolbarCollapse.ts:119-121` with SwRS-TOOLBAR-130 row "another document in
   the same webview → plays again". A preview that follows the active editor rebuilds its page on
   each switch (`src/session/previewManager.ts:455-494`). Once finding 1 is fixed, switching
   A → B → A plays the hint on each switch, because the key holds only the last document. The
   request asks for the hint on "every preview opening" and never on a reload of the same preview.
   A follow-mode switch is neither, and the docs say "the first time a preview opens for a
   document", which A → B → A contradicts. Suggest a per-webview mark ("hint shown in this panel"):
   a new panel has an empty webview state, so it still plays on every new preview opening. If the
   per-document rule is kept, record it under "Autonomous decisions" and make the docs and SwRS
   wording match.

3. **Low: pressing the chevron during the hint makes the rows flicker.** `toolbarCollapse.ts:105-106`
   and `:130-133`. `pointerdown` on the chevron cancels the hint first, which hides the rows at once
   with no animating mark. The following `click` then unrolls them again from zero height. The
   reader sees the rows vanish and grow back. Suggest ignoring the `pointerdown` whose target is
   the collapse button, so the click handler ends the hint and keeps the rows open. Related, and
   kept as the request specifies: a press on a row 2-5 button during the hint hides that button
   before its `click`, so the click is lost. Mention this in the PR's autonomous decisions.

4. **Low: the pending overlay can cover rows 2-5 during the hint, and the hint attribute has no
   effect in CSS.** `src/core/preview/styles/pageChromeStyles.ts:285-287` places the overlay at
   62 px whenever `data-sphinx-preview-toolbar-state="collapsed"`. During the 700 ms hint the rows
   are open, but that state attribute stays collapsed. `data-sphinx-preview-toolbar-hint` (set at
   `toolbarCollapse.ts:90,113`) is used by no stylesheet. Exclude it in the overlay rule (for
   example `html[…state="collapsed"]:not([data-sphinx-preview-toolbar-hint])`), or remove the
   attribute and record the limitation.

5. **Low (traceability): the reduced-motion rule has no marker for the new requirements.**
   `src/core/preview/styles/propertiesStyles.ts:506-513` holds the reduced-motion half of
   SwRS-TOOLBAR-129 and SwRS-TOOLBAR-130. The file carries only `@implements_req` CORE-050, and
   neither SwRS lists it in `implemented_in_files`. Add the two markers, or state in the SwRS
   verification notes that CORE-050 covers it.

6. **Nit: missing blank line in the requirements log.** `requirements/tiers/log.md:13-14` has no
   blank line between the new entry and the next `## 2026-10-28 (find in preview …)` heading.
