## What holds

- Root cause: the evidence supports it. The 1.143.0 and 1.143.1 bundles differ only in their
  version strings, and 1.143.1 fails the same way. A plain WorkspaceEdit plus undo also fails, and
  so do disposing the preview and `bringToFront`. The frontmost app correlates with failure over 15
  logs, and a locked screen reproduces it every time while blurring an activated window does not.
  This is a harness/session cause (Decision 1b), and the guard fixes it there.
- No undo assertion is weakened, skipped or removed. The `waitFor` predicates and timeouts in
  `checkboxToggle.test.ts` and `realInput.test.ts` are unchanged; only the failure messages gain the
  window report and the change trace. No retry, sleep or longer timeout is added. The 10 s guard
  deadline is a failure deadline on `onDidChangeWindowState` (a state VS Code reports), and its
  error carries diagnostics.
- `ensureTestWindowFocused()` returns at once off macOS or when the window is already focused, so
  Linux CI is unchanged. It uses no network, and each `execFileSync` has a 5 s timeout, so it
  cannot hang. Looking the window up by pid (`process.ppid` = the main process, which runs the
  extension host as a utility process) avoids the Code/Electron and `/Applications` vs
  `.vscode-test` naming trap.
- Slash menu (Decision 6): `waitForPageSettled` and `waitForTextInput` are the repo's existing
  readiness signals, and they wait on product-reported state. The menu wait now has `explained`
  plus editor and focus diagnostics. The report says honestly that the cause is not proven.
  `stressPlan.test.ts` "CR 048" fails on the old `stressPlan.ts` (`includes("slash-menu")` is
  false), and the existing CR 043 test confirms that the name maps to a runner.
- `STUDIO_VSCODE_EXECUTABLE` (run-tests.ts:13-16) fails fast on a missing path and goes through the
  existing `codeExecutablePath()` / `vscodeExecutablePath`. That is fine.

## Findings

1. **Medium: the reload campaign is not guarded** (test/integration/reload-suite.ts:50-60, run from
   run-tests.ts:170). `runReloadCampaign` spawns a fourth real VS Code window and drives it over
   CDP with `page.keyboard` (Escape, F1, Enter, editor clicks). That is the same dependency on an
   activated window that the CR diagnoses, but `ensureTestWindowFocused()` is called only in the
   trusted, untrusted and scroll-sync suites. The full four-suite run has never reached this
   campaign locally, because every failing run stopped at the trusted undo. So "Done = full local
   suite green" is at risk, and CONTRIBUTING.md:74 / CHANGELOG.md:5 ("every window suite first
   asks macOS…" / "Each window suite") are inaccurate.
   Fix: give the runner side a guard too. For example, export a host-free
   `activateMacWindow(pid)` from windowFocus.ts (the same osascript call, a no-op off darwin) and
   call it with `child.pid` after the workbench page appears. Then wait on a state the workbench
   reports, such as the custom title bar losing its `inactive` class (`.part.titlebar:not(.inactive)`)
   or `page.evaluate(() => document.hasFocus())` if it is shown to be reliable there. On timeout,
   fail with the frontmost app and the screen lock state. Alternatively, show with a run that the
   campaign does not need activation, and correct the docs wording to name the three suites.

2. **Low: the one-time macOS Automation consent is not explained** (windowFocus.ts:26-31,
   CONTRIBUTING.md:70-78). The first `tell application "System Events"` from a given VS Code build
   triggers the TCC prompt "… wants to control System Events". Each build path counts separately:
   `/Applications`, each `.vscode-test` download, and the Code binary used by the reload campaign.
   osascript blocks until the user answers, the 5 s timeout kills it, and that first run fails with
   only "activation failed: … ETIMEDOUT". If the user refused, it fails with error -1743. It cannot
   hang, but the failure does not explain itself.
   Fix: when the osascript error contains `-1743`, `ETIMEDOUT` or "Not authorized", add "allow
   Automation > System Events for this VS Code build in System Settings > Privacy & Security" to the
   message. Add one sentence about that prompt to CONTRIBUTING.

3. **Low: the CHANGELOG line is over 100 columns** (CHANGELOG.md:8, 101 characters: "undo step
   ("one undo to restore …"), on any VS Code version. On a locked screen the suite now fails").
   Fix: rewrap the bullet at a clause boundary so that every line is at most 100 columns. The
   CONTRIBUTING lines 70-78 are within 100 columns, and both texts are in English.

4. **Info: slash menu is defensive, not root-caused** (realInput.test.ts:1049-1082). This is
   acceptable under CI rule 12 as written up: the logs prove nothing, the readiness waits are
   deterministic, the failure now explains itself, and the case is in the stress plan. The manual
   heavy CI run with `slash-menu` is the proof that Decision 3 asks for, and the PR text should say
   that the cause was not observed.
