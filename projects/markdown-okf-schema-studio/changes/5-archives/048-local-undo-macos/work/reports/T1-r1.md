## 1. Undo never restores the buffer: root cause (harness / macOS session, not product, not version)

**Cause.** The test window was never the active (key) window on macOS. When that happens VS Code
reports `vscode.window.state.focused === false`, and the workbench sees no focused code editor,
even though the DOM focus is in the editor (`document.activeElement` = `div.native-edit-context`,
the editor has the `.focused` class, Playwright's focus emulation makes `document.hasFocus()` true).
So `undo` (keyboard or `executeCommand`), `cursorTop` and typed keys all reach nothing. macOS leaves
a newly launched app in the background when the user is working in another app (cooperative
activation) or when the screen is locked. On CI the xvfb display always focuses the window. Losing
the focus *later* is harmless. Only a window that was never activated fails.

**Evidence.**
- *Version ruled out.* I downloaded the 1.143.1 test build into `.vscode-test/`. The renderer bundle
  `workbench.desktop.main.js` of 1.143.0 and 1.143.1 is byte-identical apart from the
  version/commit/date strings (statement-level diff). The same holds for `main.js`, the extension
  host and the preload. The Electron version is 43.7.7 in both. Under the failing condition,
  1.143.1 fails exactly like 1.143.0 (`cb-early-1431.log`, 2 of 2 rounds).
- *Product edit path ruled out.* The trace of document changes, now in the failure message, shows
  one plain edit (the toggle, line 3, 1 char) and no undo event at all. Probes in the failing state
  (temporary, now removed) gave these results:
  - typing "Q" with the keyboard did not reach the document;
  - a plain `WorkspaceEdit` applied (`probeApplied: true`) but `undo` did not revert it either;
  - `cursorTop` left the cursor on line 11;
  - disposing the Studio preview (so no webview could take the command) did not help;
  - `page.bringToFront()` did not help.

  Nothing specific to the extension's edit (TextEditor.edit vs WorkspaceEdit, undo stops) is
  involved. A user with a focused window is not affected.
- *Correlation over 15 earlier runs.* In every failing log (CR 034, 040, 043 ×5, 044, origin/main,
  and my 2 failing runs) the test window was not frontmost: the diagnostics show `frontmostApp` = the
  user's own VS Code or System Settings. In passing runs the frontmost app was the test window
  (pid = `testWindowPid`).
- *Deterministic reproduction.* With the screen locked, every round fails with `windowState.focused:
  false` and `frontmostApp` = loginwindow (`cb-early.log` 6/6, `cb-early2..5`). Deactivating an
  already-activated window does not reproduce it: Finder activated before the undo step
  (`trusted-blur.log`), between the editor click and Cmd+Z (`trusted-blurB.log`), or the user's
  VS Code brought to the front (`trusted-front.log`) all pass. CPU load alone (8 × `yes`, a parallel
  `just visual` capture loop) does not reproduce it either.

**Fix (harness).** `test/integration/windowFocus.ts` adds `ensureTestWindowFocused()`. On macOS, if
`window.state.focused` is false, it asks macOS (System Events, by the window's main-process pid =
`process.ppid`) to bring the window to the front. It then waits for `onDidChangeWindowState` to
report `focused`, a state the product reports. The 10 s deadline is the failure deadline, not a
sleep. If the window still is not focused, it fails at once with the window state, the frontmost app
and `screenLocked`. Other platforms return at once, so CI is unchanged. It is called at the start of
the trusted, untrusted and scroll-sync suites. Verified with the screen locked: the suite fails
immediately with `The VS Code test window never became the active window … "screenLocked":true`
(`guard-locked.log`) instead of a 10 s undo timeout later.

## 2. "Timed out waiting for the slash menu to open after a line break"

I could not reproduce it (it passed in every one of my ~15 trusted runs, loaded or not). The only
failing log (CR 044 r1, `integration-run1.log`) has no diagnostics. In that run the checkbox undo
before it passed, so the window was focused, which makes it a separate cause. What the code shows:
`scenarioSlashMenu` presses End/Enter and types `/` as soon as the block editor is *visible*. Unlike
the scenarios fixed earlier (CR 041), it waits neither for the page to settle (a deferred host update
can replace the page under a just-opened editor) nor for the caret in the text box. The menu opens
only on an `insertText` input of `/` at a line start in the focused textarea, so a lost End/Enter or
a lost focus gives exactly this timeout. Fix, the repo's existing readiness signals (no sleep, no
retry, no longer timeout):
- `waitForPageSettled` before the click;
- `waitForTextInput` (the textarea is the active element and the page has focus) before the first
  key;
- the menu wait now carries the editor state, the window focus report and the page diagnostics
  (`explained`);
- the scenario joins the stress plan (`slash-menu`, CI rule 12).

This is a defence against a race I could not observe, not a proven root cause. See the open points.
