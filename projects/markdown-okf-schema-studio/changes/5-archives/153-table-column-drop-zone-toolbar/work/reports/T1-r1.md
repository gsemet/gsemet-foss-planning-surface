## Root cause (proven with an in-page drag event probe, run 4)

The page's drop zone is a `document` `dragover` listener (`dragOverZone` in
`src/page/features/tableRowMove.ts`). When a drag update changes the element under the pointer,
Blink fires only `dragenter`/`dragleave`. `dragover` fires only when two updates in a row land on
the same element. The probe log shows this:

- Over plain page content: `dragover main 503,93`, `dragover main 504,93`.
- Over the toolbar, at the list-table point: the final moves of `holdAt` (+1 px and back) only log
  `dragenter svg 454,95`, `dragleave button`, `dragenter button 453,95`, `dragleave svg`. They
  alternate between the toolbar button and its 18 px svg, so no `dragover` arrives. The marker
  stays where the last `dragover` left it (x 376: H3, left half → `before`), or none shows.

The Fold button widened the toolbar by 32 px (166 → 198) to the left. This moved the strip points
of both tables onto toolbar buttons, at the edges of their svgs. Before the change, the pipe point
was over a toolbar button too (theme toggle, 479..509), but at a spot where the 1 px jiggle stayed
on one element. Users meet the same defect: the toolbar takes the drag events (and shows tooltips)
over the part of the drop zone it covers.

## Fix

`src/core/preview/styles/editModeStyles.ts`: one rule. While a dragged row or column cell carries
its drag attribute, the floating toolbar takes no pointer events:

```css
html:has(#sphinx-myst-preview-content :is(tr[data-okf-row-dragging], :is(td, th)[data-okf-col-dragging])) [data-sphinx-preview-toolbar] {
  pointer-events: none;
}
```

The drag events now reach the page under the toolbar, and no toolbar tooltip opens. Because the
rule keys on the dragged cells, a render that replaces them gives the toolbar back, even if
`dragend` never fires. After the fix, the probe shows `dragover main 503/504/453/454` at the strip
points, and the marker is `{2, after}` for both syntaxes. Screenshots:
[after-pipe-cream-column-strip.png](shots/after-pipe-cream-column-strip.png),
[after-list-table-cream-column-strip.png](shots/after-list-table-cream-column-strip.png).

## Open points

1. **Product, not fixed here (backlog candidate).** In the same 1400x900 window, the toolbar
   covers the third column's handle of a table right under the first heading (handle x 453..474
   under toolbar x 444..642). A user cannot grab that handle until they scroll or collapse the
   toolbar. This round only makes the drop zone work under the toolbar. Keeping handles clear of
   the toolbar at scroll 0, like the first-element clearance of LAYOUT-007, is a separate change.
2. **Blink only fires `dragenter` when the target changes.** The zone listener does not handle
   `dragenter`, so the marker can lag one step when a drag stops right after crossing an element
   boundary (for example between two column handles in the strip). This is not the cause of this
   failure once the toolbar is transparent, but adding `dragenter` to the zone listener would make
   it robust. Backlog candidate.
3. **Environment.** One local run timed out in `setEditMode`, before the scenario began ("Timed out
   waiting for the rendered Studio webview", run 3). This happened while other VS Code test windows
   from other worktrees were open. It is not related to this change, and the next run was green.
4. `uv run --group requirements` (no `--no-sync`) synced the worktree `.venv` from the lock file to
   get okfreq 0.16.0. The global okfreq on PATH is older and rejects `default_owner_email`.
