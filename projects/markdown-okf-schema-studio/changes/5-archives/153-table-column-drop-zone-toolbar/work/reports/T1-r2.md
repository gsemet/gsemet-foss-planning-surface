# T1 round 2 — Four-row floating toolbar

Worktree: `/Users/az02065/Projects/DevTools/markdown-okf-schema-studio-wt-153`, branch
`change-requests/153-table-column-drop-zone-toolbar` (HEAD 06975c23, nothing committed).

## Verdict

The toolbar now has four rows of at most four buttons:

1. Refresh, Anchor, Edit and the collapse chevron.
2. Back, Next, Zoom out and Zoom in.
3. Theme, Width and Table of contents.
4. Fold, Diff and Comments (new row `content`).

It is 134 px wide instead of 198 px, so it no longer covers the table handle strip in the 1400x900
integration window. The round-1 CSS workaround (toolbar `pointer-events: none` during table drags)
and its unit test are removed. The deterministic integration assertion stays: `elementFromPoint`
at the strip point is not inside the toolbar.

The toolbar is taller (y 12..146 instead of 12..114), which caused two side effects. Both are now
fixed:

- **Table bar under the toolbar.** The bar of a table right under the first heading had "Delete
  selected column" under the toolbar. Fix: the bar gives up the width the toolbar covers.
  SwRS-MDOKFSTUDIO-TABLE-064, `src/page/features/tableCellEditor.ts`.
- **Tall block scrolled up.** A tall code block, opened scrolled, scrolled the page up. Fix:
  `src/page/features/scrollCore.ts`, SwRS-MDOKFSTUDIO-PALETTE-021. Details below.

## frontmatterFields CI failure (round-1 heavy run 40679373479)

The failure: the "New field name" input click never became stable for 30 s, right after the r15
capture.

- **The round-1 CSS cannot cause it.** The rule matches only while a table row or column cell
  carries a drag attribute.
- **No useful comparison on main.**
  - The last green heavy main run, 724841e6, predates fold (#151) and find (#144).
  - Every heavy run since fold, on main or on branches, stopped before the frontmatter scenarios:
    tableMoves, stress or find failed first.
  - Only two runs reached it: fix/tab-item-edit-source bddede2e and 3e2ffa1b. Both were before
    fold and both passed.
  - Our round-1 run is the first run with fold that got that far.
- **Plausible mechanism (unproven).** In the CI r15 shot (Linux fonts), the leading properties
  table ends at x 1171 and the 6-button toolbar starts at 1168, a 3 px overlap.
  - `firstClearance` makes a leading properties table give up the toolbar's width, or pushes it
    down, when its controls sit under the toolbar.
  - It has a loop guard (200 updates per second, then a trailing update), so a layout that
    oscillates would move in bursts. That fits "not stable" over 30 s of retries.
  - With 4 rows the toolbar starts about 64 px further right, so this overlap goes away.
- **Not reproduced locally.** On macOS the four frontmatter add-field scenarios pass with HEAD's
  6-button markup and with the 4-row toolbar.
- **Next step.** Heavy CI on round 2 will show whether it recurs. If it does, the next step is the
  `firstClearance` diagnostics (`describe()`) on the r15 page in CI.
