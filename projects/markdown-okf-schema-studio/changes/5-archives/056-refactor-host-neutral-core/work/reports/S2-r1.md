**Page runtime constraint.** `createHostMessageFilter` and `createMessageRouter` are
self-contained. `scrollSync.ts` injects them with `${fn.toString()}`, as it does the other page
modules, and S5 turns that into normal imports. The bundled-runtime tests of S1 (undeclared names,
pinned trace) pass on the esbuild output. The new unit tests also rebuild both functions from their
source text with `new Function`.

**Page side** (`scrollSync.ts`). The ~150-line `if` chain of the `message` listener is gone. In its
place: `hostMessages.on(type, handler)` for the 22 types the runtime handles, then one listener,
`hostMessageFilter.accepts(message, context) && hostMessages.dispatch(message).handled`. Any other
`…Result` still goes to `hostRequests.receive`, as before; the fall-through order is unchanged.
`labelRename.receive` and `plantUmlFileRequests.receive` return `false` when the message is not
theirs, which passes it on exactly as before. `sameContext` and `isValidContentPatch` are removed.
`linkNavigation.ts` keeps its own listener for `previewLinkTargets`, because its unit test drives
that listener. The filter still has a rule for that type.

**Host side** (`extension.ts`):

- Removed: `isPreviewSyncMessage` (the boolean chain, about 120 lines), the `PreviewSyncMessage`
  bag type, `registeredMessageHandlers`, `RegisteredPreviewMessage` and `src/preview/previewMessages.ts`.
- `handlePreviewSyncMessage` now runs `isPageToHostMessage`, then the gate from
  `PAGE_MESSAGE_GATES` (typed by the union: `render`, `comment`, `document`, `own-id`,
  `page-state`), then `pageMessages.dispatch`.
- The `page-state` gate (`handlePageStateMessage`) keeps the old order:
  1. the ready-report reload or patch-chain checks;
  2. the render check, then `reportStaleEdit`;
  3. the anchor report (not for `previewLinkDiscover`);
  4. the read-only refusal of the edit requests;
  5. the handler.
- Each former branch is now an `on(...)` handler. The state-reporting types call
  `recordPreviewState` first. Scroll and reveal share `revealFromPage`.
- Return values are kept: the formerly registered types still return `Promise.resolve(result)`,
  the page-state types still return the handler's own result. `genericMarkdown` asserts this for
  the frontmatter save.
- Handlers now receive precise types. The `message.x as T` casts are gone, except two narrowings
  in handlers shared by two types.
- Every host send goes through `postToPage(preview, message: HostToPageMessage)`, so all 31 sends
  are type-checked.

**Revision.** The wire field `documentVersion` is now `revision`, everywhere in the page runtime
and in its modules. The page only repeats and compares it. The host maps it in exactly two
functions, `revisionOfDocument(document)` and `revisionOfStage(stage)`, which both return the VS Code
`TextDocument.version`: VS Code already keeps a per-document counter. Internal host bookkeeping
(`stage.activeDocumentVersion`, `editLock`, `buildQueue`, frontmatter state) still uses VS Code
versions; it is not protocol. `RevisionCounter` is the core counter for hosts without one. It is
unit-tested and not used by the VS Code host (see Autonomous decisions). The DOM attribute
`data-sphinx-preview-document-version` keeps its name and now holds the revision.

## Autonomous decisions

1. **The VS Code revision is `TextDocument.version`, without a separate counter.** The protocol
   names a `revision`, and the page no longer knows about VS Code versions. The VS Code host maps
   the version 1:1 in one place. A real counter would change the numbers the page carries.
   `realInput.test.ts:3024` pins `data-sphinx-preview-document-version === source.version`, and
   real-input tests must stay unchanged. About 30 integration message literals would also need new
   value expressions. `RevisionCounter` ships for the hosts that need one (S3 `DocumentStore`).
2. **Exact behaviour over cleanup.** The page-state family keeps its unbounded `documentId` and its
   cross-type field rules. Unvalidated reported fields (`sourceFile`, `focusedBlockId`, …, the
   label-rename `editId`) stay unvalidated. They are typed as before and documented as "not checked
   by the validator". Tightening any of them would be a behaviour change.
3. **Gates are host policy, not protocol.** `PAGE_MESSAGE_GATES` lives in `extension.ts`, next to
   `matchesCurrentPreview`. S4 can move it to the `PreviewSession`.
4. **`linkNavigation.ts` keeps its own listener** (see Design).
5. **Glossary**: added "Message gate", "Message router", "Protocol" and "Revision", and updated
   "Message registry", in `.agents/glossary/common.md`.
