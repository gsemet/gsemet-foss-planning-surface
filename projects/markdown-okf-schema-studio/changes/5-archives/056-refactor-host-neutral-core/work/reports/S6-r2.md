## F1 (must-fix): DOM code in core

- **Fix**: `applySpanColors` (the CSSOM writer) moved as is to the new page module
  `src/page/modules/spanColors.ts`. The pure `isSafeOkfColor` stays in
  `src/core/security/spanColors.ts` (the sanitizer uses it); the core file now holds only the grammar.
  The page module re-exports `isSafeOkfColor` from core, so `src/page/runtime.ts:32` stays a single
  import line (`import { applySpanColors, isSafeOkfColor } from "./modules/spanColors";`). A second
  import line would have grown `runtime.ts` to 4966 lines, over its 4965-line ratchet entry, and the
  ratchet can only go down. Other importers of `isSafeOkfColor` (`html-sanitizer`, three page
  module tests, `mystFeatures.test.ts`) did not change.
- **Test**: `test/core/security/spanColors.test.ts` keeps the grammar test. The `applySpanColors`
  test (with its `fakeElement` helper) moved word for word to `test/page/modules/spanColors.test.ts`.
  Assertions are identical. The unit count stays at 2283 (183 test files, up 1).
- **Boundary config**: no change was needed. The page → core edge was already allowed, and
  `core-is-the-bottom-layer` now covers the move: a probe `typeof import("../page/modules/spanColors")`
  in core is reported (see F3).
- **Ratchet baseline**: no change (`runtime.ts` is still 4965 lines; the other files are not
  listed).
- **Bundle**: `npm run bundle` → `preview.js` is the same size as the HEAD build (274 062 bytes).
  The minified bytes differ only in mangled local names, because esbuild now has one more module
  scope. To check the code itself, I built both trees with `minify: false` through
  `scripts/page-bundle.mjs` (scratchpad script `s6/r2cmp/build.mjs`). With `//` path comments
  removed, the two outputs differ by exactly 2 blank module-separator lines. The code order and
  the content are identical. `preview.css`, `mermaidPreview.js` and `plantumlPreview.js` are
  byte-identical. `extension.js` is unchanged from r1 (+865 bytes against HEAD, as before).

Kept as reviewed. `.dependency-cruiser.cjs` `NODE_DEBT` changed from `file → [built-ins]` to
`file → { builtins, reason, removal }`. Each `core-node-debt-is-bounded` rule comment now prints
the built-ins, the reason and the removal plan, so a violation message carries them. The removal
plans:

| File | Built-ins | Removal |
| --- | --- | --- |
| okfFrontmatter | fs, path, util | renderer/frontmatter split, a later step of this refactor (S8) |
| renderPipeline | path, perf_hooks | perf_hooks: the same split, which switches to the global `performance` (S8); path: kept, path shim |

The config text says "later step of this refactor", not "S8", because repo text must not carry
internal ids. The set of allowed built-ins per file did not change, so the enforcement is the same.
Check: `just check-boundaries` passes, and the probe in F3 shows the rules still fire.

  that esbuild erases is still cruised. A real dynamic import is counted twice, which is harmless.
  The file header and the TSDoc describe this.
- **Test** (probe, then deleted): a temporary `src/core/zzProbe.ts` with

  → page. Before the fix, the reviewer's r1 probe showed that such references were not reported.
  After the probe was deleted: 0 violations (241 modules, 629 dependencies; r1 had 240 / 628, and
  the difference is the new page module).
