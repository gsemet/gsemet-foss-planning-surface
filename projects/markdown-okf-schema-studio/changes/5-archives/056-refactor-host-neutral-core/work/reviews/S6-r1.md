## Findings

### F1 — must-fix — DOM code classified into core

- **Where**: `src/core/security/spanColors.ts:36`. `applySpanColors(document: Document, …)`
  calls `querySelectorAll<HTMLElement>` and `element.style.setProperty`.
- **Problem**: this is page DOM code inside `core`, which breaks the spec rule "core ↛ DOM". The
  boundary tool cannot see DOM globals or DOM types (open point 2: `lib.dom` is loaded
  everywhere), so classification is the only guard for this rule. A DOM function in core is
  exactly the case to keep out. It is the only DOM-typed code in `src/core`
  (`core/paste/htmlToMarkdown.ts` uses parse5 node types, not DOM).
- **Fix**: keep `isSafeOkfColor` in `src/core/security/spanColors.ts`, because the sanitizer uses
  it. Move `applySpanColors` to the page, for example `src/page/modules/spanColors.ts` or
  `src/page/features/`, and import it from `src/page/runtime.ts:32`. Split
  `test/core/security/spanColors.test.ts` in the same way: the `applySpanColors` test (line 38)
  goes to `test/page/...` with identical assertions. Pure move; `preview.js` stays byte-identical
  apart from module order, so check it with the same HEAD bundle comparison.

### F2 — decision recorded, non-blocking — Node built-ins in core (`NODE_DEBT`, 14 files)

- **Spec**: "core ↛ Node built-ins", with no allowance for a baseline, unlike the size ratchet.
  The coder chose a bounded per-file, per-built-in allowlist.
- **Verdict**: I accept it for S6. Moving files would not resolve the gap, it would only relabel
  it:
  - The I/O files are imported by other core files: `resource-policy` by `html-sanitizer`,
    `mystRenderer` and `previewNavigation`; `stemIndex` by `fileLinks`; `fileLinks` by
    `okfFrontmatter` and `propertiesTable`; `documentGlob` and `confLocator` by
    `renderPipeline`. Moving them to node-services cascades into core → node-services
    violations.
  - The files only the session imports (`renderPipeline`, `csp`, `commentStore`) would turn into
    session → node-services debt.
  - The real fix is the async ports of S3. That changes timing, which a "no behaviour change"
    move step must not do.

  The allowlist does enforce the rule for every other core file, and no exempted file can gain a
  new built-in.
