## Design

Four new folders. The S2 dependency rule continues: the inner layers never import the outer ones.

| Folder | Imports allowed | Role |
| --- | --- | --- |
| `src/host-api/` | other `host-api` files, `protocol/revision` (types) | The ports: interfaces only, plus `EventSource`, `isFileNotFound` and `readTextFile`. No `vscode`, DOM or Node. |
| `src/core/edits/` | `host-api` types, pure mapping/comments/render helpers, `okfFrontmatter` | Pure edit planners. They take text and return `TextEdit`s or a refusal. |
| `src/host-memory/` | `host-api`, `core`, `protocol` | In-memory `DocumentStore` and `FileSystem`, for tests and for a future host without a disk. |
| `src/node-services/` | Node | `FileSystem` on `fs/promises`, and a `ProcessRunner` built on `spawn` without a shell. |
| `src/host-vscode/` | `vscode`, plus all of the above | The VS Code adapter. It reads the VS Code API lazily, inside its methods, so the module loads under the strict S1 fake. |

**Text edits.** `TextEdit` is `{start, end, text}`, with UTF-16 offsets into the text the planner
read. Only the adapter turns offsets into positions, through `document.positionAt`. That conversion
is the one the old handlers used for offset-based edits.

The handlers that worked with line positions (checkbox, thread delete, thread reply) now get their
offsets from `sourceLines`. It splits on `\r\n|\n|\r`, like VS Code's line model, and gives the same
ranges. CRLF tests cover this.

**Undo steps.** `ApplyEditOptions.ownUndoStep` keeps the old per-site behaviour:

- When it is true and an editor shows the document, the adapter uses `TextEditor.edit` with
  `undoStopBefore`/`undoStopAfter`. Otherwise it uses a `WorkspaceEdit`.
- `ownUndoStep: true` is used for checkbox, label rename, thread reply/delete, block move and block
  cut/paste.
- `false` is used for the frontmatter save and the block-edit drain. These always used a plain
  `WorkspaceEdit`, and they still do.

The old code looked for the editor with `documentKey(editor.document) === documentKey(document)`.
`visibleEditorFor` did the same against `preview.documentUri`. The adapter's lookup,
`editor.document.uri.toString() === id`, is the same comparison.

**In-flight edits (CR 046).** `previewEditsInFlight`, `trackPreviewEdit`, `applyPreviewEdit` and
`editInPreview` are gone. The adapter's `applyEdits` counts its running edits per document id, and
`DocumentStore.isApplying(id)` exposes that count. `noteOutsideChange` asks
`host.documents.isApplying(key)`. The S1 host tests and the CR 046 unit tests pass unchanged.

**Revisions (S2 review, N2).**

- `TextDocument.version` is now read in one place only: `VscodeHostDocument.revision` in
  `src/host-vscode/documents.ts`.
- `revisionOfDocument()` in `extension.ts` delegates to `host.documents.revisionOf()`.
- Every former `document.version` read in `extension.ts` goes through it. That covers
  `frontmatterRevision`, `frontmatterLinkResultsRevision`, the pins, the block-edit checks, cut and
  paste.
- `BuildQueue` has a new `revisionOf` option. It still defaults to `document.version`, and the
  extension passes `revisionOfDocument`.
- `RenderOptions` has a new `revision`, and the extension passes it. Without it, `createStage`
  falls back to `document.version`, so the unit tests that call the pipeline directly are unchanged.
- `RevisionCounter` now has a user: `createMemoryDocumentStore` counts its revisions with it.

**Async file access.** Order is preserved: every converted call was already awaited in sequence, or
is now awaited at the same point.

- `previewNavigation`: `createPreviewNavigator(files)` returns async `resolvePreviewNavigation`,
  `validateResolvedPreviewNavigation` and `validatePreviewNavigation`. The `local` wiki search is a
  sequential loop that keeps the first local hit, which is what the old `map`/`find` returned.
- `bibScan`: no `vscode` import any more. It now takes `scanBibKeys(documentPath, {files, workspace})`,
  and an `AbortController` replaces the `CancellationTokenSource`.
- The comments sidecar (read, write, stat, rename), the image paste (`readDirectory`, `writeFile`),
  `currentDocumentText` and the link-marker read all go through `host.files`. The link-marker read
  keeps `Buffer.from(...).toString("utf8")`, because `TextDecoder` would strip a BOM.

## Open points

1. **Render-path sync file access stays.** It runs inside synchronous render passes and
   `updatePreview`, and making it async would change the timing of renders. That belongs to S4 or
   S8. It covers:
   - `resource-policy`, `okfFrontmatter`, `fileLinks`, `stemIndex`, `documentGlob`, `confLocator`
     and `snapshotWorkspace`;
   - `sphinxBuild`, the `canonicalPath` of `buildQueue` and the `stat` of `plantUmlRenderer`.
2. **`ProcessRunner` is defined, implemented and tested, but not wired.** `plantUmlRenderer` and
   `sphinxBuild` keep their own spawner seams, which their tests use.
3. **`core/edits/frontmatterEdit` imports `okfFrontmatter`, which imports `fs`.** The planner
   functions it uses are pure, but the module is not host-neutral until S8 splits `okfFrontmatter`.
4. **Revision field names.** The stage field `activeDocumentVersion` keeps its name. The Sphinx
   `stageSnapshot` path still reads `document.version`, but it has no caller in `src/` (only tests).
5. **`bibScan` uses the folder of a file path only.** The old code also called `getWorkspaceFolder`
   on the URI of a document that is not a file. Such a document could only belong to a virtual
   workspace folder, which the extension does not support (it is eligible only for `file:`
   documents).
6. **No direct adapter test.** No unit test covers `host-vscode/documents.ts` alone, such as the
   undo-step path against the `WorkspaceEdit` path. It is covered indirectly by the S1 host tests
   and the visual campaign. A focused test needs `applyEdit`/`edit` support in `fakeVscode.ts`.
