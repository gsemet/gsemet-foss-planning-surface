## Findings

### 1. Low (security hardening, non-blocking): a directive attribute rule can override the generic attribute block

`src/core/security/html-sanitizer.ts:255` and `src/core/directives/registry.ts:29`

`directiveAttributeRule(name)` runs before the `on*` / `style` / `srcdoc` removal and before the
`src`/`href`/`srcset` rewriting. On a valid value it `continue`s. Today the only rule is
`data-okf-width`, so nothing is wider, and the order matches HEAD. But CONTRIBUTING now presents
`attributes` as an extension point. A future plug-in that declares a rule for `style`, `onclick`,
`href` or `src` would skip the generic protections without any test noticing.

Fix (cheap, recommended for the next round of any step that touches the registry, or in S8): in the
`registry.ts` load loop, throw unless the attribute starts with `data-` and is not already handled
by the sanitizer (`data-myst-table-style`, `data-okf-color`, `data-okf-background`). Add one line
to the CONTRIBUTING plug-in recipe: "attribute rules are for `data-*` attributes only".

### 2. Low (docs): the "Add a setting" recipe overstates the boot plumbing

`CONTRIBUTING.md:126-134`

- `previewBootSettings` and `readPreviewBootSettings` iterate `PREVIEW_SETTINGS` only. A
  `startupSetting` added to another section would not reach the page.
- A `liveSetting` still needs its own host message and page handler. Only the boot read is
  generic (`showComments` has `hostEvents`/`commentsToggle` wiring).

"Boot settings reach the page without more code" is therefore only true for startup settings of
the preview section. Fix: say so ("boot settings live in `PREVIEW_SETTINGS`; a `liveSetting` also
needs its update message").

### 3. Nit: `ci-static` recipe comment

`justfile:167` lists "TypeScript, boundary, size, unit, contract and security checks". It could
name the settings schema check, like the updated `check` comment and AGENTS.md. Optional.

## Decisions requested by the driver

### preview.js +7.9 kB (setting descriptions on the page)

**Accepted, non-blocking.** The descriptions are static strings, already public in
`package.json`, with no secret and no user input, so there is no security issue. The page bundle
loads from the extension folder once per webview. 7.9 kB on 274 kB (+2.9 %, about 4.9 kB of it
descriptions) has no measurable effect on start time next to Mermaid/KaTeX. A slim page projection
would need a second artifact or a build-time transform: either a second table, or an esbuild
plugin that strips `markdownDescription`. Both add machinery against "one table". If the size ever
matters, the cleanest variant is a separate core module of descriptions keyed by setting name. The
registry imports it only from `contributedConfiguration()`'s caller (the generator), and a test
asserts that every setting has a description. That is still one source of truth, but it is not
worth doing now.

### `chipToggle.ts` reading `showComments !== false` directly

The toString-based tests did **not** retire in S5. S5 removed only the tests of the page
*assembly*. Its report lists the per-module tests as open point 2. Ten page tests still evaluate a
module through `fn.toString()` in a `vm`, `test/page/modules/chipToggle.test.ts:65` among them
(also `motion`, `codeCopy`, `commentCompose`, `commentThreads`, `incomingChanges`,
`inlineThread`, `commentsToggle`, `labelRename`, `linkNavigation`). The coder was right not to
change the test in this step: changing its harness is outside S7. The inline rule
(`src/page/modules/chipToggle.ts:115`) is the same as the table's `bootFlag(true)` read, so there
is no behaviour drift.

Recommendation: do one sweep in S8, or as a follow-up, that moves these ten tests from
`vm.runInNewContext(fn.toString())` to direct imports with the fake DOM, keeping the assertions
identical (allowed by rules.md). Then switch `chipToggle` to
`readPreviewBootSettings(context).showComments` and drop the stale "injected with `.toString()`"
comments at the same time.
