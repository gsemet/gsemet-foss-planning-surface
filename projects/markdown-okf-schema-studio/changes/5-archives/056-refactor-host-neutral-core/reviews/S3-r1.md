## Blocking finding

### B1 (behaviour regression) `src/node-services/nodeFileSystem.ts:48-50`: `realpath` switched from the JS to the native implementation

`FileSystem.realpath` is `fs.promises.realpath`, which is the native `realpath(3)` (libuv).
`HEAD` used `fs.realpathSync`, the JS implementation, in `previewNavigation.ts`. The two do not
return the same path:

- **macOS (case-insensitive APFS).** I checked this on this machine. For an existing
  `CaseDir/File.md`, the input `casedir/file.md` gives:
  - `fs.realpathSync`: `…/casedir/file.md` (the case as typed);
  - `fs.promises.realpath`: `…/CaseDir/File.md` (the case on disk).

  So a link written with a different case now opens another URI. The editor tab, the
  `recordNavigation` history entry (`opened.id`) and the existing-tab lookup of `showDocument` (an
  exact `fsPath` match) all change.
- **Windows.** The native realpath resolves `subst` and mapped drives to their target. It is also
  known to fail on some virtual or RAM-disk volumes, where the JS version works. A link on such a
  drive would open under a different drive letter, or end as "The navigation target is unavailable."

Containment stays sound, because the root and the candidate are resolved by the same function. But
the step has to make no visible change, and the S1 tests only pass because `mkdtemp` paths are
already in canonical case. The rest of `extension.ts` (`canonicalPath`, `canonicalWatchRoot`) still
uses `fs.realpathSync`, so the host now mixes two canonical forms.

**Fix:**

1. Use the JS implementation in the Node file system, for example
   `import { realpath } from "node:fs"; … realpath: promisify(realpath)`. The callback
   `fs.realpath` is the JS implementation; `fs.realpath.native` is the native one. Say in the TSDoc
   that it matches `fs.realpathSync`.
2. Add a test in `test/node-services/nodeServices.test.ts`: on a case-insensitive file system
   (detected at run time, skipped otherwise), `realpath` keeps the case of the input, like
   `fs.realpathSync`.

The VS Code adapter (`createVscodeFileSystem.realpath`) delegates to this function, so the one
change fixes both.

## Behaviour equivalence (checked, no problem found)

  - Checkbox: `lines.start(line-1) + column`, one character.
  - Thread delete: both branches (through the start of the next line, or from the end of the
    previous line to the end of the file).
  - Thread reply: the whole closing line without its line break, joined with the document EOL.
  - Label rename, block move, cut, paste and block drain: the same offsets as before, turned into

  `sourceLines` splits on `\r\n|\n|\r`, like the VS Code line model. The CRLF tests cover it.
- **Refusal order and texts.** The refusal order is unchanged:
  - block move: the planner's refusal, then the include refusal;
  - copy/cut: span, include, cut;
  - paste: include before the clipboard, the plan after it.

  The messages are byte-identical constants. `planFrontmatterSave` and
  `checkFrontmatterCandidate` are a line-for-line split of the old `handleFrontmatterSave`, with
  the same branches, messages and flush behaviour. The only new refusal is `line < 1`, which used
  to throw in `lineAt`; the page never sends it.

  editor shows the document. It is set for checkbox, label rename, thread, move, cut and paste,

  as before. The editor lookup (`uri.toString() === id`) is the same comparison as `documentKey` /

  `editor.edit` / `applyEdit`, and decrements it on settle or on a synchronous throw. Positions are

  `currentPreviewDocument`, which checks against `message.revision`. The reply is re-planned on the

- **Async conversions.**

  - `handlePreviewLink`: the `disposed` / stage-identity re-checks are still made after every

  - `bibScan`: dedup by path instead of `uri.toString()` (equivalent for `file:` URIs). The

  - The exclude, max-results and timeout values are unchanged.

  - `host.workspace.trusted` is a live getter, not a value captured when the module loaded.
