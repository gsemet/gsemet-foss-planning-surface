# T1 round 1: coder report (CR 152)

## Root cause

This is a test-isolation leak. Commit 6df062d3 (#153) did not cause a product regression.

- The workspace remembers the edit mode for the next preview
  (`WorkspaceChoices.setEditMode`, `src/session/workspaceChoices.ts`). The page stores it whenever
  it is toggled (`src/session/features/viewState.ts:59`).
- #153 added `runPasteUrl()` to the trusted suite, just before `runWindowSwitchKeys()`. Before #153,
  `runEditKeys()` came just before it. `editKeys.test.ts` turns edit mode off in its `finally`, but
  `pasteUrl.test.ts` disposed the preview with edit mode still on. It was the only top-level
  scenario that left edit mode on.
- As a result, `windowSwitchKeys.test.ts` opened its preview already in edit mode.
  `setEditMode(page, true)` saw the mode was already on, so it returned without clicking the
  toggle. The toggle click had been the only thing that gave the page the keyboard focus. The two
  ArrowDown presses went to the workbench `<body>` and never reached the page.

Evidence from local real-window runs (macOS, under `WINDOW-TESTS.lock`, with temporary diagnostics
that are now reverted):

- With paste-URL run first (unchanged code): focus before the arrows was
  `{"active":"body"} hasFocus false`, and the workbench activeElement was
  `BODY.agent-status-enabled`. After two ArrowDown presses the selection was `[]`. Then
  `Timed out waiting for margin: the keyboard to select a block`. This is the CI failure,
  reproduced.
- Control run without paste-URL first: right after rendering, mode was `off` and hasFocus was false.
  After the toggle click, focus was on the `button` with hasFocus true, and the workbench
  activeElement was `IFRAME.webview`. After the arrows the selection was `["1. Citation"]`, and the
  test passed.
- In both runs, a freshly opened preview holds no DOM focus. The arrows only ever worked thanks to
  the toggle click.
- Supporting evidence: the CI stress job, which runs windowSwitchKeys separately, stayed green on
  the failing runs.

## Fix

In `test/integration/pasteUrl.test.ts`, the scenario now ends by turning edit mode off
(`setEditMode(page, false)`). It then waits for `storedEditModeForTests() !== true`, the same
pattern as `realWindowGaps.ts`. The `finally` also turns it off on a best-effort basis, the same
pattern as `editKeys.test.ts`.

No product code changed: the paste-URL behaviour and its unit, webview and integration tests are
untouched. No assertion was weakened or retried.

## Tests added

`test/build/integrationEditModeRestore.test.ts` runs in `test:unit` through the `out/test/build`
glob. It checks that every top-level `test/integration/*.ts` that calls `setEditMode(page, true)`
also calls `setEditMode(page, false)`.

- On the unchanged code (`git show HEAD:test/integration/pasteUrl.test.ts`) it fails with
  `actual: [ 'pasteUrl.test.ts' ]`.
- With the fix it passes (1/1).

A unit test of the page itself cannot catch this, because the defect lives in the order of the
scenarios.

## Open points

- The CR premise "after a window switch" is inaccurate. The failing step is the first step of the
  scenario, before any switch.
- Possible product follow-up for the backlog: a preview panel opened by the command is the active
  editor, but its page has no DOM focus (workbench `<body>` holds it), so the keyboard does nothing
  until a click. This is seen in the CDP-driven test window and is not verified in a normal window.
  It existed before #153 and is out of scope here.
- The four `realInput/*.ts` steps that turn edit mode on without turning it off are parts of one
  shared run, not top-level scenarios, so the guard does not check them.
