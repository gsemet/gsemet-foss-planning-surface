## Candidate use cases (StRS)

- UC-REVIEW-1: A reviewer opens a document with a `<name>.comments.json` next to it and sees the
  quoted text of each thread highlighted, can read the thread, and a broken file is ignored with a
  warning and never overwritten.
- UC-REVIEW-2: A reviewer selects text in the preview, writes a comment, replies, resolves,
  reopens or deletes a thread; the text they typed is never lost, two quick comments both land and
  the author is the configured name, then Git, then the OS user.
- UC-REVIEW-3: Review threads follow the text while the author edits, renames or reloads the
  document; a doubtful match is never guessed: the thread is listed as orphaned and stays in the
  file.
- UC-REVIEW-4: In a read-only preview (untrusted workspace, standalone file) the reviewer can read
  threads but cannot create, reply, resolve or delete, and nothing is written.
- UC-REVIEW-5: A writer sees HTML comments and TODO notes as chips that open into a box, hides the
  gray ones with the Comments button or the setting, and toggles a TODO comment from the keyboard.
- UC-REVIEW-6: A writer keeps a discussion in the Markdown as an inline `<!-- THREAD` comment, reads
  it as a green chip, replies or deletes it from the preview; only those lines change, in one undo
  step, with LF or CRLF kept.
- UC-REVIEW-7: A writer sees which blocks changed since the last Git commit (unsaved edits
  included) as green bars, and can hide them with the Diff button or the setting; files outside Git
  show nothing.

## Notable findings

- The toolbar Comments button hides the gray chips only; inline thread chips (green) stay, while the
  setting `preview.showComments` off hides both (`commentStyles.ts`). README/CHANGELOG do not state
  the difference.
- Incoming changes: only the untracked-file negative case has an integration test; the positive path
  of `IncomingChangesController`, its gates (trust, setting, Diff toggle, non-file document) and the
  300 ms debounce / HEAD watch / trust-granted triggers have no host-level test (F-REVIEW-062, 065).
- Host refusals of inline thread changes (read-only, open Markdown edit, stale document, "changed
  meanwhile", apply failure) have no host test; only the "lines are not a thread" case is covered
  (F-REVIEW-057).
- `moveSidecars` is tested for the move and the existing-target conflict only; the invalid, other
  document and dirty refusals and every warning text are untested; the same holds for the
  `persistAnchors` warning (F-REVIEW-043, 045).
- Invalid comment messages are dropped without an answer, so the compose box shows its 15 s timeout
  text for a message the protocol rejects; a whitespace-only body passes the protocol and is
  answered by the handler (F-REVIEW-029).
- Inline "Delete thread" has no confirmation while a review thread's Delete asks "Delete thread?"
  (F-REVIEW-054, 034); read-only wording "needs a trusted workspace" also appears for standalone
  files (F-REVIEW-036).
- Undocumented bounds: 2 MiB / 1000 threads / 200 comments / 10 000 characters, 50-line window and
  12-character floor, fuzzy 20 % and the 20 M-cell budget, 8 MiB document cap for re-anchoring,
  1 MiB HEAD cap, 20 000-line / 2000-edit diff caps.
