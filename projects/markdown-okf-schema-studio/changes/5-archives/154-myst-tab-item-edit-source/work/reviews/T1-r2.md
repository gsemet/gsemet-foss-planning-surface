## Blocking

1. Inline review comments (and THREAD chips) inside a tab panel lose their source lines.
   `unmapPlainBlocks` (src/core/render/mystGridToctree.ts:326-338) strips `data-line` /
   `data-end-line` from every descendant, including `.okf-comment` blocks. Probe (rendered with the
   built code): a `<!-- review: inner -->` in a tab item renders `<div class="okf-comment" ...>`
   with NO `data-line`, while the same comment at top level has `data-line="3" data-end-line="3"`.
   Consumers: src/page/modules/inlineThread.ts:25-31 + :66-73 (`lines(comment)` is read from the
   comment's own attributes; without them Reply and Delete answer "The thread has no source
   position. Refresh the preview." for a THREAD in a tab item), chipToggle.ts:55 (key falls back to
   the panel line, so keys can collide with other comments of the panel), commentThreads.ts /
   commentCompose.ts (anchors coarsen to the whole item). Fix: keep unmapping the plain blocks
   (paragraph, list, table, heading...) but do not unmap comment markers (`.okf-comment`
   / the comment node type) and add a test that a THREAD in a tab item keeps `data-line` and
   `data-end-line`; or unmap only the block types that edit mode would open.
2. Tables inside a tab item also lose their line mapping (mystTables.ts:111/121 read
   `node.position`, deleted by `unmapPlainBlocks`), so row/column handles that rely on
   `sourceLine` are dropped for a table in a tab item (probe: `<table>` has no `data-line`).
   Either confirm with a test/requirement that this is intended (MYST-098 table row says a grid,
   card, code or nested set in an item are "rendered in the panel") or exempt tables; at minimum
   add a unit test for a table, code block, grid/card and nested tab set under a tab item so the
   behaviour is pinned.
