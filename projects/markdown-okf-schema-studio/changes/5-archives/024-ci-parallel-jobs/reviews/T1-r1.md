## F1 (high) Epoch STUDIO_E2E_STARTED_AT weakens stale-evidence detection
.github/workflows/ci.yml:13-17. `validateIdentity` (test/site/reviewEvidence.ts:21-26) requires manifest.startedAt >= campaign.startedAt. With 1970 that check can never fail, so the "predates review start" guard is dead in CI. The remaining protection is runId equality (run_id-attempt is unique per run), so stale files from another run are still rejected, but the time guard is disabled by design, and the comment in the YAML presents it as a feature. It also puts a fake date in review.json / REVIEW.md / e2e-manifest.json.
Fix (no weakening of the validator): let each stage own its begin and let the report validate against it.
 - ci-visual / ci-integration write their own `out/reports/e2e/campaign-<stage>.json` (runId from STUDIO_E2E_RUN_ID = run_id-attempt, startedAt = real `now`, command) and pass THEIR identity to their stage via env. Their manifests carry campaignStartedAt equal to it.
 - ci-report (e2e-campaign.mjs report + review-index finish) validates visual against campaign-visual.json and integration against campaign-integration.json (validateReviewEvidence called per stage, or the identity split into two arguments; the unit test keeps its intent), and requires both runIds to be equal. The merged campaign startedAt = min of the two. review:finish needs a small change to read the two files instead of one review-start.json; the artifacts already carry each file, so nothing else has to travel.
 Simpler alternative if the validator must stay untouched: one cheap first job `begin` (ubuntu, no setup, `node scripts/e2e-campaign.mjs begin` only needs node, run by setup-node) that uploads review-start.json; visual/integration `needs: begin`, download it, and export it. Real startedAt, validator untouched; costs ~15 s of serial time and breaks "<= 2 targets per job" slightly, so the per-stage design is preferred.

## F2 (high) Stages are not standalone (guideline rule 2)
justfile:127-148, e2e-campaign.mjs:20-31. `just ci-visual` then `just ci-integration` by hand: each runs `begin`, which has no env, so it creates a NEW random runId and overwrites review-start.json; the visual manifest then carries the old runId and `ci-report` fails with "run identity does not match". CONTRIBUTING documents a manual `eval` to work around it, which is exactly what rule 2 forbids. Also `ci-visual` + `ci-report` with a stale review-start.json from an earlier campaign silently reuses nothing and fails confusingly.
Fix: make `begin` idempotent. Order of precedence: (1) env STUDIO_E2E_RUN_ID/STARTED_AT/COMMAND if all set; (2) an existing out/reports/e2e/review-start.json (valid shape) is reused and exported; (3) otherwise create. `just clean` (rm -rf out) already resets it, and `preflight` keeps its single `begin` after `clean` (it can then just rely on the reuse, drop its own eval). Document "run `just clean` for a fresh campaign" and delete the manual eval paragraph in CONTRIBUTING.md:73-76. If F1's per-stage design is adopted, each stage simply creates/reuses its own file and ci-report checks runId equality, which also removes this problem (stages share only the runId; locally a missing runId env falls back to reading an existing sibling file, else random is fine because the report then reports the mismatch clearly - better: report accepts matching runIds only and says "run ci-visual and ci-integration after the same clean").
Note also `ci-report` locally on a fresh tree prints "review-start.json missing; run ci-visual..." which is fine.

## F3 (medium) report/checks `if: always()` runs on user cancel
ci.yml report (`if: always()`) and checks (`if: always()`). always() still runs after a workflow cancel, spending a full runner and dev-ci (apt + Chromium) to produce a failure. Use `if: ${{ !cancelled() }}` on both: they still run when a needed job failed or was skipped, but not on cancel. The checks logic itself is right (success only; skipped, cancelled, failure all fail). With !cancelled() a cancelled workflow leaves checks cancelled, which blocks the merge as expected.

## F4 (medium) report job installs too much
ci.yml report: `just dev-ci` does apt plantuml/graphviz, uv sync and `playwright install --with-deps chromium`; ci-report needs only node + npm ci (compile, review:finish, node script). ~1 min wasted on the critical path (the report is serial after the 5-min jobs). Fix: either let `dev-ci` take a parameter (`dev-ci profile="all"`, `just dev-ci node`) so the job is still "setup target + ci target", or cache the Playwright browsers (`~/.cache/ms-playwright`, key on the playwright version) to make it cheap everywhere. Same for gallery (needs node only, and uv for nothing).

## F5 (medium) Artifact selection can race with static
ci.yml report: `pattern: reports-*` also matches `reports-static`, which uploads concurrently and is not in `needs`; the report then contains it or not depending on timing. Fix: name the e2e artifacts `e2e-visual` / `e2e-integration` and download `pattern: e2e-*` (or add `static` to report's needs; the first is cleaner). Overlapping files (review-start.json, REVIEW.md, archive/README.md) are overwritten; with F1 per-stage files this overlap disappears for the identity.
