## Spec conformance

### Decision 1: the warning banner

- **Accessibility:** the banner has `role=status` and `aria-live=polite`. The close button is a
  real `<button>` with `aria-label="Close the warning"`, and v29-v32 assert that it takes focus.
- **Open Problems:** the button sends `previewShowProblems`, and the host runs
  `workbench.actions.view.problems`.
- **Closed per document per session:** the page keeps the closed key. The host keeps it in a
  module map keyed by `preview.documentUri`, and `scrollContext` reads the map back by
  `stage.activeDocumentIdentity`. Both are `documentKey(document)`, so they match.
- **Reappears when the warning set changes:** the key is a hash of the sorted messages without the
  `file:line` prefix. The unit tests cover this.
- **Styles:** the stylesheet only; there is no `style=` in the diff. Colours come from theme
  variables, with a forced-colors fallback. The v29-v32 assertions check contrast (4.5:1 for the
  text and buttons, 3:1 for the icon). The screenshots read well in dark and cream.
  "current-theme" is the default mode used by v29 and v30.
- **Toolbar:** the banner does not overlap the floating toolbar. The width is capped and asserted
  in v29-v32, at 900 and 460 px.
- **Scroll-sync anchor:** it does not move. The banner is `position: absolute` in the 40px top gap;
  the h1 stays at 40px, which is asserted both open (v29) and closed (v33).
- **Patch path:** this case is handled. `runtimeContextSettings` does not include the new context
  fields, so closing the banner does not turn later in-place patches into full reloads.

- `previewWarningBannerClosed` stores a key bounded to 32 characters and matching
  `^[0-9a-z]+-[0-9a-f]{8}$`. The map stays bounded by the number of open documents.
- Both handlers require the envelope and a `documentId` that matches `preview.documentUri`, and
  they edit nothing. Allowing them in read-only and untrusted previews is acceptable.
