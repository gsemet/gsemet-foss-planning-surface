## Findings

1. **[blocking] The production wiring of the fix has no test that fails without it.**
   `src/session/features/rendering.ts:222` (the page policy gets the workspace folder in Restricted
   Mode) is the fix for cause 1 (an image in the workspace folder outside the document folder). I
   reverted that line in a scratch copy: all session, core, host-memory and security tests stay
   green. The unit tests call `buildPreviewWebviewHtml` with the workspace root handed in directly,
   and the visual harness (`test/visual/renderFixtures.ts:130`) does the same with `visualRoot`,
   so neither exercises `rendering.ts`. The report admits the workspace-root unit test passes on the
   old code. Constitution section 3 ("a behaviour change comes with a test that fails on the
   previous code") and `task.md` ("unit tests ... that fail today for the reproduced case(s)") are
   not met for this case. Fix: a session-level test through the memory host (as
   `test/session/trustReq.requirements.test.ts` does) with an untrusted workspace folder, a document
   in a subfolder and `../images/x.png`, asserting the image is served (and the local resource roots
   hold the workspace folder); it must fail with line 222 reverted.

2. **[blocking] The new security gate (non-images stay in the document folder) is untested; its
   test assertion is vacuous.** `src/core/security/resource-policy.ts:287` restricts every
   non-image request of a read-only policy to the document folder. I replaced it with
   `const reachable = this.roots;` in a scratch copy: every test stays green. The test meant to
   cover it, `test/session/readOnlyImages.test.ts:117` / `:126`, writes
   `<video src="../../images/data.csv"></video>` in the Markdown, but the render emits no `<video>`
   element at all (checked: zero `<video` in the page html), so `html.includes("data.csv") === false`
   holds whatever the policy does. Fix: assert on the policy directly
   (`createPreviewResourcePolicy(doc, ws, true).resolveResourceDetailed("../data.csv", doc,
   { image: true })` gives `resource-outside-root`, and the same with an `.md` include target),
   and/or use a construct the sanitizer actually keeps (an `<img src="../../images/data.csv">` or a
   `<video>` that survives the render), so the test fails with line 287 removed.

3. **[minor] The image gate trusts the requested extension, not the real file.**
   `src/core/security/resource-policy.ts:286` tests `IMAGE_EXTENSIONS` on `decoded`; after realpath
   (`:334`) the target may be any regular file inside the same root, e.g. `ws/img/x.png` as a
   symlink to `ws/notes/secret.txt`. Impact is low (it is loaded only as an image, so its bytes are
   not shown, and dot-segments and root escape are still refused), but the owner limit says
   "images only". Suggest re-testing the extension on `realCandidate` when the request used the
   image exception, with a unit test for the symlink case.

4. **[minor] "As `<img>`" is enforced by extension, not by element.** `src/session/webview.ts:184`
   passes `{ image: true }` for every page resource (`src`, `poster`, `data`, `srcset`, linked
   stylesheet lookup), so a `.png`/`.svg` path in a `<video>`, `<audio>`, `<track>` or `<source>`
   also reaches the workspace root. Not exploitable as far as I can see (object/iframe/embed are
   removed, CSP has no frame/object source), but it differs from the owner wording; either state it
   in TRUST-002 ("an image file, whatever element loads it") or limit the option to `img`/`picture
   source`/`srcset`.

5. **[minor] Side-by-side diff in Restricted Mode still uses the document folder only.**
   `src/session/features/baselineDiff.ts:54` passes `preview.workspaceRoot` (the document folder
   when read-only), unlike `rendering.ts:222`, so an image of the workspace folder shows in the
   preview but is refused in the diff page of the same panel. Use the same expression (ideally one
   helper shared by both call sites, which also makes finding 1 easier to test).

6. **[minor] TRUST-007 description and normative text differ.**
   `requirements/tiers/swrs/trust-security/SwRS-MDOKFSTUDIO-TRUST-007.md:6-11` (description, hence
   `index.md`) says the read-only preview "also loads the images of the workspace folder that holds
   it", without "unless that folder is broad", which the normative text at `:49` has. Align them.

7. **[note, owner decision] Broad document folder becomes a webview root.** With a document in the
   home folder or in `/`, `previewLocalResourceRoots` now returns that folder
   (`rendering.ts:153-156`), so the webview may load any file below it, the dot-directories
   included, if a URL to it ever reached the page. Today the sanitizer resolves every resource
   through the policy and the CSP blocks scripts, so I see no path, and it is the literal owner
   exception. It is still a loss of defence in depth versus the previous `[]`; the driver should
   surface it to the owner (especially the file-system-root case, which makes every non-dot image
   on the disk loadable) rather than leave it only in the coder's open points.

8. **[note] Documentation.** `docs/known-limitations.md:37-41` describes the read-only resource root
   for includes only; one sentence on Restricted Mode images (document folder, workspace folder,
   allowed formats) would keep the user docs in step with TRUST-002. Optional.
