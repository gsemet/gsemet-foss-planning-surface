## Autonomous decisions

1. **useJar in Restricted Mode**: the JAR stays disabled with the existing message ("PlantUML
   preview is disabled in an untrusted workspace."). The preview does not silently fall back to
   the built-in engine. This keeps the explicit choice predictable and leaves the JAR tests
   unchanged.
2. **Smetana only, no Graphviz wasm** (`viz-global.js` not bundled). This avoids
   `'wasm-unsafe-eval'` and keeps the CSP at zero change, at the cost of layout differences on
   class-like diagrams, which README and CHANGELOG mention.
3. **Bundled `themes.js` (+0.32 MB) and `openiconic.js` (+50 KB)**, so `!theme NAME` and
   `<&icon>` work offline. `emoji.js` (1.8 MB) is not bundled: emoji diagrams show the engine
   error with the useJar hint.
4. **Unsupported detection by source pre-scan**: any `!include*`/`!import` (local, URL or stdlib
   `<...>`) and `!theme ... from`. I measured that the engine reports these through the *success*
   callback with its own error picture, not through `onError`, so the pre-scan is what gives a
   clear message. The file and stdlib loaders refuse everything as a second line of defence.
5. **`RenderOptions.plantUmlEngine` omitted means `jar`**, for API compatibility, so the existing
   pipeline test stays unchanged. The extension always passes the resolved engine. The product
   default is still the built-in engine through the setting default.
6. **A separate `readPlantUmlEngineSettings`** instead of adding `useJar` to
   `PlantUmlConfiguration`. The existing config tests assert the exact shape `{ jarPath }` and
   that only `jarPath` is read.
7. **Dark/light is taken from the luminance of the computed body background**. It works for the
   host themes and for the forced white, cream and dark modes.
8. **Setting order 79** (just before `jarPath` at 80). The setting and message wording is mine.
9. **The package LICENSE ships as `out/bundle/plantuml/LICENSE`**, like KaTeX's.

## Open points

1. **No real VS Code webview check**. The CSP and engine behaviour were verified in Chromium
   with the production policy string, not in VS Code itself. A manual check (or one integration
   scenario under the window lock) of first-render latency and the console in a real webview is
   still to do.
2. **Built-in engine errors are not reported to the host**: no `plantuml-render` diagnostic or
   status line in built-in mode, unlike the JAR path. That needs a webview → host message.
3. **No source-size cap in the built-in path** (the JAR path has 1 MiB). The engine's default
   `maxSvgSize` of 8192 px guards the output, but a huge diagram still blocks the webview main
   thread while it renders.
4. **Fidelity of Smetana vs Graphviz** is not compared fixture by fixture.
5. The Restricted Mode + useJar message could also suggest unticking `useJar`. I left it
   unchanged because the existing JAR tests assert it.
6. `npm run package` fails locally only because of the shared `node_modules` drift (see the
   bundle size section). CI should be the judge.
