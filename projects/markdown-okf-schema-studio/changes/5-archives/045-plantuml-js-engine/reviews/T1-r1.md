## Spec decisions

1. **Built-in engine by default, bundled like Mermaid.** Met. There is a separate esbuild IIFE entry
   (`esbuild.mjs:32-43`) that writes `out/bundle/plantumlPreview.js`. `.vscodeignore` excludes
   `node_modules/**` but not `out/bundle/**`, so the bundle ships and the 6.9 MB package does not.
   That is the same pattern as Mermaid. `package.json` and the lockfile change only by the one
   exact pin `@plantuml/core@1.2026.9` (license MIT, LICENSE copied to `out/bundle/plantuml/`).
2. **`plantuml.useJar` boolean, default false.** Met. `readPlantUmlEngineSettings` accepts only a
   real `true`. The JAR pipeline is unchanged when the option is on. `jarPath` is unchanged apart
   from its description. CHANGELOG and README both say that existing `jarPath` users now get the
   built-in engine until they tick `useJar`.
3. **Restricted Mode.** Met. When useJar is off, the built-in engine runs and the pipeline never
   calls the spawner, trusted or untrusted (`renderPipeline.ts:214`). The
   `plantUmlEngine.test.ts` test proves this with a counting spawner. When useJar is on in an
   untrusted workspace, the existing refusal runs and starts no process.
4. **No network or CSP widening.** Met. `csp.ts` is untouched: `connect-src 'none'`, and
   `img-src` allows only cspSource and `data:`. In the shipped bundle, the stdlib loader adds a
   `<script>` only when `PLANTUML_STDLIB_LOADER` returns `false`. The installed loaders always
   call `err` and never return `false`, and no `PLANTUML_STDLIB_BASE` is set. I found no `eval`,
   `new Function` or Worker in the bundle. For unsupported features, a pre-scan of the source
   shows a clear message with the useJar hint (v12).
5. **Tests.** Met. Unit tests cover the setting resolution and trust. Visual scenarios v10 (light),
   v11 (dark) and v12 (unsupported) are present. The existing JAR tests (plantUmlRenderer,
   mystFeatures, the config tests, contentPatch T34, visual v04-v07) are unchanged. The two
   edited assertions (the exhaustive settings list and the scenario count 300 → 303) follow
   the repo convention. No test was weakened.

## Security, correctness and races

- **XSS from the engine output.** The SVG is placed only as a `data:image/svg+xml` `<img src>`
  (`plantumlDiagram.ts:99-108`). Scripts and links inside it stay inert, which matches how
  Mermaid output is handled (`mermaidPreview.ts`). Error text goes through `textContent`. The
  source is read with `textContent` from the placeholder, which the host escaped. The page
  `script-src` is nonce-only, so DOM nodes the engine builds while measuring cannot run script.
- **Shell and patch interplay.** Injecting the script changes `shellKey`. Switching useJar on or
  off, or a document gaining its first diagram, therefore reloads the whole page instead of
  patching it, and `localResourceRoots` is part of the patch condition. On a patch, new elements
  have no `data-render-state` and are drawn again from the promise cache, so there is no visible
  flash.
- **Theme race.** The guard on `data-plantuml-dark` after the `await` (`plantumlDiagram.ts:176`)
  drops stale variants during fast light/dark switches. Results drawn into detached elements
  after a patch are harmless.
- **Engine choice vs render.** `updatePreview` chooses the page renderer from
  `result.plantUmlEngine`, not from the live setting. This is correct, and it avoids a race
  between a settings change and an in-flight render. `applyPlantUml` is a no-op on built-in
  renders, because the results are empty and so are the diagnostics.
- No inline `style=` is added. The message reuses `.myst-plantuml-error`.

## Findings

1. **minor**: `src/webview/plantumlDiagram.ts:162` has no source-size cap on the built-in path
   (the coder's open point 3). The JAR path refuses sources over 1 MiB. Here an untrusted
   document can now hand any size of source to a synchronous engine on the webview main thread.
   The impact is limited to freezing the preview tab. A size cap would not stop preprocessor
   loops (`!while`), and `maxSvgSize` bounds the output. Fix (recommended, cheap): reuse the
   same 1 MiB limit before `outcome()` and show an "unavailable" message that mentions useJar.
   Not required for this CR.
2. **minor**: `src/webview/plantumlPreview.ts:33-37` renders every diagram synchronously in one
   loop at load. A page with many diagrams blocks the first paint and scroll sync until all of
   them are done. Fix (optional): yield between diagrams, for example with `setTimeout(0)` or
   `requestIdleCallback`.
3. **minor**: there is no automated check that the engine works under the real page CSP
   (`test/visual/renderFixtures.ts:262`). The visual harness injects the bundle without the
   production CSP or nonce. The CSP claim rests on the coder's manual Chromium check (open
   point 1). Fix: before merge, the driver runs one real-window check under the window lock
   (open a document with a PlantUML fence and confirm a rendered `img.myst-plantuml-image`), or
   adds the production CSP meta to the built-in visual pages.
4. **minor**: no unit test covers `buildPreviewWebviewHtml` (`src/preview/webview.ts:289-299`).
   Such a test should check that it injects the nonce'd `data-sphinx-preview-plantuml` script
   only for `builtin` plus a figure, and never for `host`. It should also check the
   `out/bundle` resource root in `extension.ts:1111-1115`. The visual scenarios cover this only
   indirectly, through a harness that has its own injection. Fix (optional): add a small test
   next to the existing webview HTML tests.
5. **minor**: no host diagnostic is reported for built-in engine errors (the coder's open point
   2). The JAR path reports a `plantuml-render` status or Problems entry. With the built-in
   engine the message appears only in the page. The spec does not require it, so it is fine as a
   follow-up: a webview → host message.
6. **nit**: the message shown for useJar in Restricted Mode could also suggest unticking
   `useJar` (the coder's open point 5). Leaving it unchanged keeps the existing JAR tests
   untouched, which the spec requires. This is a follow-up.
7. **nit**: the `style-src-attr` CSP violation reports in the console on every render are
   documented as harmless (`docs/preview-lifecycle.md`). They will add noise to the webview
   console when users debug other issues. Acceptable.

## Coder's self-taken decisions

All nine are acceptable. When useJar is on in Restricted Mode, the preview does not fall back to
the built-in engine, which is the predictable behaviour and keeps the JAR tests unchanged. Layout
is Smetana only, with no wasm, so the CSP is unchanged; the README and CHANGELOG disclose this.
Bundling the themes and OpenIconic, and leaving out emoji, is a reasonable trade-off for bundle
size. Detecting unsupported features with a pre-scan is justified by the engine reporting
includes through its success callback. An omitted `plantUmlEngine` means `jar` for API
compatibility; the extension always passes the engine, so the product default is the built-in
engine. The separate settings reader and dark mode taken from the body background luminance are
both fine.
