## Spec decisions 8 to 10

8. **`{uml} path.puml` and a body-less `{plantuml} path.puml`.** Met.
   - `mystRenderer.ts` `plantUmlFileRequest` / `resolvePlantUmlFile` read the file through
     `context.readDiagramFile`. In `renderPipeline.ts` that is `readBoundedText(resourcePolicy, …)`
     with the same `resourcePolicy` instance as `{include}`.
   - `readBoundedText` is now also the read path of `{include}`, so the two share one function
     (policy, 5 MiB cap, UTF-8). There is no weaker parallel path.
   - The file is charged to the include budget (expansions and characters). It is added to
     `dependencies`, and a missing candidate inside the roots is added too, so it renders again.
   - In Restricted Mode, `createPreview` already passes the document folder as `workspaceRoot`
     (`extension.ts:4562`), so `{uml}` keeps to the document folder.
   - Missing, outside, absolute, too-large and empty `{uml}` each give a clear message in a
     non-diagram `div.myst-plantuml-file-error`, plus a warning diagnostic. The JAR receives the
     file text (unit test).
9. **Local `!include` family in the built-in engine.** Met.
   - Host side, `resolvePlantUmlInclude` (`src/render/plantUmlIncludes.ts`):
     - It builds a fresh `createPreviewResourcePolicy(documentDir, trusted ? workspaceRoot :
       undefined)` and reads through `readBoundedText`. That is the same policy class, the same
       `isWithin` (`path.relative`-based, so there is no prefix or separator bug), the same
       realpath symlink-escape check and the same 5 MiB cap.
     - An absolute request is refused by the existing policy (`decoded.startsWith("/")`). A scheme
       or `<…>` request is refused up front. A non-absolute `from` is refused.
     - A forged absolute `from` cannot widen anything, because the candidate is still checked
       against the roots (unit-tested).
     - Restricted Mode drops the workspace root (the live `vscode.workspace.isTrusted`), so only
       the document folder and below are served.
   - Page side (`plantumlDiagram.ts`):
     - Nested includes resolve against `from` (the host's real path).
     - The limits are depth 8, 64 requests and 1 MiB of total text, with cycle detection through
       the parent chain.
     - Renders are serialized, so the global loader always belongs to the current diagram.
   - Dependencies are watched through `PlantUmlIncludeWatch` (bounded at 1024, cleared on a
     document switch) and `refreshReferencedPath`, and the page redraws only the diagrams that
     used files.
10. **Still refused.** Met.

## Message protocol

- The validator (`previewMessages.ts`) bounds `path` (4096 characters, non-blank), `from` (null or
  a bounded non-empty string) and `editId`.
- The handler only reads under the policy. The webview cannot read outside the policy roots, and
  `connect-src 'none'` leaves it no exfiltration channel.
- The gate bypass only checks `documentId`. That is acceptable, because a document switch changes
  `activeDocumentPath` and so forces a full page reload, not a content patch
  (`extension.ts:1175`).
- Late answers are dropped by `installHostRequests` (unknown or settled id) and by the
  per-element render token.
- There is a separate request instance, so `cancelAll()` on an editor teardown does not drop
  include reads. That is a good call.

## Findings

1. **minor**: `src/webview/scrollSync.ts:257` builds PlantUML edit ids as `"plantuml-" + seq`,
   which restarts at 1 on every page load. The other host-request instances embed
   `context.requestId` (`scrollSync.ts:231`, `:245`). If an answer the host posted to the old page
   is delivered after a same-document full reload (a shell change), it could settle the new
   page's `plantuml-1` request for a different file. The diagram would then show the wrong
   (policy-bounded) text, and that result is cached. The report's claim that "after a page reload,
   old answers cannot match" does not hold as written.
   - Fix (one line): `nextEditId: () => "plantuml-" + context.requestId + "-" + (++plantUmlFileSequence)`,
     or a random per-page prefix.
   - The window is narrow and there is no security impact, so this is not blocking.
2. **minor**: `src/extension.ts:2369`: the watch path for a missing file is
   `canonicalPath(candidate)`, which falls back to `path.resolve`, a non-real path. When the file
   is created, `refreshReferencedPath` computes `canonicalPath(filePath)` with `realpath`. If the
   document folder sits under a symlink (for example macOS `/tmp` → `/private/tmp`), the two
   differ and the redraw on creation is missed.
   - Fix (optional): canonicalize the nearest existing parent directory and then join the
     basename.
   - `{include}` dependencies probably share this edge case.
3. **minor**: `src/render/plantUmlIncludes.ts:96` serves each `!include` file up to 5 MiB, while
   the page refuses more than 1 MiB per diagram in total. A 5 MiB file is therefore read and posted
   to the webview only to be refused there.
   - Fix (optional): pass `maxBytes = MAX_PLANTUML_SOURCE_LENGTH` (or a small multiple of it) to
     `readBoundedText` for PlantUML includes.
   - Decision 9 says "the same bounds and cap", so the current choice is defensible.
4. **nit**: `docs/preview-lifecycle.md:27` is over the 100-character wrap ("refuses every request
   and it fetches nothing. While it builds a picture the engine sets `style` attributes on SVG").
5. **nit** (carried over from the round-1 item 3, coder open point 1): there is still no
   real-window check of the bridge under the production CSP and nonce. Before the merge, the
   driver should run one integration or manual check under the window lock: a `{uml}` file and a
   local `!include` render in a real webview.

## Coder's own decisions

All 10 are acceptable.

- **The async message round trip instead of host pre-resolution.** It is correct given the
  verified async loader, and it handles `%dirpath()` paths.
- **Serialized renders.** They are required for the global loader to know which diagram is
  asking.
- **Cycle refusal on top of the depth limit.** This is a sensible guard against `_many`
  self-cycles. The side effect, a mutual `!include` now giving a message where PlantUML would
  skip it silently, is a fair trade.
- **The gate bypass on `documentId` only.** It is justified above.
- **Leaving the useJar hint off file errors.** That is right, because the JAR would not fix a
  missing file.
- **Refusing `!includedef`.** It is consistent with the loader not routing it.
- **`{uml}` with a body renders the body.** That matches `{plantuml}`.
- **The error div.** Making it a non-`.myst-plantuml-diagram` element avoids the message being
  drawn as diagram source.
- **The PR body update.** Open point 5, updating the PR body, is the driver's job.
