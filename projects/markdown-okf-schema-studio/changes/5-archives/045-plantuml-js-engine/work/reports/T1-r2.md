## Summary

- Decision 8: `{uml} path.puml` and a body-less `{plantuml} path.puml` (an option-only body such as
  `:caption:` counts as empty) are read by the host during the MyST render, through the same
  resource policy, 5 MiB cap and include budget as `{include}`. The file text becomes the diagram,
  so both engines (built-in and JAR) render it. The file is a render dependency. A missing file
  inside the roots is a dependency too, so creating it renders again. A missing file, a path
  outside the bounds, an absolute path, a too-large file, or `{uml}` with neither file nor body
  shows a `p.myst-plantuml-error` message in a `div.myst-plantuml-file-error`. That div is not a
  `.myst-plantuml-diagram`, so neither engine reads the message as diagram source. Each of these
  also emits a warning diagnostic.
- Decision 9: local `!include` / `!include_many` / `!include_once` / `!includesub` in the built-in
  engine.
  - **Loader API, verified in Chromium** with the real `@plantuml/core` 1.2026.9: it is
    **asynchronous**. The loader may answer later. The engine re-renders when every answer is in,
    and `renderToString` calls back only after the final pass. The engine processes queued
    renders one at a time.
  - So the design is a message round trip, not host pre-resolution. The webview loader asks the
    host, and the host applies the bounds.
  - The page renders one diagram at a time, so every loader call belongs to the diagram being
    drawn.
  - Top-level includes resolve next to the document, or next to the `.puml` file of a `{uml}`
    diagram, or next to the included document for a diagram inside `{include}`
    (`data-plantuml-base`). Nested includes resolve next to the including file (`from` = the id
    the host gave, its real path).
  - Limits: depth 8 (the same as `{include}`), 64 files per diagram, 1 MiB of text in all
    (source plus includes), and cycle detection through the parent chain.
  - Restricted Mode: the host resolver drops the workspace root when untrusted, so only the
    document's folder and below are served.
  - Files the host served (or found missing inside the roots) are remembered. A watcher event on
    one of them posts `previewPlantUmlIncludesChanged`, and the page forgets the cached pictures
    that read files and draws those diagrams again.
- Decision 10: `!includeurl`, `!include http(s)://…` (any `scheme://`), `!include <…>` (also
  `_many`/`_once`/`sub`), `!includedef`, `!import` and `!theme … from` are still refused by the
  pre-scan with the useJar message, and the scan also runs on every delivered included file
  ("line N of file.puml"). The loader refuses `request.kind === "theme"` too. No network, **CSP
  unchanged**, `connect-src 'none'` stays.
- Round-1 minor: the built-in path now refuses sources over 1 MiB, the same constant as the JAR
  path (`MAX_PLANTUML_SOURCE_LENGTH`, moved to the new `src/render/plantUmlLimits.ts` and
  imported by `plantUmlRenderer.ts`). The text matches the JAR's: "The PlantUML source exceeds
  the 1 MiB preview limit." The engine is never called for such a source.

## Message protocol and races

- Bundle → page: `document.dispatchEvent(new CustomEvent("studio:plantuml-file-request", { detail:
  { request: { path, from }, accepted, respond } }))`. The bundle cannot call `acquireVsCodeApi`,
  because the page script owns it. If no listener sets `accepted`, the request is refused at once.
- Page → host: the registered `previewPlantUmlInclude` (`path` ≤ 4096 chars, non-blank; `from`
  null or a non-empty string ≤ 4096; `editId`). It is sent through a **separate**
  `installHostRequests` instance with ids `plantuml-N` and a 10 s timeout. It is separate because
  the editor's `cancelAll()` on every content patch would otherwise drop include requests
  silently.
- Host → page: `previewPlantUmlIncludeResult` with the same `editId` (`ok/id/text` or
  `ok:false/reason`). An answer with an unknown or already-settled edit id is dropped. After a
  page reload, old answers cannot match.
- Stale gate: `previewPlantUmlInclude` bypasses the version/request-id gate, like
  `previewEditFlushed`. It is answered when the preview is alive and `documentId` is the
  preview's document. Reason: a read does not depend on the document version, and a page one
  render behind would otherwise wait 10 s and cache nothing useful. The resource policy bounds
  every read whatever `from` says (unit test: a forged `from` outside the roots is refused).
- Re-render races: each `render()` takes a per-element token, and a superseded result (theme
  switch, include change) is dropped. A render with a refused or unsupported include is never
  cached, so it is asked again on the next render.

## Autonomous decisions

1. **Message round trip, not host pre-resolution**, because the loader is async (verified). It also
   handles variables in include paths (`!include %dirpath()/x`), which a host pre-scan could not.
2. **The page renders diagrams one at a time** so the global loader knows which diagram is asking.
   The engine already processes renders sequentially (measured), so this costs nothing.
3. **Include-cycle refusal** through the parent chain, in addition to the depth limit.
   `!include_many` self-cycles never reach the loader a second time (the engine reuses the
   answer within a render; measured), so a depth limit alone cannot stop them, and the engine's
   only stop was `maxSvgSize`. Side effect: a mutual `!include` (not `_many`), which PlantUML
   would otherwise skip silently, is refused with a message.
4. **Limits**: depth 8 (like `{include}`), 64 files per diagram, and 1 MiB for the source with all
   its includes (the JAR source cap). Each file is capped at 5 MiB by the host (the `{include}`
   cap). The `{uml}` file is charged to the `{include}` budget.
5. **The include request bypasses the version/request-id gate** (documentId only). Explained above.
6. **No useJar hint on include failures** (missing, outside, cycle, limits): the JAR would not help.
   The hint stays for URL, stdlib, `!import`, `!theme … from`, emoji and engine errors.
7. **`{uml}` with a non-option body renders the body** (args ignored), the same as `{plantuml}`
   with a body today. `{uml}` with an option-only body is the file form. Options such as
   `:caption:` are accepted but not rendered.
8. **Missing files inside the roots are watched**, for both `{uml}` (render dependency) and
   `!include` (include watch), so creating the file draws the diagram.
9. **`!includedef` is refused** as unsupported: the engine does not route it to the loader.
10. A `{uml}` error is a `div.myst-plantuml-file-error` (not a figure), so the JAR pipeline and the
    built-in engine never try to draw the message text. It reuses the `.myst-plantuml-error` style,
    so there is no new CSS.
