# T1 round 1 report (CR 175, host guard for block ranges)

## Decision from evidence (important deviation from the brief)
The renderer legitimately sends ranges that END on a blank line: ul/ol and li of loose or
separated lists get `data-end-line` = the blank separator line (e.g. `ul 6-12`, `li 7-8`,
`li 9-10`, `ol 13-15`, `ul 16-18`, where the last line is blank). So the edit guard checks
only: integers/bounds (already done by `sourceRangeForLines`, text unchanged: "stale") and a
BLANK FIRST LINE. A blank last line is accepted (documented in code and SwRS). The shifted-alert
shape (blank first line) is caught. Case (c) "ends on blank line refused" is therefore NOT
implemented, deliberately. Frontmatter rule not applied (only shape is checked).
The page message `previewEditOpen`/`previewEditSave` carries no block kind: no kind check added.
`planInsertion` already refuses insertAfterLine past the end / non-integer (and page schema
validates integer >= 0), so the insertion path needed no guard.
