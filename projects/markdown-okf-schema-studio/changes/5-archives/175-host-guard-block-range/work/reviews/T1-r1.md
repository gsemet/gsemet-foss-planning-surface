## 1. Correctness, and the blank END line decision

Independent probe with `renderMyst` (script outside the repo) confirms the coder's claim, and it is
wider than lists:

| Document | Ranges ending on a blank line |
| --- | --- |
| tight list `- a\n- b\n\nP` | `ul 1-3`, `li 2-3` |
| loose list | `ul 1-4`, `li 1-2`, `li 3-4` |
| nested list | every `ul`/`li` |
| ordered loose list, two blank lines after | `ol 1-5`, `li 3-5` (two trailing blanks) |
| list inside an admonition | inner `li 2-3` |
| definition list `Term\n: def\n\n...` | `dl 1-6` |

No renderer range starts on a blank line in any probe (lists, alerts, frontmatter, footnotes,
html comments, include, indented code, tab-set, grids, review comments, labels, `%` comments).

Safer partial rules considered:
- "end blank AND not a list/li": the host message carries no block kind (`previewEditOpen` has
  only `line`/`endLine`), and the definition list (`dl`, first line is plain text) ends on a blank
  too, so a "first line is a list marker" heuristic would still refuse dl. Not viable host-side.
- "compare against trailing-blank-trimmed": the trimmed range is non-empty whenever the first line
  is non-blank, so this adds nothing over the implemented rule.
- "end blank AND the line before end is blank": the ordered list with two blank lines after
  (`ol 1-5`, `li 7-9` in a double-spaced doc) breaks it.

Conclusion: not refusing a blank last line is correct and NOT a blocker. Residual gap (documented
in code and SwRS): a +1 shift of a multi-line block that lands on its trailing blank line is not
caught. The historical bug (-1 shift: blank line + `### heading`) and any -1 shift of a block
preceded by a blank line are caught. Follow-up idea (separate CR, optional): the page sends the
mapped tag (or the renderer trims list/dl end lines), which would allow the end-line rule.

Logic check: `currentSourceEdit` keeps `sourceRangeForLines` first, so out-of-bounds keeps the
existing "stale" text (SwRS-BLOCK-216 unchanged), then `checkBlockLines`; refusal is posted through
`postEditSourceError` (flush warning included) before any `openPageEditor`/`beginActiveBlockEdit`,
so no lock is taken and nothing is written. Correct.
