# T1 round 2 report - CR 109 front-matter key column

## Root cause (exact)
The round-1 before-shot did not reproduce the user's image because its fixture had a short description and no code block. The trigger is a long value next to short keys: the preview-wide `overflow-wrap: anywhere` on `th`/`td` gives every cell a one-letter min-content width, so the auto table layout shares the width by max-content. A long description (hundreds of characters) has a huge max-content, so the key column gets about 5% of the table (37-43 px at a 700-1100 px pane) and "name", "description", "metadata" and the header "Names" break letter by letter. Not the code block, not `container-type`; the `<=640px` block uses `table-layout: fixed` (50/50) and does not collapse.
- Reproduced on 5aff39e in the visual harness (fixture 65, widths 700-1100: key column 37-43 px; at 400-600 px the fixed-layout block gives 168-252 px) and in a REAL VS Code window (pane 786 px, Cream and Default Dark Modern: key column 38 px, "Na/me/s", "na/m/e", "de/sc/rip/tio/n").
- Round-1 code already fixes the user's case (key column 87 px, one line, in harness and real window). The user probably ran a build without round 1; round-1 tests just did not cover it.
- One gap left in round 1: when every key is shorter than the header label (id, tags, note), the key column is only as wide as the keys (46 px) and "Names" breaks ("Nam/es", header 44 px high).

## Fix (round 2)
- `src/core/preview/styles/propertiesStyles.ts`: `.okf-properties thead th:first-child` is `white-space: nowrap; overflow-wrap: normal` (id-scoped), so the key column is at least as wide as the "Names" label. Header comment updated. Nothing else changed in src.
- `src/core/frontmatter/propertiesTable.ts`: unchanged in round 2.
