## Findings

1. (Must fix, bug 1 for the popover) src/page/modules/commentThreads.ts:598-600. `open()` calls `position(target)` before `paintReply()` and `paintActions()`, and those fill the Resolve / Delete row (and any error line). `floatingTop` therefore measures a popover shorter than its final height. Near the bottom of the window, the popover can still be cut off by the height of that row, or, when it flips above its text, it overlaps the text by that height. The position is corrected only at the next scroll. The test misses this because the fake's height is fixed at 200 px. Fix: call `position(target)` after the painting, at the end of `open()`, or at the end of `paintReply()` while `openTarget` is set. Also add a test whose popover height grows during painting.
2. (Should fix) src/page/modules/commentThreads.ts:241 and :697-703. In the popover, Escape while the question shows calls `paintDiscard()`, which removes the focused Keep editing button without giving focus back to the reply text area, so focus falls to the body. Clicking Keep editing (:687-690) does restore it, and so does the compose box's `keepEditing`. SwRS-REVIEW-217 says Escape works "as Keep editing" and that after Keep editing "the text area has the focus". In the same way, `paintDiscard` returns early (:236) when the question goes, so the popover is not placed again after it shrinks. If it sits above its text, a gap is left until the next scroll. Fix: focus the reply input and call `position(openTarget)` when the question is removed.
3. (Should fix) src/page/modules/commentThreads.ts:237-240. `paintDiscard` runs from every `paintReply()`, including asynchronous ones (the reply or resolve answer from the host, timeouts, a re-apply), and each time it moves focus to Keep editing. While the question shows, a host answer that arrives steals focus from wherever the reader is. Move the focus only when the question is first created.
