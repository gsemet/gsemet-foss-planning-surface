## Findings

### F1 (blocking): the SwRS and the setting text claim more than PlantUML enforces

DIAG-084 (description and normative text) says the process "allows only files under the workspace
folder". The new `useJar` description says "files outside the workspace ... are refused". Re-run with
PlantUML 1.2026.8 (the current Homebrew release, the coder's second version) under exactly the
configuration in the diff, with both the env and the `-D` args:

- an absolute include of a file outside the workspace is refused (good)
- an include path that leaves the workspace through parent-directory segments is **read**
- an absolute include into a sibling folder whose name starts with the workspace folder name is **read**
  (a trailing separator on the allowlist path does not change this)

Both gaps come from how PlantUML checks paths against the allowlist, not from this code. They do mean the
"refuses outside ones" claim in `reports/T2-r1.md` is only partly true, and the requirement as written
does not hold.

Required:
- Reword DIAG-084 and the setting description to state what the extension sets (the ALLOWLIST profile
  with the workspace folder as the allowlist path, and the size limit). Do not promise that PlantUML
  enforces the boundary.
- Add a short "Known issue" note in DIAG-084 that says the JAR's allowlist check does not fully confine
  includes to the workspace. Keep it generic, with no payload.
- File a backlog item for the residual (for example, resolve `!include` lines in the extension before the
  JAR runs, or refuse sources whose includes leave the root). Per the project rules, requirements
  describe current behaviour, and the bug is recorded as-is plus a backlog fix.
- Correct the verification note so that it records what was actually observed.

### F2 (blocking): the user docs are now wrong (DoD: "Docs updated when a user-visible behaviour changes")

`docs/user/plantuml.md` lines 36-41 still tell users to tick `useJar` for URL includes (`!includeurl`,
`!include https://...`) and `!theme ... from`. It also says the JAR "resolves `!include` lines itself",
with no limit. Under ALLOWLIST with no URL allowlist, remote includes are now refused. Update that
paragraph: the JAR handles the standard library and includes inside the workspace folder; URL includes
and files outside the workspace are refused. Mention the new behaviour in the CHANGELOG if the project
keeps one for user-visible changes.

### F3 (minor, fix in the same round): a relative JAVA_HOME is resolved in two different places

`resolveJavaCommand()` runs `statSync` on `JAVA_HOME/bin/java` relative to the extension host's cwd.
`spawn` then runs that relative command from `cwd: workspaceRoot`. The binary that was checked may not be
the binary that runs, and the one that runs can sit inside the workspace. Accept JAVA_HOME only when
`path.isAbsolute(javaHome)` is true, and add one assertion to the JAVA_HOME test.

### F4 (minor, optional): the PATH command honours the profile only on recent PlantUML

The PATH command gets the env variables but no `-D` args, because its launcher owns the java call. With
1.2026.8 the env alone works (an outside absolute include is refused, an inside include is read). Older
jars, such as 1.2020.20, ignore `PLANTUML_ALLOWLIST_PATH` from the environment and refuse all local
includes. One sentence in the docs ("needs a recent PlantUML") is enough. The coder already listed the
missing `-D` args as an open point.

### F5 (nit)

- In DIAG-084 the new "Method:" bullet sits above an empty line, before the existing Method bullets. Put
  it in the same list.
- `PLANTUML_LIMIT_SIZE=4096` equals PlantUML's default. It still meets the task (the limit is now explicit
  and pinned). Mention it in the report so that nobody reads it as a tighter limit.
