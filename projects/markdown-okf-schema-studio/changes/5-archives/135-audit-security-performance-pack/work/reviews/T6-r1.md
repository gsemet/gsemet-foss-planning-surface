## Findings

1. `src/session/features/viewState.ts:69-74` (the `previewRefresh` handler, the page's Refresh
   button, SwRS-MDOKFSTUDIO-LIFE-032) does not call `manager.sharedRenders.invalidate()`. Only the
   command path does (`previewManager.ts:662`, `refreshActive`). The new LIFE-039 row says "a
   refresh is requested → the next request renders again instead of joining a finished render",
   and LIFE-032 says the Refresh button "renders again". Scenario: previews A and B of `a.md`.
   B renders revision 5, for example on show (`renderIfDirty`) or after a dependency event. While
   that render runs, or within 250 ms after it ends, the user clicks Refresh in A because an input
   the watchers missed has changed. A's `queue.refresh` joins B's render, and no new render runs.
   A shows output that the user explicitly asked to replace, which contradicts the SwRS row.
   Fix: invalidate in the `previewRefresh` handler, or better, inside one helper used by both
   refresh paths. Add a test: two sessions of one document, page refresh in one session inside
   the window, expect 2 renders.

2. (minor, no change required) `src/session/sharedRenders.ts:68-73`: when `invalidate()` runs
   while a render is in flight, the entry leaves the map but its `.then` still opens the 250 ms
   window and holds the base stage that long. Nothing can join it, so this is harmless today.
   A comment, or skipping the window when `!created.inMap`, would make the intent explicit.

3. (minor, no change required) `docs/preview-lifecycle.md:81-86` lists lifecycle guarantees
   ("explicit refresh produces a newer request…") but says nothing about hidden previews
   rendering on show or about shared renders. This is not strictly user-visible. A one-line
   addition would keep the lifecycle doc complete. Leave it to the driver.
