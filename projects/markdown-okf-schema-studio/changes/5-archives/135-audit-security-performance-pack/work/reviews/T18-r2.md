## Round-1 findings

1. **Finding 1 (overrun thrash): fixed.**
   - `overrunMs()` is now `max(maxDebounceMs, 2 x lastWallMs)`. `lastWallMs` is the wall-clock time
     of the last completed build, measured from the same `startedAt` as `elapsed`, so both sides use
     the same measure. `renderMs` drives only the adaptive wait. With the product floor of 1 s, no
     build is aborted before it has run 1 s, which is well above the cold start measured in round 1
     (53 to 118 ms).
   - After an abort, both estimates are raised to the elapsed time (at least 1 s). They reset when
     the next build completes. LIFE-039 states this ("until a render completes").
   - `renderWorker.ts`: a job is posted only once the thread sent `ready` (`Job.posted`). An abort
     before that rejects the render, does not count it in `aborted`, and calls `release(handle)`, so
     the starting thread is kept (for a waiter or as the idle thread). When `ready` later arrives
     with no job, nothing is posted. When a waiter takes over, `acquire` finds the starting handle
     and its job is posted on `ready`. I found no path that terminates a thread that has not
     posted `ready`, except dispose and idle stop.
   - The new buildQueue test is the case the review asked for (render 2 ms, build 60 ms of wall
     time, newer edit due at 40 ms, not aborted, newer build starts right after). On round-1 logic
     the limit would be 40 ms and the test would fail.
   - Changing `maxDebounceMs` to 200 in the round-1 abort test is legitimate. That test was added
     in round 1, and the arithmetic matches the new rule: limit `max(200, 200)`, abort at 250 ms,
     not at 249 ms.

2. **Finding 2 (untested lifecycle branches): fixed.** The 4 stub-worker tests are real and
   meaningful:

     time, and the 3rd death sets `disabledReason`. The 4th render then goes to the `fallback`
     stub (`fallbackRenders` 1, no new thread).
   - Busy worker: `started` stays 1. The echo `"slow:150,fast"` proves the same thread rendered

   - Abort during the cold start: `"next"` alone proves the aborted text was never posted, with
