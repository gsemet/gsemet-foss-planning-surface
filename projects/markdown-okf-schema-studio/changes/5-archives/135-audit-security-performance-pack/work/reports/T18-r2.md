## Files changed in this round

- `src/node-services/build/buildQueue.ts` (finding 1):
  - New `lastWallMs`: the wall-clock time of the last completed build. `overrunMs()` is now
    `max(maxDebounceMs, 2 x lastWallMs)`, so the overrun compares wall time with wall time. The floor
    (1 s in the product) covers a thread restart: a small document is never aborted.
  - `durationOf` (`renderMs`) still drives the adaptive debounce only.
  - An abort raises both estimates to the time the aborted build ran, until a build completes.
  - Builds under 10 ms leave the wait at `debounceMs` (`MIN_ADAPTIVE_BUILD_MS`). Without this, the
    existing test "still renders a build whose buffer already moved on" failed once in 7 runs. That
    test mocks `setTimeout` but not `Date`: a real 1 ms tick made the wait 2 ms instead of 0. Product
    behaviour does not change, because twice a build under 10 ms is below the 40 ms debounce.
- `src/node-services/renderWorker.ts` (finding 1):
  - A render is posted to a thread only once the thread posted `ready` (`Job.posted`).
  - An abort before that rejects the render as canceled, keeps the starting thread and releases it
    for the next render. It is not counted in `aborted`.
  - Never terminating a cold thread removes the restart cascade the review described.
- `test/node-services/build/buildQueue.test.ts`:
  - New test "never aborts a build of a small document whose wall time exceeds its reported render
    time" (the review's case: render 2 ms, build 60 ms wall, newer edit due at 40 ms).
  - The round-1 abort test now sets `maxDebounceMs: 200`, so the same rule runs at small numbers. Its
    debounce-after-abort assertion moves from 500 to 200 (the bound). This is my own round-1 test;
    no assertion that existed before T18 changed.
- `test/node-services/renderWorker.test.ts` (finding 2): a `stubWorker(root, readyMs)` script written
  to a temp dir, plus 4 tests:
  - A ready worker that dies during a render (3 times): each render rejects with "stopped during the
    render". After the 3rd, `disabledReason` is set and the 4th render runs in-process (`fallback`
    stub).
  - Two concurrent renders: the second waits (`started` stays 1), then the same thread renders it
    after the first.
  - A waiting render whose signal aborts: it rejects as canceled and never reaches the worker. The
    stub echoes the texts it received, which proves this. `aborted` stays 0.
  - A render aborted while its thread still starts (ready after 200 ms): it rejects as canceled, the
    thread is kept (`started` 1, `aborted` 0) and never received it, and the next render uses it.
- Requirements and docs (findings 1 and 4):
  - `SwRS-MDOKFSTUDIO-LIFE-039`: description and normative text: abort only after more than 1 s and
    more than twice the wall-clock time of the last render. Rows added: under 10 ms, and the small
    document that is not aborted. The overrun row is now 600 ms / 1.25 s and states that the estimate
    lasts until a render completes. Verification notes updated. Lifecycle `index.md` refreshed with
    `okfreq lint`.
  - `SwRS-MDOKFSTUDIO-LIFE-004`:
    - The nominal THEN now says only that the MyST render runs in a worker thread, not on the
      extension host thread.
    - New rows: abort while the thread starts, and abort of a waiting render.
    - The verification notes list the 4 stub tests. Only the idle stop stays untested.
  - `CHANGELOG.md`: "The MyST render of the preview no longer runs on the extension host thread...".
    The claim that VS Code no longer freezes is gone.
  - `docs/preview-lifecycle.md`: the same scoping (the sanitizer and the source mapping still run on
    the host), and the new overrun rule.
  - `requirements/tiers/log.md`: the overrun rule.
