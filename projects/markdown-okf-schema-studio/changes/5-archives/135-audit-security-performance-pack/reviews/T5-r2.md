## Round-1 findings

### F1 (CSP splice fails open): fixed

`injectContentSecurityPolicy` now splices only when the text before the first `<head ...>` match is
exactly `SERIALIZED_PREFIX` (optional doctype, comments, `<html` with double-quoted attributes);
anything else goes to `injectContentSecurityPolicyInTree`. This fails closed: a head-like text inside
a root attribute leaves an open quote in the prefix, which the pattern rejects.

Probes on the worktree build, with the policy checked as a real `<head>` child after a parse5 re-parse:

- through `rewriteSphinxHtml` (sanitized): `<html aria-label="<head>">`, `data-sphinx-x="a<head>b"`,
  `&quot;<head>`, single-quoted value with `"` and `<head>`, `<!--<head>-->` in the body, plain body,
  `aria-label="a>b"` with a fake head attribute, and `</head>` in a body attribute. All 8 are OK.
- raw input given directly: `a="<head>"`, `a='<head>'`, unquoted `a=<head>`, doctype + comment +
  `lang`, and a `</head>` plus a weaker CSP meta inside a head script string. In all of them the head
  holds the policy, and it is the only CSP meta.
- Real pages from `renderPreviewDocument` + `buildPreviewWebviewHtml` (a pipe table, and front matter
  plus a note) still take the splice path: the prefix is `<html>` and the meta sits right after
  `<head>`. The round-1 performance gain is kept.

### N2 (shell memory retention): fixed. Cache is correct.

- The memory key is the length plus a 64-bit non-cryptographic digest of the nonce-normalized page.
  No page text is retained. The value is `{ hasContent, key }`, and the key is the shell only, because
  `analyze` empties the content container and the runtime context before serializing. Memory is now
  3 x shell size.
- Stale risk: none apart from a collision. The value is a pure function of the normalized page, and
  `normalizeNonces` on raw HTML maps pages that differ only in nonces to the same entry. `analyze`
  normalizes nonces in the key, so it gives the same key for such pages, and content detection does
  not look at nonce values. `next` is still parsed on every plan, so `contentHtml` is never cached.
- Collision risk: accidental, about 2^-64 across 3 entries with equal lengths. A deliberate collision
  against this mix is possible in principle. A collision would require an author-crafted rendered page
  to match a remembered page of equal length that has a different shell. The worst case is a patch
  into a stale shell, and the gate is unchanged: content with no nonce and no script, and the loaded
  page keeps its own CSP. That makes it a cosmetic risk, not a security one. Using
  `crypto` is barred in `core` by check-boundaries, as the report says. Acceptable. No action.
