## Root cause (evidence)

1. **Not caused by CR 034; it is a pre-existing CI flake on main.** I grepped the failed integration jobs
   of the last runs:
   - main 75570d3, run 39848315751 (job 120067436393): the same "Timed out waiting for the linked-target
     watcher to deliver the event of the save".
   - docs/orchestration-reliability 39a1b08, run 39848594435 (job 120068405234): same error. That commit
     has no `src/` or `test/` change versus 75570d3 (`git diff --stat 75570d3 39a1b08 -- src test` is empty).
   - fix/change-bar-and-guidelines (PR #19), run 39834587762 (job 120019420923): same error.
   - main d1ada35 (same code as 75570d3 + docs) then passed. So the same code passes and fails: a flake
     with a high rate on Linux CI (3 failures here, about 40% of the recent integration runs).
   Our diff only touches webview code, CSS and tests; the counter the test waits on
   (`linkedTargetEvents`) is incremented in the extension host by the VS Code file watcher, which the
   webview cannot influence.
2. **Mechanism.** `setFrontmatterState` (src/extension.ts) watches each linked target with
   `vscode.workspace.createFileSystemWatcher(new RelativePattern(dir, filename))`. The target lives inside
   a workspace folder (the test workspace is the repo + `/tmp`), and VS Code's watcher host serves such a
   non-recursive request by reusing the shared recursive workspace watcher
   (`/Applications/Visual Studio Code.app/.../out/vs/platform/files/node/watcher/watcherMain.js`:
   `"reusing an existing recursive watcher for ${path}"`). On Linux that watcher (parcel/inotify over the
   repo and /tmp) can lag or miss the write, so the event never reaches the extension in 10 s.
3. **Local reproduction of the exact CI error.** With a scratch runner (in ignored `out/`, deleted after)
   that runs only `previewEditing` and adds `files.watcherExclude: {"**/frontmatter-edit-*/**": true}` to
   simulate a workspace watcher that misses the write:
   - unchanged watcher code: `Error: Timed out waiting for the linked-target watcher to deliver the event
     of the save.` (exit 1), identical to CI;
   - with the fix: the linked-target steps pass (16 later frontmatter captures pass); the run then stops at a
     later, unrelated step (line 1300, the document's own watcher, also excluded by that simulation only).
   - with the fix and no simulation: `previewEditing` passes completely (exit 0).

## Fix (src)

- New `src/frontmatter/linkedTargetWatch.ts`: `watchLinkedTargetDirectly(target, onEvent)` watches the
  target's folder with `fs.watch` (non-recursive, `persistent: false`, inotify/FSEvents directly), keeps
  events naming the file (or unnamed ones), survives errors and a missing folder, returns a dispose.
  Watching the folder also catches an atomic save (temp file renamed over the target).
- `src/extension.ts`: each linked-target watcher also starts the direct watch and disposes it with the
  VS Code watcher. Both may report one write; `scheduleLinkEnrichment` is debounced, so one refresh.
- CHANGELOG Unreleased bullet (linked files refresh reliably on Linux).
- The integration test is unchanged.
