# Review T1-r2, CR 247 (open a document in preview, E switches to edit)

Verdict: APPROVE

Static review only: no test run (the unit tests need `npm run compile`, and the real VS Code window tests were out of scope).

## 1. Owner decision

- `src/page/runtime.ts` starts in edit mode only when the Edit button is working, the saved state is not from another document (`saved.documentId` differs from `context.documentId`) and `saved.editMode === true`.
  - A fresh panel starts in preview mode.
  - Another document in the same panel starts in preview mode.
  - A read-only preview starts in preview mode.
  - A same-document reload keeps the saved edit mode. This is the documented exception in LIFE-172 and LIFE-170.
- `initialEditMode` is gone from `bootContext.ts`, `ToolbarState`, `rendering.ts`, `runtimeHarness.ts` and `previewProbe.ts`. A repo grep finds it only in the new test's comment and a cast. No dangling reference was found.
- `WorkspaceChoices.editMode` and `setEditMode` are kept. The getter is still read by `testHooks.ts`, and the comments were updated. Nothing in the page reads the stored value at start any more.
- The E key handler in `editMode.ts` ignores modifiers, text fields (input, textarea, select), editable elements, already-in-edit-mode pages, pages without a working Edit button, and events that were already default-prevented. It posts `previewEditModeChanged` through the same `setMode` as the button. This matches "E alone in the preview, focus outside any text field".

## 2. Traceability

- `@implements_req` LIFE-170 and LIFE-172 sit on the runtime start line, and LIFE-172 also sits on the key handler. The `@tests_req` markers are on all five new tests (LIFE-172), on T38 (LIFE-170) and on the TRUST-001 tests.
- SwRS LIFE-172 (proposed) has the right frontmatter: `derives_from` StRS LIFE-014, implemented and tested files, scenarios, and an entry in the scope index.
- StRS LIFE-014 lists LIFE-172 in `derived_by`.
- LIFE-170 and TRUST-001 were updated consistently: the edit mode row, the scenarios, and the removal of the "untested initialEditMode" note.
- `requirements/tiers/log.md` has the dated entry and `CHANGELOG.md` has the Unreleased line.

## 3. Changed assertions

- T38 and the TRUST-001 tests: `initialEditMode: true` became `savedState: { editMode: true }`. This follows the owner decision, because the host no longer sends a start mode. The read-only and greyed-button tests still prove that saved edit mode true gives preview mode, so no regression is hidden.
- `runtimeEditToggleRace.test.ts`: the stale-state scenario that mixed `initialEditMode` with saved state was reduced to saved-state-only boot plus clicks. The click and patch race coverage is unchanged.
- New tests that fail on the old code: the other-document test (old code kept saved edit mode true) and the E-key tests (no handler existed).

## Non-blocking notes

1. The "retired initialEditMode" assertion in `runtimeOpenInPreview.test.ts` is vacuous. The harness no longer reads that key, so the test would pass on old code. The fresh-panel half is also weak, because old code defaulted to off too. Consider dropping it or simplifying it. The other-document test is the one that carries the proof.
2. `setMode` in `editMode.ts` writes `{...saved, editMode}` without `documentId`. If a panel toggled edit mode and another document opened before any `scrollCore` snapshot (which does include `documentId`) was written, `savedOfOtherDocument` would be false and edit mode would carry over. The window is very small. Adding `documentId: context.documentId` to that `setState` closes it.
3. A restored panel after a VS Code restart, with the same document and saved edit mode true, starts in edit mode. This is the same-document reload exception that LIFE-172 documents. Worth confirming with the owner that it is intended.
