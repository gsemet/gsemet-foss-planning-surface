## Analysis
### `linkedTargetEvents` hook
- Incremented only inside the per-target watcher callback (extension.ts ~1199); the save handler never touches it, so a save-handler refresh cannot satisfy the "armed" wait. Per-preview integer, one `+=` per event, exposed only in `getActivePreviewForTests()`: no production cost or leak.
- Race check, external write: the baseline is read synchronously right before `fs.writeFileSync` (no event can slip in between on the single JS thread), so it cannot be read after the event arrives. A late duplicate event of the save arriving after the baseline can only open the gate early; the final assertion still waits 10 s on the excerpt text "Updated target description", so no false failure. If the external event is coalesced into a pending one, the count still rises and the enrichment reads the new disk content. `scheduleLinkEnrichment` is debounced and re-reads from disk, so the last write wins.
- No other test writes the target before this step on the same preview (line 405 is setup before the preview; 569 is later), so `> 0` really is the save's event.

### Narrowed save handler
- Refreshes only the enrichment (`scheduleLinkEnrichment`), only when the saved canonical path equals a `linkedTargetWatchers` key, skips the preview's own document, skips disposed previews. No `refreshOpenDocument`, so no double render for includes. A watcher event for the same save re-arms the same debounce timer (clears the previous one), so no double enrichment.
- readOnly/untrusted previews: same `scheduleLinkEnrichment` path as the watcher already uses (`allowSchemaResolution: !readOnly`), no new capability.
