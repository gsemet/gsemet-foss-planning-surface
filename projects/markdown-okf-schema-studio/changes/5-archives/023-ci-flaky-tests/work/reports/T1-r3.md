Evidence: CI first-gap record shows read inset 0 (toggle under the toolbar), edit inset 84. Locally
both are 84. update() computes the right answer when it runs (edit-mode attribute triggers it), so

total (counted with wrapped Observer constructors, CPU 1x and 6x), so the 200-update limit is not
hit there. It is still a real defect (a skipped update has no trailing run), so it is fixed.

section and its right-aligned Description toggle, fonts/stylesheets). Observed before: content,
toolbar, a few attributes. Not observed: the properties section itself (a toggle shown or a heading
wrapped without resizing the column), and `load`/`fonts.ready` when resources finish after the
script ran. Local trace of the 09 page shows a Description toggle (24x24) in the last column header,
plus a second zero-size toggle (the restore one) - sizes depend on layout that settles late on CI.
I could not identify which of these moved on CI; all three are now covered precisely.

Fix, src/webview/firstClearance.ts (still self-contained, `.toString()` safe):
- trailing update: when the limiter skips an update, one `window.setTimeout` runs update() just
  after the 1 s window (scheduled once, not per skipped update);
- a ResizeObserver on the leading `#content > [data-okf-properties]` section, re-armed from
  update() when the section was replaced (disconnect + observe the new one);
- update on `window` `load` and on `document.fonts.ready`.
No broad class/style watching added. capture.py settle change kept.
