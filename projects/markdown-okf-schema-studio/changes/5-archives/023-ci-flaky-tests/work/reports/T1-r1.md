## F1 visual first-gap (`[read:properties] 1 control(s) ... sit under the toolbar`) - test bug
- Cause: the settle loop (17c6122) compared two readings 100 ms apart without a rendered frame in
  between. ResizeObserver callbacks of `installFirstClearance` run in a frame's rendering steps; on a
  starved CI runner (4 workers) a frame can take longer than the pause, so two equal stale readings
  end the loop while the clearance update is still pending, and the hit test then sees a control
  under the toolbar. Fails in many CI runs (also 39756931819, 39748740311, 39746693997).
- Fix: `test/visual/capture.py` settle reading now awaits `document.fonts.ready` and two
  animation frames before each reading. No tolerance, count or timeout changed.
- Proof: mechanism by reading; not reproduced pre-fix (probe with 1x/6x CPU throttle showed a
  stable page 500 ms after load). Post-fix: 6 runs (3 x CPU rate 1 and 8) of the 14 first-gap
  properties scenarios all pass; full `just visual` 255 scenarios pass.
- Open: if it still flakes, suspect the `burst > 200` skip in firstClearance.update (an update
  dropped with no later event) or a font loaded after the loop.

## F2 previewEditing linked target never refreshes - product bug (plus fragile test)
- Cause: the refresh of a linked target depended only on file watchers (per-target watcher and
  the preview-wide `**/*` one). Saving the target in the editor: the edit triggers `refreshPreview`
  -> `refreshReferencedPath` -> enrichment which reads the DISK file before the save wrote it
  (stale), and the save itself (`onDidSaveTextDocument`) did not trigger any refresh. Only a
  watcher event could correct it; the CI workspace is the whole repo, so the recursive watcher
  is the weak point (lag, inotify limits). The test wrote with `fs.writeFileSync` and retried.
- Fix (product): `onDidSaveTextDocument` now calls `refreshReferencedPath` for every preview whose
  document differs from the saved one (`src/extension.ts`); it reuses the existing linked-target
  match and debounced `scheduleLinkEnrichment`.
- Fix (test): the retry loop is gone. The test edits the target through `WorkspaceEdit`, saves it,
  and waits once (10 s, unchanged) for the refreshed excerpt. This is the user's real flow
  ("saved change"). External-write coverage (watcher only) is no longer exercised by this test.
- Proof: reasoning only; no unit test possible (extension.ts needs the vscode host). CI must prove.

## F3 realInput RI-T39 (f) user's lock survived - product bug
- Cause: `unlockPreviewGroup` remembered the active group as a column number, and after unlocking
  the empty preview group (which then closes, shifting the user's group from column 3 to 2)
  it ran `focus<Nth>EditorGroup` for the stale column 3 if the extension-host snapshot still
  listed 3 groups. VS Code's focus-Nth-group commands create a new empty group when the position
  does not exist. The new unlocked group then receives the file from Quick Open in the user's
  locked group (opened in column 3, test expects column One; also a stray group for real users).
  Whether the creation happens depends on event/snapshot timing: flaky.
- Fix: remember the `TabGroup` objects, wait (event based, bounded 1 s) for unlocked groups to
  leave `tabGroups.all` before restoring, restore only if the remembered group is still open and
  not already active, and always go through `focusGroupCommand(column, groupCount)`, which never
  returns a command for a position past the last group. New `src/navigation/groupFocus.ts`.
- Test added: `test/navigation/groupFocus.test.ts` (3 tests, pass). It targets the new function, so
  it "fails before" only in the sense that the guard did not exist; it locks the invariant.
- Proof: reasoning only; CI must prove (several green runs). Test file realInput not changed.
