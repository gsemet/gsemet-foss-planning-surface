=== merge-words
# The words to the user about a merge

The CLI's words, in the user's language: "ready to merge" only for a PR the user can merge now; "PR in draft" for a draft, with what it waits for; "ready locally" for done work with no PR yet. "Ready" alone is never said of a CR or PR, and "mergeable" never of a draft, whatever the forge's `mergeable` field says. An icon beside a CR is copied from `label` (🟢 ready to merge, 🟤 PR in draft, 🟣 ready locally), never judged, and is the present state; the future is said in words ("🟤 #171 CR-237, do not merge: it waits for its gate").
- A draft is named with "do not merge" and what blocks it; a draft on another CR's branch is never "ready", even of its own work. A draft's icon is its CR's state from the refreshed `STATUS.md`: 🟤 only with nothing left to do, 🟡 rebasing or running CI or a Verifier, 🟠 waiting for another CR's work, 🔴 blocked.
- "You can merge it" only after the `ready-to-merge` line (or `stack-ready-to-merge`) has reached you, never on a Driver's progress, a green CI or the forge's look. A merge before that line is recorded as any merge (`order merged <cr>`, tell the Foreman in the same message), no reproach.
- `status` prints a `handed back:` line per CR: say its icon, its full PR link, each gap, its `do not merge: waits for` text and its `owed before the merge` clauses in the user's language, never the prefix. More: `help merge-gaps`, `help merge-recorded`.
=== merge-gaps
# The gaps of a ready-to-merge ask

- Quote each gap of a `ready-to-merge <cr> <link> gaps: ...` ask next to the link; with none, say nothing about gaps. A `pr-in-draft <cr> <link> on <base>: waits for <what>` ask is not offered as mergeable: a PR in draft, do not merge, and what it waits for.
- A project rule that asks a local run: the ask carries `local gate <cr> at <sha7>: ...`; quote it before you say the PR can be merged. `passed`: it ran and passed at that head. `not run` or `failed`: the rule asks that gate at that head before the merge and it has not passed there; merging anyway is the user's choice, recorded as any merge, never questioned or refused. When the ask and the `long gate` clause differ, the ask wins.
- A screenshot gap (the project asks one of the board pane): ask the user for one screenshot from a session running the PR's branch, with made-up paths, no username or home folder. A Driver's report that the user's screenshot was not uploaded for showing one: say so and ask again. A report that an image showing them was uploaded and replaced: tell the user the PR, the image, and that the old attachment may stay reachable on the forge; nothing more. On the user's file: `order note <cr> --note "evidence: <path>"`.
- For the release PR the same message asks the post-merge word (`help release-chief`).
=== merge-recorded
# Recording merges

- A `forge saw merged: <cr> ...` line (in `status` or a watcher) is a merge the user made: record it once the forge confirms it (`help watcher-events`): `order merged <cr>`, then Foreman mode sends its line to the Foreman; with `foreman watch: running` tell the user, record nothing. `landed with <other cr>` is a merge to record; only `not landed ...` is not: tell where the PR went and wait for the PR under it. Several PRs merged in one action: `order merged` for each.
- A CR taken out and whose PR the user merges later (its folder in the backlog or `3-ready`, with `formerly.json`): on "I merged #n", `order add --note <folder>` (brings back its number and PR), then `order merged <cr>` at once (Foreman mode: both lines in one message, the add first). With no batch open say it is recorded the same way in the next batch and leave the folder. A Driver's `blocked question: its PR <link> is already merged`: `order merged <cr>`.
- GitLab: a fold (`forge-stack show` prints `folded into <cr below>`) is recorded at once (`help merge-stack-gitlab`).
=== merge-series-stack
# A series batch, a stack batch, a mode switch

- Series: CRs merge one by one in order. On each ask say which PR is next (the bottom one, ready to merge on the default branch), that the others are drafts waiting on it, the gaps; on "merged" `order merged <cr>`, then say what comes next. Never merge for the user.
- On the user's word to switch mode (any to any) `order mode --note <mode>`, and tell at once what it does from the printed line: to a stack or series the PRs above the bottom go to draft while it is rebuilt, "do not merge them meanwhile" (name them); stack to series, the PRs above the bottom stop being mergeable (name them); to parallel each open PR is rebased, its gates run again, and it leaves draft once ready. A merge the user makes anyway is recorded as any merge. Merged CRs never change.
- Stack: before the stack exists each CR handed back ready on the default branch is an ordinary ask while it is the only open PR of the chain (the shape line's `alone asks`). An ask for a chain CR while `alone asks` is `refused` or `allowed for <another cr> only`, with no `outside the stack: O-<k>: ...` naming your own order carrying the user's word, is mismatched: send it back with `order note <cr> --note "shape: through the stack"` and tell the user `<cr> asked alone in a stack batch: sent back through the stack`. A Foreman ask about a blocked CR with a ready CR behind it: offer `order hold <blocked cr>`, or an order on the ready CR carrying the user's word for `--outside-stack "O-<k>: ..."`.
- A stack's readiness is a `stack-ready-to-merge` (`help merge-stack-ready`). A check that fails: no "ready to merge"; send it back through the Foreman. The user always merges a stack themselves: no grant lets a steering session merge a stack that holds the release PR.
=== merge-stack-ready
# A stack ready to merge

On `stack-ready-to-merge <stack link> ... <cr>=<link>...` (with or without `to come: ...`), read the stack on the forge yourself first (`$CHANTIER forge-stack show`, the five checks, exit 0 when all hold), then quote each CR's gaps and any screenshot or local-gate clause as for a plain ask (`help merge-gaps`), before the sentence that says it can be merged. In direct mode one `forge-stack show` is enough.
- All hold: tell the one PR to merge by the ask's `merge <cr> <link>`: on GitHub merging it merges those under it in one action; one PR at a time from the bottom stays their choice. No other PR of the batch is to be merged while the stack stands, except a fix CR's PR whose latest readiness ask names it; a merge made anyway is recorded as any merge. With `to come: ...`: mergeable up to its last ready PR, the drafts on top and the CRs to come named, the top goes on growing silently. Without it: complete, mergeable in one action from its top PR or one at a time from the bottom, the release commit last. Name the commit ("partial stack mergeable below <sha7>"). A CR that turns ready reaches the user through the next report's partial-stack line.
- After each merge action `order merged` for every CR it merged, bottom first, all before telling the Foreman, in one message; one action leads to at most one silent restack.
- Add one clause: heavy CI ran at the top PR's head only; merging below without it is their choice; on their word `order note <cr> "heavy CI: at its head"`, and the Foreman's `heavy-ci <cr> <head7> green|red <checks>` ask is told (red changes nothing by itself).
- A refused `$CHANTIER forge-stack rebuild` (an `anomaly`): the user gets the exact text; on their yes run the command the refusal's last line names (`forge-stack create` after `... is dissolved and no stack replaces it yet`, `forge-stack show` after `... the stack's state is unknown`), else `forge-stack rebuild`; no raw `gh api`.
- A stack waiver: name the CR whose gate validates the lower PRs (`waived -> CR-k`) and whether it passed; merging below before it passes leaves main with the failure if it fails.
=== merge-stack-gitlab
# A stack on GitLab

Unproved on GitLab; trial: one run on a GitLab project. `forge-stack show` reads the same checks on the chain and names the commit the same way. Tell the user the stack is mergeable one MR at a time from the bottom up to the commit named, never "in one action from that MR"; each next MR is mergeable once GitLab shows it so (retargeted to the default branch, pipeline green; a needed rebase is chantier's restack); an MR merged in the middle folds into the one below, its change reaching the default branch when that MR merges.
- A middle MR merged anyway (or `check 1: !<iid> merged into <target> ... folded into <cr below>`): `order merged <k>` at once with `order note <k-1> --note "folded: <k> into <k-1>"`, tell the Foreman in the same message, and tell the user that CR k's change now rides in CR k-1's MR.
- An MR on a merge train or set to auto-merge is not merged: on "merged" read it (`glab mr view <iid>`) and record only once it reads merged, else say it is recorded once the train or pipeline merges it, and read it again at the next report. Only the bottom MR can join the train, the next once retargeted after that merge.
=== stack-changes-chief
# Changing a stack: a drop, a hold, an insert

- Dropping a CR from a stack, on the user's word: `order drop <cr> --note <destination>`; the Foreman removes it with `take stack --epoch <n> --note "drop: <cr> to <destination>"`. Tell the user its commits come out of the PRs above it, which are drafts (do not merge) until the next partial-stack line shows them ready. Trash: its PR is closed and its branch stays until `close`. Backlog or `3-ready`: its PR goes to draft, its branch and worktree stay and are not offered for removal at `close`, its folder keeps its number. A held CR: nothing to rebuild.
- Holding a CR on the user's word to keep a live CR out for now (when unclear whether they mean held or out of the batch, ask): `order hold <cr>`; back with `order unhold <cr>` (a CR held while working returns blocked). The Foreman stops its Driver (`stop hold: <O-n>`) and in a stack takes the stack driver. CRs that wait with it wait too: name them. Name each held and each parked CR in every report with what it waits for. No release starts while one is held or parked: say so, name it, offer `order unhold <cr>` or `order drop <cr>` with the user's destination, and act on the answer only. Drop a held CR only after the hold's `order done`. Direct mode: you do the stop, `agents set <cr> -`, `order done`, and fill the freed slot only after it. A release working at the hold is let hand back, then taken again (`redo: <cr> held`).
- Inserting a CR into a stack ready to merge, on the user's word: first and at once put to draft every PR that will sit above it (`gh pr ready --undo`, `glab mr update --draft`); a CR in the middle that goes back to its Driver for a round gets the same. Then `order add --note <folder>` and `order note` naming the place (`insert: <new cr> below <cr>`). Tell the user the stack is not mergeable until the Foreman's next `stack-ready-to-merge` and that the release notes will name the change (the release CR goes back to `redo:`).
=== batch-pause
# The pause

On `[foreman→chief-of-staff] final <STATUS.md path>` that file is the exit report with the cost to date. The CLI removed the merged CRs' worktrees and branches and paused the batch when the last CR ended (`kept:` or `not removed:` names a leftover); the Foreman wrote the retro in `4-batch/retro.md` after the pause and before `final`; read it. Give the Completion report with its Retro offered by route (`help retro-route`), each point numbered, before any `close`. In Foreman mode your own `order merged` or `order drop` of the last CR prints the pause: still send its line to the Foreman and wait for `final` before the close offer.
- New work for the paused batch is `order add`, once per CR: until `close` the paused batch is still the running batch, and a CR in `1-pending` starts it again at the next `take`; send the Foreman the usual order once all are added.
- Where the heartbeat is yours (host row), tell the user to delete it in the Foreman chat at the pause and again when the Foreman ends it on its first wake that sees no Driver run for 30 minutes or more; arm it again with the next order.
- Hold and parked CRs, a release held, the wait: `help stack-changes-chief`. Then the close: `help batch-close`.
=== retro-route
# The retro, by route

The retro you read holds only the points the `retro-critic` kept; its header ends `(critic: kept <k>, dropped <d>)`. After the numbered points one line: `<d> points dropped by the critic; the list is on request.` Asked, read `4-batch/retro-dropped.md` and show it, before any `close`. `nothing worth changing` is said as such, with the dropped count. `retro not checked: <cause>` is said as such, nothing offered; drafted points are in `retro-dropped.md` on request. Offer the Retro before any `close`.
- A `project` point: on the user's word `$CHANTIER file "<the point>"` files it in `1-inbox`; a point matching an inbox or backlog item is named with that item. A `chantier` point is never filed with `file` (except in chantier's own repository); on the user's word it goes the chantier route (`help retro-route-chantier`). The user may move a point to the other route: follow it and say the route.
- A release's `work/retro.md` is offered once, with the batch's, each point by its own tag; only the kept ones (marked `(release)`).
- When the project is chantier itself (its `git remote get-url origin` equals the manifest's `repository`, compared without a trailing `.git` or `/`, ignoring case): both routes meet; the Completion report's "For you" says "This project is chantier: its `chantier` points are filed here as inbox items, like the project's; say 'as an issue' for a point to go to GitHub instead." The default is the inbox.
- Before proposing on your own initiative any other list of changes (a retro after a release, a report's suggestions, even a single change), start one `retro-critic` with the points and their evidence, its first line copied from `$CHANTIER playbook`, and offer only the kept points and the dropped line (the list stays in the chat). Keeps nothing: "Nothing worth changing." Fails twice (restarted once): "retro not checked: <cause>". A change the user asked for, or a CR's own content, does not go through the critic.
=== retro-route-chantier
# The chantier route

A `chantier` point, on the user's word naming the point for this route; all at the pause, before any `close`, in this order:
1. The repository is the `repository` field of the plugin manifest (`.claude-plugin/plugin.json` on Claude Code, `.github/plugin/plugin.json` on Copilot).
2. Already reported? `gh issue list --repo <owner/name> --state open --search "<key words>"`; a match is named with its link and not drafted. `gh` absent or not reaching it: skip and say so.
3. Draft one file per issue with the host's Write tool (UTF-8, no BOM): `4-batch/chantier-issue-<n>.md`, `<n>` the first point's number. First line the title (`Bug: ...` or `Feature: ...`); then what happened, the long-term fix, chantier's version (`$CHANTIER --version`), the host and version when known, one line saying it came from a batch retro, and for a host cause that it may belong upstream. English; no label.
4. Check before showing: the repository is public, so no project name, private path, code or text of the target project, CR number, slug, batch id, or person's name or data; a point that cannot be said without them is said in general terms, else offered as an inbox item.
5. Show the title and body, the repository's link and the tool; ask a yes per issue. The user may edit, regroup, decline, or post it themselves (give the file's absolute path).
6. Post on the yes only, and only you: `gh issue create --repo <owner/name> --title "<title line>" --body-file <path>`, the body in `4-batch/chantier-issue-<n>-body.md`; give the link. `gh` absent, not logged in or refused: post nothing; give the file's path and the "new issue" link and say what is missing.
7. No record: the drafts stay until `close` deletes them; the link is said in the chat only.
=== batch-close
# Closing the batch

At the pause, after the Completion report and the Retro, once the steering session's retro critic has handed back (Foreman mode: after its `final`; direct: after your own critic), offer the close unprompted: run `$CHANTIER close --batch <batch>` (the check, no `--yes`), show the bilan, the final cost, what goes (the batch's own files; each `3-done` CR moves to `5-archives`), where the record goes (`5-archives/batches/batch-NN.md` and `.json`), its line of worktrees and branches to remove (the merged CRs' leftovers beside the trashed CRs', with why each was kept) and its `kept, moved out with their work` line (show it, remove nothing on it), and ask "close the batch?".
- `close --yes` only on the user's yes (to this offer or "close the batch"). In that turn: `close --batch <batch> --yes`, then every entry of its line yourself from the main checkout (`git -C <clone>` with a surface): `git worktree remove --force <path>`, `git branch -D <branch>` as listed; for a folder git no longer knows, `git worktree prune` then `git branch -D`. Never without the yes.
- It refuses, naming each cause, while a CR is not merged or cancelled, an order is open, a stack agent is recorded, or a held agent (the current Foreman included) has a transcript showing it still runs or unreadable; also when nothing can be priced. Other subagents and replaced Foremans never block. An unpriced model does not refuse: the cost is a floor and the CLI names the id to add under `prices:`. Report a refusal with its cause; do not retry in a loop; do not `close --yes`. A held agent that still runs: wait for its hand-back, never a timer. More: `help batch-close-stopped`.
=== batch-close-stopped
# Close with an agent declared stopped

When you know a held agent will not hand back, or the user says so (an app restart cut it, the user's stop, a hand-back that reached you while its transcript reads as running), ask the user, quoting each agent's name, cause and file as the refusal gives them; ask the agent itself only as a last resort.
- On the yes for each named agent, in that turn: `close --batch <batch> --stopped <name> ...` (the check; the name is the held agent's file stem `agent-<id>`, or the current Foreman's session id), show the bilan with its "declared stopped" lines, ask for the close; on that second yes `close --batch <batch> --stopped <name> ... --yes`.
- Never `--stopped` without the user's yes for each named agent, and never to get past a transcript that cannot be read; the CLI refuses a name that is not a running held agent.
- A held agent with no transcript found: tell the user, and clear it with `agents set <cr> - --epoch <n>` only once it is known not to run (a Driver of another session of the user's: on the user's word); never `--stopped`. A Driver from another session of the user's is not in what the CLI reads: ask when you know of one.
- On Copilot, until the close end event lands, a held agent whose lease is live, a unit with no lease and the Foreman's heartbeat under 10 minutes refuse too; `agents set <cr> - --epoch <n>` after the agent's reported end ends it.
- On a batch set running again by a `take` or `order qa`, the CLI names what runs, or says `pause --epoch <n>` comes first.
- Putting back: on the user's word a CR in `6-trash/` returns to `1-inbox/` by moving its folder, without the date prefix.
=== recovery
# Recovery

A stale heartbeat says something only while a CR is `working`; with none the Foreman has stopped waking, as it should. "Heartbeat stopped" is a loop ended on purpose. After a break, restart or stale heartbeat, prove the Foreman is alive (`$CHANTIER foreman get`; the host knows the session and it answers a `ping`) before reporting progress.
- An app restart stops every session: tell the user, and on "resume" run preflight again and start a new Foreman with the next number (or on the user's word switch to direct mode, `help mode-switch`), adding "Resume: relaunch each CR still working by the restart path (`agents set <cr> - --epoch <n>`, `handoff`, `take <cr> --note "resume: <cause>" --epoch <n>`, a new Driver, `agents set <cr> <id> --epoch <n>`); a relaunched CR's stale long gate is stopped by its new Driver with `$CHANTIER gate <cr> --stop`."
- `cancel` follows only a drop the user ordered (`order drop <cr> --note ...`): never use it to stop the processes of a CR that goes on.
- A Driver whose id was cleared (`agents set <cr> -`) and a replaced Foreman never block `close`. In a direct batch a Driver stopped from outside is restarted by you with no question (`help lost-driver`), and when you stop a Driver and do not restart it at once you clear its id in the same turn.
=== direct-mode
# Steering a batch yourself

In direct mode no Foreman session starts; the CR lifecycle, frame, folders, reports and the user's boundaries are the same. Read the Foreman card and, for a stack, `help stack`, and do what they say of the Foreman, with these differences.
- Leases: `take` is refused while a unit's lease is live (`--reclaim` only on the user's word) or not confirmed (check with the host that it ended, then `take <cr> --reclaim --note "resume: lease not confirmed"`; a QA order `agents set O-k <id> --reclaim`; the stack `take stack --reclaim`); `agents set <cr>|O-k|stack -` after a reported end ends its lease (`help lease`). A refusal you do not understand: `$CHANTIER access <cr> --epoch <n>` before you ask.
- Escalation is yours (`help escalation`; the model is the `escalate:` line of `playbook`), as are the two rounds routes: once per CR, then the user; a CR with no rounds blocked twice goes straight to the user. A restack that fails runs the stack driver's `conflict-resolver` on the escalation model.
- Titles: at `open --direct`, rename yourself `[<code>] 💬 Project · CoS (Batch <nn>)`; after `close --yes`, `[<code>] 💬 Project · CoS` (`help titles`).
- Your number: `$CHANTIER foreman set <your session id> --epoch <n>` then `foreman transcript <your transcript id> --epoch <n>`; on an empty batch just before your first `take`. After each claim, in every batch you steer, `$CHANTIER rules` and read the files it lists (skip only a file read since this batch's `open` and last compaction). More: `help direct-mode-epoch`, `help direct-mode-accept`.
- The Drivers: you start them, several in parallel on free slots, in the background; "never message a Driver" does not hold for those of a batch you steer. Start each from the skeleton `take` printed, copied whole, each `<...>` filled in, no `writes:` line added or dropped; a QA driver from the skeleton `order qa` printed, then `agents set O-<k> <id> --epoch <n>`.
- A stack: one `forge-stack show` before you tell the user it is ready; inserting a CR is `help stack-changes-chief`. A dependent draft PR goes back to a Driver with `rebase: <dependency> merged` after an `order merged`. Before a note that carries work to a Driver (a `rebase:` first), read a plain `status`: handed back `ready` or `blocked`: `take <cr> --note` and the take-back path; `working`: the message.
- The main checkout after a merge: the Foreman card's procedure (`help main-checkout`) is yours after each `order merged <cr> --epoch <n>`, with its `main checkout:` note (`note` carries no `--epoch`).
- Nothing is sent to yourself: no `ready`, no `[foreman→chief-of-staff]` line. An ask is recorded with `$CHANTIER asks "<text>"` and told at once. A Driver's refused rebase or push is judged and run by you (`help refused-push-chief`); the CR goes back to a fresh Driver with the result as its `take` note.
=== direct-mode-epoch
# Your number as Foreman, in direct mode

Claim it as a Foreman does. Carry `--epoch <n>` on exactly these commands and no other: `foreman set`, `foreman transcript`, `status --refresh --epoch <n>` (the loop's wakes), `status --stop-heartbeat`, `take`, `agents set`, `order done`, `order merged`, `order add --fix-for`, `gate <cr> --first`, `cancel` and `pause`. Each refuses a call without it (exit 2), except `order merged` and `order add --fix-for`, whose form without it is the Chief of Staff's order, and the refresh before a report. Any other command or `order` kind (`order add` without `--fix-for`, `order note`, `order after`...) refuses `--epoch` (exit 2), except `access`. Never on the refresh before a report (`status --refresh`, no heartbeat). Arm the same heartbeat as the host row says; "heartbeat stopped" is a loop you ended on purpose.
- The CLI prices your transcript from the claim as one `Chief of Staff, steering the batch` row, counted in the spend and budget. A turn that grills with the user or writes specifications (it writes a CR's `01-intent.md`, `02-answers.md`, `03-change-spec.md` or `work/specifying`, or starts a spec-writer or critic; a turn that only names or reads them stays on the row; a turn is attributed whole) leaves that row for the `grill and specifications with the user` line, outside the budget. Write those four files with the host's Write or Edit tool, never a shell command: the CLI recognises grill work only by that write.
- `steering the batch (outside the budget)` shows what you spent since the batch opened outside your claim window; the `whole session` line prices the session and names in a parenthesis the part in the batch's spend, and counts compactions.
=== direct-mode-accept
# What you accept while you steer

- "status?", "what did it cost?", answers to a blocked CR of this batch, orders on the batch itself ("I merged #42", "drop CR-140", "stop the batch", more rounds, slots or budget).
- Backlog work: file, triage (on the user's word), reorganise, merge items, `abandon` (on the user's explicit word), record answers in `02-answers.md` at once, keep each summary fresh (`summary lint`, `summary set`; `summary label` and `summary group` on the user's word only). `triage --ready` never joins the running batch: a CR joins only by `order add` from a destination the user chose.
- The spec-writer and the spec critic, on the user's word that a CR already grilled is grilled enough (`help grill-specify`); critic questions wait for the pause.
- A CR added while the batch runs is queued by `order add` (taken when a slot frees); `order qa` is refused (exit 2); `order add --release` and `--fix-for <release-cr>` are accepted.
- Not while the batch runs: grilling a CR (asking its questions, writing its `01-intent.md` from a discussion), touching the running batch from backlog work, the demo. Any other request is noted word for word and handed back when the batch completes; an idea is filed in the inbox at once (`file`, no grill). A request to grill or order a QA gets row A at once (`help refusals-to-say`; a Griller session or a fork is the user's step, never done by you).
- A paused batch is not running: this lifts at the pause; your retro and its critic still run after the pause and before the close offer. At the pause run the fast-forward, cancel the armed wake, write the retro (`help retro-lines`, `help retro-critic`), give the Completion report, then the close offer (`help batch-close`); a pause that prints `every CR is merged or cancelled, not paused: <causes>`: do what blocks it, then the cleanup and `$CHANTIER pause --epoch <n>`.
- Inbox ideas may be grilled at the pause and added with `order add --note <folder>`; your first `take` sets the batch running again.
