=== release-chief
# A release, the Chief of Staff's part

A release is a CR a Release driver runs by the project's own procedure; chantier holds none. Find it in `AGENTS.md` and what it links; nothing written, or a gap, is a question for the user and an offer to write the answer in the project. A procedure silent on release notes or an announcement is no gap: the Driver follows the release template. If it has no long check on the exact head of the default branch before the version commit, ask whether to plan one and say why (per-CR gates miss what CRs break together); the user's answer rules.
- Prepare it as any CR (`$CHANTIER file "Release v1.4.0"`, grilled: the version when the user can settle it, the scope, where the procedure is, what the user reviews). Otherwise the Release driver picks the version and says why: no confirmation. It joins the batch of the work it ships, best a stack: `--release N` at `open`, or `order add --release --note <folder>` (one per batch, default grant; `order grant` after). It waits for every other CR, later ones too (`order after` is refused on it); in an ordered batch it is prepared on top once the others are ready, in a parallel batch after the merges. Asked for in a parallel batch: explain why it cannot be prepared before the merges and recommend a stack batch for the next one (a parallel batch cannot be switched to a stack). A project rule file on the release ranks above this.
- When it joins, write your latest Progress report and the conversation excerpts you choose into the CR's folder as `report.md` and `conversation.md` (the Driver renders them, anonymised) and refresh them at each report until the release PR is prepared. In the filing grill ask whether a docs diagram goes in the notes; only a yes puts one in, named in the specification.
- The user merges the release PR (the whole stack from the bottom in an ordered batch); record each merge with `order merged`; that merge starts the procedure. No release PR in the procedure: once the other CRs are merged, ask whether to run it; the yes is `$CHANTIER order confirm <release-cr> --note "<the user's word>"`. `order add` stays refused once it has started (a fix, `--fix-for`, or the next batch).
- The grant is the user's: each irreversible action waits for their approval (`order approve`; never lets the steering session merge a release PR); ask whether they allow more and pass only what they said (`--autonomous-releases <n>`, `--grant-fixes`, both with `--budget`; later `order grant`). More: `help release-chief-approve`, `help release-chief-auto`, `help release-chief-after`.
=== release-chief-approve
# The post-merge word, asked with the merge go

When the release PR is offered (the `ready-to-merge <release-cr>` ask, or the complete `stack-ready-to-merge` whose top is the release PR), ask in that same message the user's word for each irreversible step the procedure runs after the merge, each on its own (chantier: CONTRIBUTING.md "Release" step 4, `just tag`, and step 5, `gh release create vX.Y.Z --verify-tag ...`). They may answer yes to all, some or none. Never the merge itself, and never the announcement: both stay the user's.
- A yes: before `order merged`, one `$CHANTIER order approve <release-cr> --note "<step>: user, <YYYY-MM-DD>: '<the user's words>'"` per step; answer and merge in one message: approvals first. Foreman mode: all lines in one message.
- No word: record nothing; the Driver started at the merge hands back `blocked approval: <step>`, the ask follows, the answer is `order approve`.
- A release redone before its merge: the yes already recorded holds and is not recorded again; the next ready line names the steps already approved (from `approvals unused:` in `handoff <release-cr>`) and asks only for the rest.
- A "wait" on an approved step, before the merge: write it at once in the CR's `02-answers.md` (date, the user's words, the step), not as an order or a take (an `order note` on a ready CR is a take), then close the summary gap. At `order merged <release-cr>` read that file; right after, in the same relay, one `order note <release-cr> --note "wait: <step>: user, <YYYY-MM-DD>: '<the user's words>'"` per step. A "wait" after the merge: the same note at once.
=== release-chief-auto
# "auto" for a release

While the release runs (from its Driver's start to `release published` or the CR's end) offer "auto" as the "during a release" tip, one line with the exact word; on an approval ask (`blocked <release-cr> approval: <action>`) the question lists "auto" beside approving that one action: part of the question, not a tip. On "auto" (the user's own word, any language):
1. `$CHANTIER handoff <release-cr>`; read `<k>`, the releases already published, from its `grant:` line.
2. No budget in the batch: ask for one with a recommended figure (the CLI refuses autonomy without it); send nothing before the answer. Then `$CHANTIER preflight --autonomous-releases 1`, P9's probe 5 and the release trial; ask the release-rules question still missing and act on the answer. The grant never waits for the rules: the user's word is the grant. The same for a later `order grant ... fixes=on` with `--grant-fixes`.
3. `$CHANTIER order grant <release-cr> --note "releases=<k+1>[ budget=<usd>]"`, and record the user's word with the date in the CR's `02-answers.md`.
4. Send the order's line to the Foreman (direct mode: act on it; a CR blocked on an approval goes back to a Driver with `--note "auto: <the grant line>"`).
5. Tell the user in one line what auto does (the steering session merges the release PR by the GitHub route once every other CR is merged or cancelled, and the steps the procedure asks a go for, this release only) and what stays theirs (the announcement, a fix unless granted).
"auto" covers this release only; never an announcement, a fix's start or merge, the procedure's word (`order confirm`) or a budget raise. Under a live grant the steering session merges and no ready line goes to the user; approvals recorded before an "auto" stay whole.
=== release-chief-after
# A release: refusals and after

- The publication refused by the host (`blocked <release-cr> approval: publish: <exact command>`): give the user the command as a **For you** line, exactly as handed back, with where to run it (the main checkout, or the clone `take` names): "the publication is yours: run `<the command>`, then tell me when it is published". An `order approve` does not help. The user's word that it is published, relayed at once: `$CHANTIER order note <release-cr> --note "publication done: user, <YYYY-MM-DD>: '<the user's words>'"` (Foreman mode: send its line; direct mode: `take <release-cr> --note "<the note>"` and a Release driver). If you ran the command on the user's word, the same note follows once it succeeded, `publication done: steering session, ...`. Never relay a `publication done:` note the user did not give: no guess from the forge, no silence read as a yes.
- A refused main-checkout step (`release <cr>: <step> refused: <line>`): a **For you** line with the refusal and what it says to do; you never settle the checkout yourself. When the user says to run it again: Foreman mode `[chief-of-staff→foreman] release <cr>: run <step> again`; direct mode run it yourself.
- `status`'s `draft <path>` on the release's line: give the user the link as soon as it appears. Once released, read `work/retro.md` in the CR's folder (`4-batch/3-done/`); it is offered once in the next Completion report's Retro.
- "Released in": once the Driver records `release published` (its note carries the version and link), list the issues the release ships, one line each: the issue's link and the comment "Released in <the release's link>" (the `issue:` lines of the CRs the release contains: the batch's `4-batch/3-done/` and the `5-archives/` folders merged since the previous release). One yes covers the whole list; post each as `help ticket-summary-post` says (an unreachable issue is skipped and said). No issue: say nothing. "auto" never covers these comments.
=== seat-handover
# Handing the seat over

Rules only; the models judge the rest.
- The seat moves only on the user's word, and only on the new session's explicit acknowledgement.
- A running Driver is never stopped nor moved. On the user's agreement the old Chief of Staff finishes the running work itself or through its Foreman: it starts no new Driver (`order slots --note 0` while CRs are queued). Once every Driver has finished (a PR may still be open) it sends `[chief-of-staff→chief-of-staff] your turn, you are the Chief of Staff`.
- The new one answers `I have the batch`, then `$CHANTIER seat take <own id> --over <old id> ...`. A direct batch: it claims the next number (`help direct-mode-epoch`) and gives the slots back if a hold was set. A Foreman batch: it sends the Foreman `chief-of-staff <own session id>`.
- The old one becomes a Griller (or ends) and renames itself. Its board stops when the seat moves (or 30 minutes after its last client); the new one's watcher, from the line of its `seat take` on its yes, registers on a board still running or starts one (a hand-started board joins). The old watcher ends once the new session takes the seat; the new one starts its own from that line or `status` (another session's does not count).
- With no batch active the hand-over is the seat alone: `seat take --over` on the user's word.
=== demo
# Subagents and the demo

You may start a subagent of your own for an exploration, a prototype or a study. For a CR its brief names that CR's folder and the place in it, and the result is written there as a file; for no CR yet it names a folder, and you move what it kept once a CR comes of it. It never starts an implementation: no commit, push, PR, or write in a CR's worktree. Its cost is on the `steering the batch` line. In Foreman mode still no message to a Driver.
- The offer: on the Foreman's `ready-to-merge` that is the last of a stack, when no CR is working, end the Progress report with the offer of a demo (`status-layout.md`). A parallel batch gets none. Nothing starts without the user's yes; a no ends it.
- The study: on a yes start the `demo-explorer` with the prompt of "Starting an agent", a `Read <skill>/references/demo-explorer.md;` line and the rules line, the first line `chantier demo-explorer for the Chief of Staff of batch <batch>, in the project <root>.` with `4-batch/` as its folder, the user's language, and the agent and model `playbook` prints. It writes `demo/demo.md` in `4-batch/`.
- The demo: show the summary, then guide one change at a time and wait for the user's result; they try each change themselves. Prepare any fixture outside the repository's tracked files and remove it at the end. The code is the top of the stack, not yet merged. How to run the project comes from its `AGENTS.md`; what it does not say is a question for the user.
- A problem found is the user's decision: `order note <cr>`, a round of fixes, or the inbox when rounds are spent or the idea is new.
=== pr-template-own
# The user's own PR template

On the user's request for their own PR template, file a CR for it (`$CHANTIER file`), grilled and specified like any other; a CR Driver delivers the guideline and the template by PR (the PR template's "A customised version"). You do not write them in the main checkout yourself.
