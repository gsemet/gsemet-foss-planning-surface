## Deviations from the spec (for review)

1. mypy: with `skills/chantier/scripts/chantier.py` in `files`, mypy refused "Duplicate module
   named `chantier`" (the script and the package). Added `explicit_package_bases = true` and
   `mypy_path = ["skills/chantier/scripts/cli/src", "skills/chantier/scripts/cli/tests"]`, so the
   package keeps its names and the launcher is named from the repository root. Same result on
   the rest (the `copilot_session_usage` unused-section note was already printed before).
2. `--print` adds `--project "<folder>"` whenever the session's project is a surface's, as
   `cli_command` does, not only when `--project` was given: a surface with one project and no
   `--project` gets it too, so `--print` equals `cli_command(repo)` in every cell. Hence
   `launch.session_project(cwd, project) -> (is chantier, surface folder)`, which
   `project_is_chantier` wraps.
3. `child_env`: the CLI's environment drops `VIRTUAL_ENV` when it names the launcher's own
   script environment (uv run --script sets it). Without this the dev form's `uv run` warned on
   stderr at every call (seen on Windows: "`VIRTUAL_ENV=…environments-v2\chantier-…` does not
   match the project environment path").
4. Holders: a process under `.venv` that is not a chantier command (a test run) is written
   `PID <n> <program>` (e.g. `PID 37644 python`); a chantier holder with no `--project` is
   `PID <n> <subcommand>`. A listing that fails (powershell or ps missing or erroring, or
   unreadable JSON) is an ordinary failure: one line on stderr, exit 1, no sync.
5. The missing-uv line and uv's failure texts go to standard error; the three fixed lines and the
   plugin mode's line to standard output.
6. The scenario's `cli:` fact form is read by calling `plugin_files.cli_command(Repo.find())`
   in the sandbox (the function that prints the fact), not from a `take`'s facts: the case runs
   with no batch.
