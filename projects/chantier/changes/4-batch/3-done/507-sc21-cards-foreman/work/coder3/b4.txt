=== trials
# The trials before the go

At step 1 of a batch, after the preflight with the batch's options: one harmless trial per used capability, run by you, each command alone, in this session's permission mode, with the user there (a command the CLI ran would be a child process the host never sees). Forms (host row "Trial before the go"):
- every batch: the `$CHANTIER preflight` you just ran; `git -C <main checkout> push --force-with-lease -u <remote> chantier/preflight-trial --dry-run`; on GitHub `gh pr view --json number`, on GitLab `glab mr view`;
- a stack with the extension: `gh stack view`; with `forge-stack`: the stacks API probe of P9;
- a release on its own: `git push <remote> v0.0.0-preflight-trial --dry-run`; `gh release create` and the merge, and fixes on a grant: "no trial: P10's rule check only".
- A trial proves the host let the command run; the command's own error (no such branch, no PR) is a pass. A denial, a prompt or a classifier refusal is a refusal, said at once with the command and the host's exact text, in the strong warning, with the rules P10 named; it never blocks the go. A pass where P10 named a missing rule: say the limits of the host row "Auto mode" (a pass proves nothing for a Driver).
- Recorded after `open`: a section "Permission trials" in `brief.md`, one line per trial, `<capability>: <command> -> ran | refused: <exact text> | no trial: P10's rule check only`, with the P10 line. Before a batch, the result is told, not recorded.
=== batch-plan
# Starting a batch: the preflight and the plan

Only in the turn where the user gave the go.
1. Preflight, all or nothing. In chantier's own checkout (the dev mode) first the sync (`help sync`); a pending sync never blocks the go (the plan says `sync pending: held by ...`); only you sync. Then `$CHANTIER preflight` with the batch's options (`--mode`, `--autonomous-releases`, `--grant-fixes`) checks P1, P4, P5, P6, P7, P8, P10 (warns, never fails; ask the allow-rules question if not asked yet, `help allow-rules`), P12, and P14 (informational). You check P2, P3 (the go is in the user's own message of this turn), P9 (`help forge-permissions`) and that a person is at the keyboard. Warn of each skill or tool the playbook names and you lack. Then the trials (`help trials`). On a failure start nothing, offer no other way, say which condition failed and what the user can do.
- Forced `direct`, or no argument under the host's Remote Control notice: `$CHANTIER preflight --direct` (P1 passes on any Claude Code entry point or Copilot agent session, P2 left out). Otherwise the Foreman-mode preflight; with no forced mode a P1 or P2 failure alone makes the mode direct; with `foreman` forced it is the refusal of step 2.
2. Show the plan: `help batch-plan-show`. The mode question and the steering mode: `help batch-plan-mode`. The cut and the waits: `help batch-plan-cut`.
3. Open, start the Foreman or steer, start the watcher: `help foreman-start`.
=== batch-plan-show
# The plan to show

The CRs (the `3-ready` ones first) and what each waits for, with the reason of any queue that is no real dependency; how many CRs start at once, on how many slots (the `limits:` line of `$CHANTIER playbook`; `open` takes it with no `--slots` and refuses a configured 0), and on a surface the other batches of P14 so the user picks the slots knowing the machine's load (no cap proposed); the mode as a question; the budget; the floor with its two terms and critical path and the delivery time "not before <time>" or "unknown" with the reason (`help delivery-time`); the team (what `playbook` printed); and who steers.
- An empty batch (a go before any CR is ready) asks the shape too and shows slots, budget, team and who steers; floor and delivery time "none yet: no CR"; no cut.
- A waiver for a stack: offer "one long gate on the top PR only" (lower PRs are ready to merge once CI is green and the Verifier says VERIFIED); on a yes `$CHANTIER order waive stack --note "<the user's words>"`, also during the run; `--note -` withdraws it. A waiver of one CR or of every CR is recorded one CR at a time, `order waive <cr> --note "<the user's words>" --follow-up <folder>`, after filing the CR that runs the long gate on main (`$CHANTIER file`); never a note in a brief.
- Re-read the seat first (`help seat`).
=== batch-plan-mode
# The mode question and the steering mode

The mode question is a batch question in the series format, with no `<short name>-Q<n>` reference: parallel, series (with the order) and stack, your recommendation marked `(recommended)`. Weigh whether the CRs are linked, the overlap of the files their specifications name (the same files or linked CRs point to a stack, independent CRs with disjoint files to parallel) and the cost of the local-gate rule by shape (once per covered PR in parallel or series, once on a stack's top). Name the shared files. A word the user gave earlier answers it. Always pass `open --mode`; never take parallel by default. `order mode --note <mode>` switches on the user's word.
- On GitHub with a stack: recommend installing the `gh stack` extension (the stack driver makes one native stack, mergeable from its top PR or one PR at a time from the bottom; each ready PR may be merged as it comes while it is the only open PR of the stack; nothing about the merge path is recorded in `brief.md`). The stack is made at two PRs handed back ready, each CR joins on top as a draft, a new stack of what remains is made silently after a merge. On a no: `$CHANTIER forge-stack create` over the REST API, recorded in `brief.md`. On GitLab: `forge-stack create` makes the chain of MRs, merged one at a time from the bottom, a middle MR folding into the one below; unproved on GitLab.
- Steering mode, direct (you steer, no Foreman) or Foreman. The argument counts only as the invocation's first word, exactly `foreman` or `direct`. Forced holds for the session until the user's word. With no argument read it at each plan: direct under the host's Remote Control notice or on a host that cannot start a Foreman (P1 and P2), Foreman otherwise; no notice means local. The plan says it in one line, no question, with what direct changes (no Foreman; you steer the Drivers; no grill while the batch runs; new ideas go to the inbox). A forced `foreman` where none can start is refused at the plan with the reason and the way (say "direct", or start from the desktop app); never swapped silently. A batch keeps its steering until the user's word.
=== batch-plan-cut
# The cut, the waits and the depends

- The cut: when the user gave a time and the floor exceeds it, propose the largest set of CRs whose floor fits, short chains first; a CR enters only with every CR it waits for. The rest is "for later" (nothing is moved before the go). Show the whole batch with its floor and the cut with its own; the go names the choice and `open` takes only the CRs chosen. No time given: no cut. Delivery time unknown: say so.
- A parallel batch starts a CR as soon as a slot is free; every open PR is rebased after each merge. Touching the same file is no reason to wait. `depends.json` (`{"after": ["<slug>", ...]}`) only when a CR needs another's result, merged or handed back ready; `open` and `order add` read it and exit 2 on an unknown slug, a malformed file or a cycle.
- Read the specifications for the same lines (a shared table, a template block, a list each appends to). For such a pair propose that the later one waits, with the reason: each merge of one would make the other rebase with a conflict anyway; and the cost: it starts once the other is handed back ready, so it takes longer and a slot may stay free. Small work whose rebase would cost more than waiting is a reason too. The go approves each wait; the user may refuse it per CR. You judge and say why; no threshold.
- While a batch is not closed (running or paused) there is no new plan: new work joins with `order add`.
=== foreman-start
# Opening, starting the Foreman, the watcher

3. `$CHANTIER open [<prepared-folder>...] [--default-branch <b>] [--slots N] [--budget USD] [--mode parallel|series|stack] [--release N] [--direct]`. `open` numbers the batch (`batch-<n>`) and exits 2 while a batch is not closed. With no folder it opens paused with no CR (`--release` refused then; CRs join with `order add --note <folder> --batch <batch>`; the first `take` sets it running). It moves each folder to `4-batch/1-pending/`, names branches and worktrees and writes `brief.md`: complete it from the grill (the team, autonomous decisions allowed, questions to bring back). Right after `open`, before the first `take` or the Foreman, record each wait the go approved: `order after <cr> --note "<cr>"` then `order note <cr> --note "chain: <reason>"` (`--add` adds one, `--note` replaces the list; no `--epoch`).
4. Foreman mode: start the Foreman; direct mode: `help direct-mode` (`open --direct` refuses when your session id is unknown). `<n>` is the next number as Foreman (`foreman get` plus one; a new batch claims 1). The prompt: `chantier Foreman n°<n> of batch <batch>, for the Chief of Staff <your session id>.`, `Your session title: <title>` (`[<code>] ⚙️ Project · Foreman (Batch <nn>)`), the `Read` line of startup-core, role-core and the named sections, `CLI: <$CHANTIER> <command> --batch <batch>`, `Repository: <path>`, `Team:` the `playbook` lines as printed with timing lines and review steps, `Needs:` as printed. Start the session as the host row says, in a session fit for a Foreman; a host that refuses, or an unfit session: give the host's "For you" block after saying what it costs, and "I have not tested this path" for an unproved block. More: `help foreman-start-more`.
5. When `open` ends with `watch: not running`, start the watcher now on the session's yes (`help watcher`), the printed command as is; also after a batch opened paused.
=== foreman-start-more
# Starting the Foreman, other cases

- On `[foreman→chief-of-staff] ready <batch>`, arm the heartbeat if the host row says you do. After an empty `open` you may start the Foreman at once: it claims its number, sends `ready` and waits for the first order; its wait counts in the spend and it arms no heartbeat while the batch has no CR.
- Reusing the last Foreman: when the previous batch's Foreman session still exists, even stopped, you may reuse it with the new batch and its number 1; the prompt is the full one, so it reads the cards again. A new session stays the default where the host lets you start one: a reused Foreman carries its old context and the batch pays for it. The host row says how the prompt reaches an idle or closed session.
- An ask from a Foreman in a worktree: tell the user the impact (Write is refused in the planning folder, so no Driver can leave work and evidence there) and give the "For you" block to start again on the main checkout. Suggest no way around; if the user allows one for that batch, pass their words as they wrote them and never turn them into a rule.
=== steering-reports
# Status, turn ends and reports

- `$CHANTIER status [--notes]` with PR links, and the planning folder's `STATUS.md` for the user. Before a report, `$CHANTIER status --refresh` with no epoch. A red CR is a question for the user. Never read the Foreman's transcript.
- A host notice that the Foreman ended a turn is no line: end that turn at once, no tool call, message or report, restate nothing. You act on the Foreman's lines, the user's words and your reports. A notice showing the Foreman stopped on an error (a usage limit, an API error) with no line from it: one line to the user, still no tool call (unproved).
- Reports follow `status-layout.md`, read whole before each. Never the word epoch to the user: `Foreman n°<k>`; a stale-Foreman refusal is reported by that number.
- Every Progress report gives the remaining floor and the updated delivery time in **Notes** (`help delivery-time`, counted again on the state `status --refresh` just wrote), and beside it `partial stack mergeable below <commit>`. A delivery time an hour or more later than the last told: the slip and its cause in one line, nothing else (no new cut, the CRs stay). When it passes the time the user gave: `$CHANTIER order note - --note "deliver by <time>"` and send the printed line to the Foreman; direct mode applies the Foreman's "Deliver by a time" yourself.
- Before each report, in both modes, `git status --porcelain` on the main checkout (the clone `take` names) and name every path outside the planning folder not named yet; revert nothing, hold no CR back. Give the latest `main checkout:` note of a CR merged since the last report.
- Stack batch: before each Progress report read `$CHANTIER forge-stack show`; **Notes** takes `partial stack mergeable below ...`, or while a check fails `stack changing: last mergeable below <sha7>` (or `stack changing`).
=== refused-push-chief
# A refused force push, your part

On `[foreman→chief-of-staff] push <branch> <expected remote sha> <local sha>` (in direct mode the Driver's `push` line) the push climbs to you. A covered branch (any `chantier/*` branch that is not the default branch, `--force-with-lease`) is never a question for the user: judge it and run it. The check and judgement are the Foreman's (`help refused-push`), run in full again whatever the Foreman's note says, at the shas of the line; read `handoff <cr>` for its `push judged legitimate` and `refused:` or `push not tried: route rule missing` notes. In direct mode the gate check and its skips are yours, once.
- Legitimate: `$CHANTIER note <cr> "push judged legitimate at <local sha7> for <branch>: <one line>"`, then the plain `git push --force-with-lease` in the route form, no ask. Accepted: answer `pushed <branch>` (direct mode: the CR's `take` note); the user hears nothing.
- A hard check that fails (a branch `handoff` ties to no CR of this batch, or no long gate passed at the local head outside the skips): push nothing; `$CHANTIER note <cr> "push refused <branch>: <reason>"`; answer `push refused <branch>: <reason>`; no user question.
- A branch that is not a `chantier/*` branch, or the default branch: push nothing, ever; record and answer `push refused <branch>: not a chantier branch`; tell the user as information (branch and CR). A yes does not push it.
- A failed lease: answer `push failed <branch> <git's text>` and tell the user at once with what it means (the remote moved); never retried. All answers go to the Foreman, never a Driver; in direct mode the CR goes back to a fresh Driver with the result as its `take` note (`push: <result>`). More: `help refused-push-chief-more`.
=== refused-push-chief-more
# A refused force push, the user's part

- Not legitimate (the checks pass, your judgement differs from the Foreman's): push nothing; tell the user at once in the report's shape (**For you:**, no tip) naming both judgements, the CR, the branch, the expected and local shas. On their go, first `$CHANTIER note <cr> "push on the user's go at <local sha7> for <branch>"`, then the route form; a host refusal then: record it (`refused:` note), show the exact text and command, answer `push refused <branch>: <exact text>`, no second try. On their no: `push refused <branch>: <the user's reason>`. The Foreman's ask that a push is not legitimate is relayed the same way.
- The host refuses your push: record `$CHANTIER note <cr> "refused: <exact command> -> <exact text>"`, then one question in the report's shape (in direct mode also `$CHANTIER asks "<question>"`) naming the CR, branch, shas, both judges with their `push judged legitimate` lines, each step's outcome quoted from `handoff <cr>` (the Driver's refusal, the Foreman's refusal or its `push not tried`, yours, each with exact command and text) and the exact command you will run on a yes.
- On the yes: run it once, unchanged. Accepted: `pushed <branch>`. Refused again: record it, show the user the exact text and the command so they can run or allow it, answer `push refused <branch>: <exact text>`; never a second try, another form, or a change to the permission settings. On the no: answer with their reason.
- The Foreman's `pushed <branch>` answers nothing (a report line); its `push failed <branch> <text>` is told to the user at once.
=== refused-rebase-chief
# A refused rebase, your part

On `[foreman→chief-of-staff] rebase <branch> <base>` (direct mode: the Driver's `rebase` line) the rebase climbs to you, the same ladder as the push's. The check and run are the Foreman's (`help refused-rebase`): the branch is covered and `handoff <cr>` ties it to the CR (its `worktree: ... branch` line gives exactly it, its `<base>` the line's), the worktree clean; then `git -C <worktree> fetch <remote>` and one command, `git -C <worktree> rebase <base>`.
- A clean rebase: note `rebased <branch> onto <base> at <sha7>` and answer it. A conflict: leave the rebase stopped and answer `rebase conflict <branch> onto <base>` (a new Driver resolves it). A check that fails: rebase nothing, answer `rebase refused <branch>: <reason>`, no user question.
- Answers go to the Foreman; in direct mode the CR goes back to a fresh Driver with the result as its `take` note.
- The host refuses your rebase: record `$CHANTIER note <cr> "refused: <exact command> -> <exact text>"`, then one question naming the CR, the branch, the base, each step's refusal (exact command and text) and the exact command you will run on a yes; on the yes run it once, unchanged; on a no or a second refusal answer `rebase refused <branch>: <text>`.
=== refused-forge-chain
# Two more refusals you settle

- A refused `gh pr ready <n>` or `gh pr edit <n> --base <branch>` on a PR the record holds for a CR of this batch (`handoff <cr>` shows it): run the command once, unchanged, and note the result with `$CHANTIER note <cr> "<what>"`; no user question, told in the next report's Notes. A host that refuses your own run: record the exact text, ask one question naming the command, run it once on the yes. A PR the record does not hold, or of another batch: not yours; ask the user.
- A chantier subcommand the host refused when chained (the host's classifier refuses a chain): run it again alone, once, and note it. A second refusal is reported with its exact text (floor 9).
- Never a `--force`, never another form of the command, never a change to the permission settings.
=== asks
# The asks

`$CHANTIER asks` lists every ask still unread, sent or not; `asks --read A-<k>` or `--read all` once the user has heard them. `asks --read A-<k>` runs in the same turn you relay that ask to the user or act on it (an `order`, an answer to the Foreman), not later; `--read all` only after every unread ask listed has been relayed or acted on, never to clear the list. An ask that waits for the user stays unread until the user has heard it. At each report `asks` lists what is still unread: each is relayed or acted on in that turn. A host may limit messages between sessions (its row says how): a refused send is reported, never sent another way.
=== cost
# The cost

The cost table of a report, and `cost --explain`: see `status-layout.md`, "Cost". The Chief of Staff's own cost is the `Chief of Staff, whole session` line; a Griller's and the grill's are in no batch (`help griller-cost`). Say a past cost only from `$CHANTIER status` or `cost`.
=== chain-conflict
# A chain and an early conflict

- On `[foreman→chief-of-staff] chain <cr> after <cr>: <reason>` record it at once without waiting for the user: `order after <cr> --note "<cr>"`, then `order note <cr> --note "chain: <reason>"`. The same covers a chain the go approved, recorded at `open`. The next report says the chain and its reason. The user turns it off while the CR is queued with `order after <cr> --note -`; once started, the chain stands until the stack driver restacks.
- On `[foreman→chief-of-staff] conflict <cr> with <cr>...: <paths>; switch to a stack?` tell the user, in their language: the PRs by link and CR name; the paths both change; that each PR stays ready to merge on its own but merging one makes the others conflict and go back to their Drivers for a rebase; and the offer to switch to a stack. On a yes `order mode --note stack` and say what the switch does (`help merge-series-stack`). On a no record nothing, send nothing; the batch stays parallel. In direct mode run the check yourself and put the same question; the ask is still recorded with `$CHANTIER asks`.
=== rounds-exception
# The rounds exception

A CR handed back `blocked rounds:` whose last round failed on a red the batch caused (a restack or rebase onto another CR's branch, a CR merged or moved below; judge from the hand-back, `log <cr>` and `diagnosis.md`; in doubt, the user's word) gets its next round from you. The cap is the batch's own `settings.max_rounds`, never the CR's limit `status` shows: +1 per grant, each on its own cause, never above `max_rounds` + 2. Send the Foreman two orders in one message, `order rounds <cr> --note <limit + 1>` and `order note <cr> --note "rounds exception: <the event>; <the failing check>"`, and tell the user in the same message, no wait: `CR-<n>: round <k> granted under the rounds exception: <cause>`. The Foreman takes the CR with that note and no escalation. Every other grant of rounds stays the user's.
=== driver-question
# A Driver's question, a fix, a refused command, a wait

- `ask ... blocked <cr> question: ...`: record the user's answer in the CR's `02-answers.md`, then `order note <cr> --note "answer: ..."`.
- A `fix:` from a release: under the grant the Foreman starts it alone; else show the user its `fix-<n>.md`, and on their go `order add --note <that file> --fix-for <cr>`, or file and grill a CR when it needs more.
- `refused <cr> <text>`: show the exact text, record it at once with `$CHANTIER note <cr> "refused: <exact command> -> <exact text>"`; the user types one line in the Foreman's session allowing that action.
- `qa <folder> <n> findings`: its inbox folder is an ordinary item; triage it with the user, split into CRs as needed.
- A typed wait (`$CHANTIER wait <cr>` lists a blocked CR's waits; `status` shows `| waits:`): cleared on the user's answer, or on a `wait-cleared@1` line your watcher carries: `wait <cr> clear <id> --epoch <n>`, then the take-back path as for any blocked CR. A parked CR: `wait <cr> clear <id> --epoch <n>`, then `order note <cr> --note "wait cleared: <what>"` (Foreman mode), or in direct mode `take <cr> --note "wait cleared: <what>" --epoch <n>` before any queued CR. On `parked <cr>: ...` tell the user in one line: the CR, what it waits for, its slot is free, the batch goes on; ask nothing.
