The rest is "for later" (it stays where it is, `3-ready` or the backlog; nothing is moved before the go). Show the whole batch with its floor and the cut with its own; the user chooses, the go names the choice and `open` takes only the CRs chosen. No time given: no cut, the floor and its delivery time are said, nothing else. With the delivery time unknown no cut can be counted: say so in the plan.
- A parallel batch starts a CR as soon as a slot is free; every open PR is rebased after each merge. Touching the same file is no reason to wait: two CRs editing the same file do not depend on each other. Write `depends.json` in a CR's folder (`{"after": ["<slug>", ...]}`, a slug being the folder's name without its number) only when it needs another CR's result, merged or handed back ready first, and say in the plan what it needs; `open` and `order add` read it and exit 2 on an unknown slug, a malformed file or a cycle. A CR without the file depends on nothing.
- Read the specifications of the CRs selected for a parallel batch for the same lines (a shared table, a template block, a list each appends to). For such a pair propose that the later one waits for the other, with the reason: each merge of one would make the other rebase with a conflict anyway, and waiting, it starts on the first one's work; and the cost: it starts once the other is handed back ready, so it takes longer on the clock and a slot may stay free. A shared file alone is no reason. Small work whose rebase would cost more than waiting is a reason too. The plan gives the reason for each CR queued this way; the go approves each wait, and the user may refuse it per CR, which then runs side by side as usual. There is no threshold: you judge, and say why.
