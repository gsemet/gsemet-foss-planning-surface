Short name: `stack-chain`

# Answers
1. stack-chain-Q1 (2026-11-21): **When the chain is checked.** A. Refused at `ship`: at each ship of a CR already stacked, the CLI refuses when its branch is not based on the head of the CR below ("CR-442: branch not based on CR-441's head"), before a gate or verdict is paid on it.
2. stack-chain-Q2 (2026-11-21): **The stack driver's check before "no restack needed".** A. One card line: it verifies with `git merge-base` that each branch starts from the head of the CR below.
3. stack-chain-Q3 (2026-11-21): **Series batches too.** A. Series and stack: wherever a CR is meant to start from another.
Restatement (2026-11-21): in a stack or series batch, each CR already stacked must start from the head of the CR below; `ship` refuses otherwise, naming both CRs; the stack driver checks with `git merge-base` before concluding no restack is needed (card line); the CLI restacks nothing (no git write) and has no flag to force past the refusal: the fix is the stack driver's restack.
4. stack-chain-Q4 (2026-11-21, after the full restatement): **Grilled enough.** A. Yes: the spec-writer, then the critic; destination batch-30 (a stack batch, joined with `order add`).
Spec v1 (2026-11-21): written; three open questions (who fixes a refused ship; only at ship; a CR taken on another's branch but not placed), technical: sent to a Fable advisor.
5. stack-chain-Q5 (2026-11-21, spec v1 open question 1, Fable advisor): **Who fixes a refused ship.** The caller of the refused `ship` owns the branch (driver.md, "Who moves a branch"), so it rebases; no route through the stack driver or the Foreman. Follow-ups: one refusal message for both modes (`CR-442: branch not based on CR-441's head 1a2b3c4: rebase onto <branch below>, push, ship again; nothing recorded`); state the consequence (checked against the CR below's recorded head, so a stacked working CR is refused at its next ship each time the CR below shipped a new round or was rebased, and rebases without waiting for the Foreman's note); fix driver.md's `rebase: mode <mode>` paragraph (~946-953), whose pre-rebase `ship` would be refused, and search the cards for any other `ship` before a rebase (lines ~203, ~484).
6. stack-chain-Q6 (2026-11-21, open question 2, Fable advisor): **Only at ship.** One more refusal at `stack --out-of-draft` only (`_check_out_of_draft`, commands/delivery.py): each named CR whose recorded head does not hold its CR below's recorded head, same helper, exclusions and `git cannot read` refusal, message ending `then stack --out-of-draft again; nothing recorded`, no flag; card line in the stack driver's paragraph; one parametrized test; scenario step if it costs one step. `stack <crs>`, `forge-stack`, `take stack` stay out of scope, with the reason. Reason: in a stack the stack driver may ship nothing (the incident's path). To name in the restatement to the user.
7. stack-chain-Q7 (2026-11-21, open question 3, Fable advisor): **A CR taken onto another's branch, not placed yet.** Checked when its `start_on` is live (`stacks._live_start`); an unplaced CR with no live `start_on` stays unchecked. Follow-ups: "Words used here", §1 and Goal reworded to "a CR the record places on another CR's branch (placed by `stack`, or taken onto it)"; the CR driver sentence names the first-ship case; tests split (live `start_on` cut from main refused; no `start_on` recorded; owner merged or held not checked); existing test worlds made true to the chain.
Spec v2 (2026-11-21): Q5-Q7 and their follow-ups applied (one refusal message, caller rebases; `stack --out-of-draft` refusal; live `start_on` checked; driver.md `rebase: mode` and other pre-rebase `ship`s fixed; tests split, test worlds made true to the chain); overlaps with CR-428, CR-430, CR-431 and stack-shape-guard named; no open question.
8. stack-chain-Q8 (2026-11-21, spec v2 critic question a, Fable advisor): **A CR below merged on the forge but not yet in the record: what does `ship` do.** A. The check reads the CR below as `take` does, with `landed` (`journal.seen_merged`, as `commands/driver.py` and `commands/facts.py` pass it to `start_base` and `top_cr`): a CR seen merged counts as ended, so the CR above has no CR below there (or the next open one the base functions give) and its `ship` is not refused on it. Reason: after a rebase or squash merge the merged CR's recorded head is in no branch, so the refusal would be false and its fix ("rebase onto <branch below>", a branch that may be gone) wrong, on a CR its Driver rightly moved onto the default branch; `take` already trusts the same journal read, and it stays a read. Follow-ups: the same `landed` at `stack --out-of-draft`; "Words used here" says "not `merged`, not `cancelled`, not seen merged (`journal.seen_merged`)"; one test (the CR below seen merged in the journal, the CR above rebased onto the default branch: `ship` records); with a merge neither the record nor the journal holds, the refusal stands as written (the CLI reads no forge at `ship`), and the card's refusal sentence says: the steering session's `status` records the merge, then `ship` again.
9. stack-chain-Q9 (2026-11-21, critic question b, Fable advisor): **A CR above already on the branch below, whose CR has not shipped its new head: what does the refusal say.** A. A second message, when the head holds `<remote>/<branch below>` but not the CR below's recorded head: `CR-442: CR-441's branch moved since its last ship (<rec7> -> <tip7>): it ships first, then ship again; nothing recorded`. Reason: the first message's fix ("rebase onto <branch below>") is already done there, so a Driver would rebase in a loop and pay tokens for nothing; the check itself stays on the recorded head (Q5's follow-up holds, the head the gates, verdicts and `stack --out-of-draft` read), only the words change. Follow-ups: the remote ref is read as it stands in the clone (no fetch by the CLI; unreadable or absent: the first message); one read-only `merge-base --is-ancestor` more, only on the refusal path; the card's refusal sentence names both messages (the second: wait for the CR below's `ship`, or the stack driver ships it first, bottom up); one test case; `stack --out-of-draft` keeps its one message (it compares two recorded heads).
10. stack-chain-Q10 (2026-11-21, critic question c, Fable advisor): **Is the release CR checked too.** A. Yes, at `ship` and at `stack --out-of-draft`: its CR below is the top CR (`start_base`'s release rule, `top_cr`, with Q8's `landed`), checked against that CR's recorded head with the same helper and messages; `check_release_branch` at `take` stays as it is. Reason: Q3 says "wherever a CR is meant to start from another", and the release is the stack's top piece, restacked "like any PR above" by the stack driver's card; `check_release_branch` proves only that the top branch holds the CRs under it at the release's first `take`, never that the release's own branch sits on the top CR's head after a later restack, which is the incident's shape one CR higher. Follow-ups: "A CR the record places on another CR's branch" drops "neither a `release`" (a fix and a held CR stay excluded; a release with no open CR under it has no CR below); section 1's "The release CR keeps its own check" and Out of scope's "the release CR" reworded; the release Driver's card gets the refusal sentence (it rebases as the `ship --conflict` rule already names it); one test case each (`ship`, `stack --out-of-draft`).
