## 2026-11-12, Griller session

**What does `chantier board` lack?** The view is limited; one cannot really act from it; and in
remote it does not show (the mod does not show on the user's phone, for example). The user wants
a mechanism to *see* the state of the planning surface **and interact with it**, and something
more visual. Assumption to work from: network communication is possible (an `ip:port` is
reachable); no reverse proxy for now.

**Is the web board used today?** It works very well on the same PC as Claude, but not from
another PC or Mac on the same network, nor from the phone.
- Griller's note: preflight reports no `chantier.yaml` in this repository, so the board listens
  on its default `127.0.0.1:8765`, reachable from this machine only; `board: host: 0.0.0.0` (or
  the Tailscale address) is what `docs/boards.md` gives for other machines.

**Which actions from the view?** All of these:
- read the Markdown files (of a CR);
- add an intake: paste an idea, or fetch it from GitHub (an issue), and so on;
- grill a little, above all by choosing among decisions (options offered);
- follow the progress as a kanban;
- follow the costs during a batch **without causing an extra turn** (of the Chief of Staff);
- answer the asks;
- file and triage (inbox, P1-P4, `3-ready`, abandon);
- batch orders (go, add a CR, slots, budget, rounds, pause);
- talk to the Chief of Staff.

**Who executes an action from the page?** The Chief of Staff decides: the page passes it on, and
the Chief of Staff applies it as if the user had told it.

**Protection once it acts and listens on the network?** A token: a secret generated by chantier
(in the URL or as a simple password), given to the user by the Chief of Staff.

**Split into several CRs?** Not now: keep grilling; the user first needs prototypes, to see what
it can look like. The split comes later. (Proposed for then: the read view; the page-to-Chief of
Staff channel with the token; grill by choices; intake from GitHub.)

**An action sent while the Chief of Staff is busy or its session closed?** A queue: the action
waits, shown "pending" on the page, and the Chief of Staff handles it at its next turn; with the
session closed, the page says so.

**Live costs during a batch: how fresh?** On demand: a "recompute" button; otherwise the last
known cost with its age.

Views: the kanban with a CR sheet (its Markdown files); the asks and the chat to the Chief of

**Markdown for the agents, JSON for the server (the user, 2026-11-13):** the agents keep
expressing themselves in Markdown; the board's server stays deterministic and reads JSON. So
there must be a refresh that turns the Markdown into JSON. It is called when an agent notices a
Markdown file it changed, or from the CLI, which gives the Markdown files changed since the last
refresh (by a checksum, for instance).
- The JSON holds **condensed** versions, not the Markdown's text: the title, yes; and, instead of
  the text, **a summary of the CR's current state**. A summary is a judgment, so an agent writes
  it, not the CLI.
- So the refresh is a loop the **agent** starts: the CLI **lists every gap** (each Markdown file
  changed since the summary it fed, by its checksum), the agent reads what changed, then **calls
  CLI commands that set the condensed fields** (a CR's summary, for example). The CLI stays
  deterministic: it computes the gaps, stores what it is given and records each file's checksum;
  it writes no summary itself.
- **No frontmatter forced** in the Markdown files: they stay free text; the condensed fields
  live in the JSON only.
- **Who refreshes:** ideally the agent that just changed a file calls a **linter**, which tells it
  what to do (which gaps, which command to run for each). At worst, the **Chief of Staff** runs
  the linter and closes the gaps left behind.
- **Scope, for now:** CRs only, but **every CR** (whatever its stage), each with its **title and
  summary**. No batch or project summary yet.
- **The checksum covers** (the Griller's proposal, agreed by the user): `intake/*.md`,
  `01-intent.md`, `02-answers.md`, `03-change-spec.md` and an archive's `delivery.md`; not
  `STATUS.md` (the CLI's, its state shown from the record), `work/` (changes every round) or
  `evidence/`. The summary says what the CR means; its progress comes from the record, beside it.
- **Fallback (the user):** at worst, each card has a **"refresh summary"** button. Since only an
  agent writes a summary, the button asks for it (through the board's request to the Chief of
  Staff); it does not write the summary itself.
- **A late summary shows (the user):** a card whose summary is older than its Markdown files
  (a checksum gap) carries **a small icon**, nothing more.
