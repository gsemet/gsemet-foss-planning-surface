# Answers

- Q: Who does the fast-forward? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): the session that records the merge: the Foreman in Foreman mode, the Chief of Staff in direct mode; never a Driver or a worker. The request says "the steering session", and it is the only one that sits on the main checkout and knows the merge is recorded.
- Q: Does the CLI do it (inside `order merged`)? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): no, the agent runs git; the CLI may at most say what is off, as it does today. The CLI runs no git command that changes anything, by AGENTS.md.
- Q: What counts as a "clean" main checkout? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): no change, staged or not, to any tracked file; untracked files do not count and are never moved, read or deleted. The request says so, and this very checkout always has untracked files (the planning folder, the user's notes).
- Q: What if the incoming commits add a file that exists untracked in the checkout? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): git refuses the fast-forward, and the session leaves it refused and says so; it never forces, moves or deletes the file. "Never touching untracked files" has no exception.
- Q: What if the main checkout is not on the default branch? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): nothing is done: no checkout of another branch, and no update of the local default branch behind the user's back; one line says it. The user chose that branch, and here a switched branch changes the running plugin.
- Q: What if the local default branch has diverged from the remote (local commits)? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): the fast-forward is impossible, so nothing is done and one line says it; never a reset, a rebase or a merge commit. Only a fast-forward is without loss.
- Q: What does a skipped or refused fast-forward cost the batch? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): nothing: the batch goes on, the session says once why (dirty, other branch, diverged, refused by git or by the host) and tries again at the next merge. It is a convenience, never a gate; no workaround, by the no-fallback rule.
- Q: What about a steering session that cannot write the main checkout (a worktree or remote session)? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): it does not try another way; it says so at once, as the fail-fast rule asks. The host reference already says such a session is not fit for the main checkout.
- Q: How does the session know an eval is running? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): it does not guess: the card says "unless the project's rules forbid it", and this repository's AGENTS.md already forbids any change to the main checkout during an eval. A user's project rules rank above the cards, and the cards must not know this repository's evals.
- Q: Inside an eval's workspace, does the batch under test fast-forward the sandbox's main checkout? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): yes, like any project's batch: it is the behaviour under test, and the eval kit's audit and the dry run are brought in line in the same CR. AGENTS.md's eval rule protects chantier's own checkout, not the sandbox's.
- Q: With an external planning surface, which checkout is meant? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): the code repository's clone, under the same conditions; the surface's own checkout keeps its existing rule. The stale code is in the code clone, and the surface is already kept in step by `chief-of-staff.md`.
- Q: Does the session reload the plugin or read its cards again after a fast-forward? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): no. The CLI is read live, which is what the request needs (the price table); the cards load at the next session or with `/reload-plugins`, as CONTRIBUTING.md says.
- Q: Which gates does this CR pass? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): `just check`, `just scenario` (the flow changes, and the scenario shows a fast-forward done and one refused) and `just eval-dry-run` if the audit changes. AGENTS.md and "Changing the kit" say so.

## Open for the user

- Q: Is the fast-forward on by default in every project chantier runs in, or only where the project asks for it? It moves the files of your own working copy while you may have them open; today chantier changes nothing there but the planning folder and the merged CRs' worktrees and branches. — Recommended: on by default, under the strict conditions above (default branch, no tracked change, fast-forward only), with one line in the next report ("main checkout: fast-forwarded to `<sha>`", or "not fast-forwarded: `<why>`"); a project turns it off with a rule in its `AGENTS.md`. It is what your request describes, a fast-forward of a clean tree loses nothing, and a stale checkout is the more common surprise. The other choice is off by default and on by a key in `chantier.yaml`: safer, but then chantier's own repository needs the key and most users never learn of it.
- Q: When does it happen: after each merge recorded, or once, at the batch's pause? After each merge, in this repository, the CLI of a running batch changes under it (it is read live): good for a price or a fix, a risk when a merged CR changes the record's format mid-batch. — Recommended: after each merge, as your request says. The stale CLI is the measured fault; a CR that changes the record's format is rare and already has to handle a batch in flight. At the pause only would be safer and would not have fixed the batch-14 case.
