# Answers (grill with the user, 2026-11-07)

1. Target: any project. An existing repository without chantier, or a folder with no git; on a
   folder with no git, explain what is missing (git, a remote, `gh` or `glab`) and offer
   `git init`, run on the user's yes.
2. Files: the five stage folders, created empty. The `.gitignore` line for `.agents/changes/` is
   explained only: the user adds it. `AGENTS.md` gaps are explained with their impact, then the
   exact text is shown and written only on the user's yes, section by section.
3. Pedagogy: a guided tour.
4. Logic: a card plus a CLI command `chantier init`. The command only creates the five empty
   folders for now ("we will put bigger CLI changes later"); no `.gitkeep`.
5. Repository rules (writes only in `.agents/changes/`; a CLI tool only from measured token
   cost): leave them as they are for now.
6. Invocation: an argument of the skill, `/chantier:chantier init`, or plain words ("chantier,
   initialise this project"). No dedicated slash command.
7. Re-run on an initialized project: files unchanged when already right, improvements assessed
   again, the tour offered, not imposed.
8. The tour writes nothing in the project. It runs in the chat or as generated HTML.
9. Chapters: words and roles; folders and a CR's life; harness and `AGENTS.md`; money and the
   user's decisions.
10. The first-turn introduction stays; when the project has no `.agents/changes/`, it ends by
    offering init. With init, the introduction is skipped: the tour covers it.
11. Chat or HTML: asked once at the start, chat by default; on Remote Control the HTML is sent as
    a file.
12. HTML location: the system's temporary folder, `<temp>/chantier-tour-<project>/`.
13. Diagrams: generated by the agent, not the docs SVGs.
14. Order: tour first, then the improvements.
15. Gates: none run by init.
16. Improvements: keep it simple; the agent proposes improvements itself, from what it read.
    Form: what fits in a rule goes as `AGENTS.md` text, written on the user's yes; what needs
    code (tests, CI) goes as a CR filed in the inbox, on the user's yes.
17. The example CR: not specified; the agent's call.
18. Hosts, docs, scenario: "I don't know. Focus on presenting the concepts well."
19. Thread: the story of one CR, end to end; each concept appears when it serves.
20. Metaphor first (the building site: chief of staff, foreman, team leads, workers), then the
    exact term.
21. Vocabulary: about ten core terms in the story, the rest in a glossary at the end.
22. No comprehension check, no quiz.
23. Workers named in the story: Coder, Inspector, Verifier; the other three in the glossary.
24. Previews of what the user will read: a CR folder tree with the project's real paths, and a
    `status` table.
25. Cost: the mechanics, with no figure.
26. End of the tour: phrases to say, the proposed improvements, the glossary, the `.gitignore`
    line.
27. HTML: one page, from a template the plugin ships (fixed style, table of contents, slots);
    the agent fills in the project's text and its diagrams.
28. Reading the project: light. Instruction file and what it links, README, build files, CI
    workflows, the tree on two levels; no code reading.
29. Length in the chat: about 60 lines asked; the user then approved as "perfect" the simulation
    run on the chantier repository (about 95 lines): it is the reference, `reference-tour.md`.
30. Diagrams in the tour: who talks to whom; the five folders; a CR over time.
