# The evals folder is self-sufficient: anyone can run a campaign from it

Filed 2026-11-15 by the Chief of Staff, on the user's word: "make the evals folder self-sufficient, e.g. if another person wants to run them".

What running batch-18's evals (CR-275) needed that `evals/` does not give today:

1. **The sandbox is the maintainer's.** `kit/sandbox.py` (`REPO`), `kit/sandbox_forge.py` (`REPO`) and `kit/sandbox.json` name `gsemet/chantier-eval-sandbox`; another person cannot push there, and the README says "the repository is a constant of the script" (a safety: `reset` force-pushes). Give a person a way to run on their own sandbox (create it, publish the base, point the kit at it) that keeps that safety: one place names the repository, and `reset` still refuses anything that is not a sandbox at the recorded base's history.
2. **The operator's prompt is assembled by hand.** The runbooks give it with `<this checkout>` and the workspace to fill in; CR-275's spec rewrote it with absolute paths. `setup.py` already prints the `open` and `merge` lines: it prints the operator's prompt too, ready to paste, with the absolute paths filled.
3. **Starting the operator's session is not described beyond "type it in the desktop app".** What worked on 2026-11-15: a chantier session at the desktop started the operator's session on the workspace itself; the app first asked the user to trust the new workspace folder, which it can only ask while the Code tab shows the session (refused under Remote Control), and wanted the folder's native spelling (backslashes on Windows). Say both ways (open the folder once from New session, or ask a desktop session to start it), and the trust step.
4. **Prerequisites in one list** at the top of `evals/README.md`: the plugin installed from the checkout, `uv`, `git`, `gh` logged in with push to the sandbox, Claude Desktop at the desk (not Remote Control) for the start, Auto-fix off; then the per-campaign steps.
5. **Before launching a campaign, recommend turning off the host's PR automations** (the user's word, 2026-11-15: "before the campaign next time, recommend turning off auto-fix and auto-close PR"): on Claude Desktop, the global Auto-fix setting (Settings > Code or Settings > Claude Code) and the auto-archive / auto-close on PR merge or close. What happened in real-direct run 3 of 2026-11-15: the operator's session got Auto-fix events on a sandbox PR before it was turned off per PR (`mcp__ccd_pr__set_monitor`, or the PR's ⋮ menu in the Changes card). The official docs describe only the per-PR switch and say nothing of a session or global default for PRs opened later (https://code.claude.com/docs/en/desktop.md#monitor-pull-request-status); third-party bug reports say the global toggle may not reach PRs of local sessions: so the README says both (the global setting off before the run, then a per-PR check), and marks the global one unproved. The runbooks' and the hosts card's "Auto-fix off ... gives no path" line (`evals/README.md`, "Before you start"; `references/hosts/claude-code.md`, "Auto-fix events") gets these paths.

6. **Two more staging lines** (batch-18 eval study, 2026-11-15; retro-critic: before release): no board left running from an earlier run (run 2's `chantier board` failed on a port in use), and the campaign's cost read after `close` from the closed batch's record (run 2's cost rose from $11.47 to $11.91 between the audit and the close).

Done when a person who never ran one, with only this repository and their own GitHub account, can stage and start `real-foreman` by following `evals/README.md`.

Constraint: during an eval the main checkout does not change (AGENTS.md); this CR runs in a later batch, after batch-18's evals. Generality: Claude Code and Copilot hosts, GitHub (the sandbox is on GitHub; a GitLab sandbox is out of scope unless the grill says otherwise).
