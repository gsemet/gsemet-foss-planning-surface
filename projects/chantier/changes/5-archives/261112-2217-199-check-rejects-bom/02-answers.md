# Answers

- Q: Which files does the gate check? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): every tracked file of this repository, with no list of exceptions; a file is red when its first three bytes are the UTF-8 BOM. No tracked file has one today, no binary format in the repository starts with those bytes, and a list of exceptions would be the place where the next BOM hides.
- Q: Does the gate also look at untracked or ignored files? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): no, tracked files only. A gate binds to a commit, and the user's untracked files in a checkout are not the gate's business.
- Q: Is it part of `just check` on the three systems, or a separate recipe? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): part of `just check`, so it runs on Linux, macOS and Windows in CI and in every Driver's fast gate. The request wants a BOM red at the gate, and a separate recipe would be skipped; it must stay fast, as AGENTS.md asks of the structure tests.
- Q: What does a red result say? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): it names every file that carries a BOM, in one run, and says the file must be UTF-8 without a byte-order mark. A Coder then fixes all of them in the same round instead of one per run.
- Q: Does the gate also reject UTF-16 or UTF-32 marks, or files that are not valid UTF-8? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): no, the UTF-8 BOM only. It is the only fault measured (twice); anything more is speculation.
- Q: Does chantier refuse a BOM in a user's project (in the CLI's `gate` or `ship`)? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): no. The CLI's scope is the frame, a project's own gate decides what is red there, and a project may keep a BOM on purpose; the cards carry the rule to the agents.
- Q: Which cards repeat the rule, and what do they say? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): `worker.md`, in the Coder's and the Conflict-resolver's sections, one short line each: never add a byte-order mark to a file, with the Windows cause (`Out-File`, `Set-Content -Encoding utf8` on PowerShell 5.1) and a pointer to `concepts.md` rule 9, which stays the one full statement. Both faults came from these two roles; the other roles keep the rule through `concepts.md`.
- Q: What does a worker do with a file of the user's project that already has a BOM? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): it leaves the mark as it found it: the rule is "add none", not "strip all". A resolved conflict or an edit keeps the file's encoding as the base has it, so chantier never rewrites a project's choice.
- Q: Does the Conflict-resolver check its resolved files before it continues the rebase? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): yes, the card says a resolved file starts as it did before the conflict (no new BOM) before the rebase continues. PR 137 shows the fault enters at that exact step, and in a user's project no gate may catch it later.
- Q: Does the existing BOM test on the agent files stay? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): the Driver's choice, as long as an agent file with a BOM stays red and its reason (the hidden frontmatter) stays written. It is an implementation detail once the general check covers every tracked file.
