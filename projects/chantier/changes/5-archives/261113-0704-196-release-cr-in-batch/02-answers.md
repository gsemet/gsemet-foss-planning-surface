### Behaviour

- Q: Is a release CR in a batch still a kind of its own? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): Yes for who runs it and what guards it (a Release driver, the project's procedure, `release go` before each irreversible action, one release per batch). No for its place in the batch: it is a CR of the batch like the others, with dependencies, a place in the series or the stack, a branch on the CR under it and a PR in the stack. The sentence "a release CR sits outside a series and a stack, on the default branch" goes away for the release.
- Q: What does the release wait for? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): Every other CR of the batch, always, the ones added later too. The CLI keeps that list as it does today; it is not hand-edited. A release that waits for only some CRs is out of scope: a stack merges from the bottom up, so the release can only be its top.
- Q: When does it start: the others ready, or merged? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): One rule: it starts once a single branch holds all the work it ships. In a stack or a series batch, that is when every other CR is ready or merged: the top CR's branch holds everything. A blocked or working CR keeps it waiting. A cancelled CR does not hold it back (as today): it ships nothing.
- Q: And in a parallel batch? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): In a parallel batch each PR is on the default branch and no branch holds all the work until it is merged, so the single rule gives today's timing there: the release starts once the others are merged or cancelled. It is still drawn and reported as a CR of the batch with its dependencies. See "Open for the user", question 2.
- Q: Where does it stand in a stack or a series? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): On top, always. Its branch starts on the top CR's branch, its PR's base is that branch, and the stack driver treats it as the top piece (it restacks it with the rest and refuses an order that puts a CR above it). In a series it is the last of the order. A CR added later goes under it.
- Q: Is its PR a draft? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): It follows the shared definition of "ready to merge": a draft while its base is not the default branch, ready once the stack under it is merged and it is retargeted to the default branch and green. "A release PR is no draft" stays true only for a release whose base is the default branch.
- Q: What do its version bump, changelog and notes cover? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): Everything between the previous tag and its own head: what the default branch already holds since that tag, plus every CR under it in the stack. The procedure's commands run on the release branch, which is on top of all of it, so `git log vPREVIOUS..HEAD` and the "N changes" count are taken there instead of on the default branch. The version commit is the last commit of the stack; nothing may merge after it before the tag.
- Q: How does the prepared release read in `status` and the reports while it waits for the merge? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): As a CR that is ready (its PR open and green, waiting for the user's merge), not as a blocked CR. Today the only way is `handback blocked merge:`, which reads as trouble. After its merge it goes on to the tag and the publication and ends "released" as today.
- Q: What happens if a CR below changes after the release PR is open? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): Two cases. A move with no change of content (a restack, a rebase onto the default branch after a partial merge): the release PR is restacked like any CR above, and its checks run again; its notes are carried. A change of content (a CR below gets a new round, is dropped, or a CR is added under the release): what the release ships changed, so the release goes back to a Release driver, which runs the procedure again from its first step on the new base and refreshes the same PR (version commit, count, notes, captures). The drafts the user edited are read again, never rewritten from scratch. The steering session decides which case it is from the CR's log; when unsure, it is a change of content.
- Q: A defect the release finds before the stack is merged? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): It goes back to the CR that owns it when one does (a note and a take, as for any ready CR), and the release is redone after. A fix CR, on the fast track on the default branch, stays what it is today for a defect found once the stack is merged. Before the merge, a fix that belongs to no CR of the batch joins like any added CR, under the release.
- Q: When may the irreversible actions happen? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): Only once the release PR is merged on the default branch, which means every CR under it is merged. Until then `release go` answers no for the tag, the forge release, a publication and an announcement, whatever the approvals or the grant say; "auto" does not lift this. After the merge each action still needs the user's go, exactly as today (an approval per action, or the grant). The announcement is never posted by an agent.
- Q: May the steering session merge the release PR while CRs under it are unmerged? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): Never. A release PR merges only when its base is the default branch. Who merges it then is under "Open for the user", question 3.
- Q: Is a release alone in its batch changed? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): No: it starts when taken, on the default branch, with no confirmation.
- Q: Is direct mode different? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): No. The same rules hold with the Chief of Staff as the steering session.
- Q: Does a batch opened before this change keep running after it? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): Yes. chantier runs from the main checkout, so the change may load in the middle of a batch: the new CLI reads the batch's record as it is, with no migration by hand.

### Risk

- Q: What is the main risk? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): An irreversible action on work that is not merged, or a tag on the wrong commit. The guard is in the CLI, not only in a card: no `go` for an irreversible action before the release PR is merged. The project's own `just tag` already refuses unless the default branch's head is the version commit.
- Q: A check that only runs on the default branch (chantier's eval campaigns, a post-merge deploy)? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): It cannot run before the release PR is prepared. The release PR is the last merge of the stack, so the user who wants such a check first merges up to the CR under the release, lets the check run, then merges the release PR. The procedure says so; chantier imposes nothing.
- Q: Stale notes? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): Covered by "a CR below changes": a change of content always sends the release back. The count line and the commit list are checked again by the procedure's own check at the new head.
- Q: A stack merged only in part? — Advisor (Fable, answering in the user's place on the user's word of 2026-11-12): The release stays on top of what remains and cannot merge or act until the rest is merged or dropped. Dropping a CR under it is a change of content.

## Open for the user

Not decided. Each has a recommendation; the specification waits for the user's word on them.

1. **Does the release still wait for a separate "confirm the version" before it starts?** Today
   a release that shares a batch starts only on `order confirm`, given once the others have
   ended. Recommendation: no separate confirmation when the release CR's grill already settled
   the version; it then starts by itself like any CR, since preparing a PR is reversible and the
   user still merges it and approves each irreversible action. The confirmation stays only when
   the version was left open at filing ("settle at the end"), asked once the others are ready.
2. **Parallel batch: when is the release prepared?** Recommendation: after the merges, as today
   (no branch holds all the work before), and the user says "stack" when they want the release
   prepared before merging. The other choice is that asking for a release in a parallel batch
   turns the ready PRs into a stack by itself.
3. **Who merges the release PR at the top of a stack?** Today the steering session merges a
   release PR on the user's approval or grant. Recommendation: in a stack or a series the user
   merges it with the rest, from the bottom up, and that merge is the go (no approval asked for
   it); the steering session merges it only under "auto" or an explicit approval, and only once
   its base is the default branch.
4. **May a CR be added to the batch once the release PR is open?** Today `order add` is refused
   once the release has started. Recommendation: accepted until the release PR is merged; the
   new CR goes under the release and the release is redone on top (a change of content). After
   the merge, as today: a fix, or the next batch.
