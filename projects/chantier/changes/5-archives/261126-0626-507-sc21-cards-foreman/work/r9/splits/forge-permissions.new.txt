At your first turn of a session and again at step 1 of a batch, check that the batch's forge operations will go through: read-only, each command alone; on Windows PowerShell 5.1 print `--json` and read the JSON, with no `--jq` or `--template` expression that holds spaces. A CLI not logged in still fails P9 for a batch. Everything below only warns, and the batch starts whatever it says.
1. `gh auth status` and its `Token scopes:` line: `repo` (a fine-grained token prints none: say "unknown: a fine-grained token, see its permissions") and `workflow`. A missing `workflow` is said only as "needed by a CR that touches `.github/workflows/`"; at step 1 name the plan's CRs that do.
2. `gh repo view --json viewerPermission,defaultBranchRef`: `WRITE`, `MAINTAIN` and `ADMIN` can push, edit PRs and publish a release; `READ` and `TRIAGE` cannot: say so.
3. The rules over `chantier/` branches: `gh api repos/<owner>/<repo>/rules/branches/<a chantier/ branch name>` (the name need not exist; write its `/` raw, which the endpoint answered like `%2F`, tried 2026-11-13). A `non_fast_forward` rule refuses the force push, `update` the push, `creation` a new branch: name each with its ruleset. The legacy branch protection is read only for an `ADMIN` account, else say "not readable with your rights".
A stack, a merge by the steering session, GitLab and what the user hears: part 2.
4. A stack (made by `forge-stack` or by the extension): the stacks API, `gh api repos/<owner>/<repo>/stacks -X GET -F per_page=1`. A 404 or 403 means no native stack on this repository: warn that `forge-stack create` or the extension will fail there, and that the stack then stays a chain.
5. A merge by the steering session (a release on its own, fixes on a grant), and a stack (merged by the user in one action): the default branch's rules, `gh api repos/<owner>/<repo>/rules/branches/<default branch>`, and the methods, `gh repo view --json mergeCommitAllowed,rebaseMergeAllowed,squashMergeAllowed`. Warn on: a `pull_request` rule with required approving reviews (a steering session's merge of its own account's PR waits for a review it cannot give: the grant's merge stops); a `required_status_checks` rule (the merge waits for those checks: said, not a problem); a `merge_queue` rule (a merge enqueues instead of merging, and a stack's one-action merge may not apply); the project's merge method (its rules, for instance "merge by rebase") not among the allowed ones. The legacy branch protection is read as item 3 says (an `ADMIN` account only).
GitLab: `help forge-permissions-gitlab`. What the user hears: `help forge-permissions-say`.
